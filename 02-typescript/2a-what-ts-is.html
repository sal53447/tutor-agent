Part 2 · TypeScript · 2a

What TypeScript Actually Is

TypeScript is a static type checker that compiles to plain JavaScript. Types are erased at build time — at runtime, there is no TypeScript, only JS.

// TS source:
function add(a: number, b: number): number { return a + b; }

// After compilation — types gone:
function add(a, b) { return a + b; }

This has two consequences. First, types are a design tool, not a runtime guarantee. Validate external data at runtime — the TS compiler cannot protect you from malformed JSON. Second, adoption is incremental. Rename a .js to .ts, fix errors, move on.

Run your first compile

npm install -D typescript
npx tsc --init          # generates tsconfig.json
echo 'const x: number = "oops";' > hello.ts
npx tsc hello.ts

The compiler prints:

hello.ts:1:7 - error TS2322: Type 'string' is not assignable to type 'number'.

1 const x: number = "oops";
        ~

Fix it (const x: number = 42;), run npx tsc hello.ts again — it emits hello.js with types stripped. That .js file is what Node (or the browser) actually runs.

Workflow tip

In real projects you rarely invoke tsc yourself — Vite, Next.js, or ts-node run it for you. But understanding what it produces is non-negotiable: the emitted JS is what ships.

Python bridge

Think of Python's type hints + mypy, but enforced and with much deeper inference. Python hints are often aspirational; TS is where teams actually rely on the types. The cultural adoption is more like Rust than like Python annotations.

Structural typing — the mental model

TS is structural: a type matches if its shape matches, regardless of name. Python / Java / C# are mostly nominal (named).

type Named = { name: string };
function greet(x: Named) { return x.name; }

// Works — structural match, no `implements Named` declaration needed
greet({ name: "P", age: 30 });
Why this matters

Structural typing means duck-typed JS idioms (plain objects, options bags) get typed naturally. But it also means { userId: string } and { orderId: string } are interchangeable if you don't use "branded types" (see 2f). Be explicit when semantic distinctions matter.
