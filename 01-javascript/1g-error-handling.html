Error Handling

JS's error model: throw anything, catch anything. Idiomatically: throw an Error (or subclass). Catch at boundaries — handlers, middleware, try around awaits.

class NotFoundError extends Error {
  constructor(resource) {
    super(`${resource} not found`);
    this.name = "NotFoundError";
    this.code = "NOT_FOUND";
  }
}

try {
  const user = await db.users.findOrThrow(id);
} catch (err) {
  if (err instanceof NotFoundError) return res.status(404).send();
  throw err;  // re-throw unknown
}
Python bridge

Same idea as Python exceptions, fewer built-in types. JS has no exception hierarchy for domain errors — you build your own. finally works the same.

error.cause — wrapping errors (ES2022)

Pass a cause option when re-wrapping an error so the original is preserved in the chain. Logging tools and Node's util.inspect will print the full chain.

async function loadUser(id) {
  try {
    return await db.query("SELECT ...", [id]);
  } catch (err) {
    throw new Error(`Failed to load user ${id}`, { cause: err });
  }
}

// Accessing the chain:
try {
  await loadUser(42);
} catch (err) {
  console.error(err.message);       // "Failed to load user 42"
  console.error(err.cause.message); // original DB error
}

Async error flows — await vs fire-and-forget

// SAFE: try/catch around await catches both sync throws and rejections
async function handler() {
  try {
    const data = await fetchData();
    await save(data);
  } catch (err) {
    // catches any rejection from fetchData() or save()
    logger.error(err);
    throw err;
  }
}

// DANGEROUS: fire-and-forget — rejection is unhandled
async function handler() {
  fetchData().then(save);   // no await, no .catch — crashes Node silently in older versions
}

// If you genuinely want to run async work without awaiting, attach a catch:
fetchData().then(save).catch(logger.error);

AggregateError

Promise.any rejects with an AggregateError when all input promises reject. It holds all individual errors in .errors.

try {
  await Promise.any([fetchA(), fetchB()]);
} catch (err) {
  if (err instanceof AggregateError) {
    err.errors.forEach(e => console.error(e));
  }
}

Result pattern — the optional alternative

Some codebases prefer returning [error, value] tuples or Result<T, E> types (popular in Rust, TS libraries like neverthrow). This forces the caller to handle errors explicitly. Pragmatic trade-off: throw is idiomatic, Result is safer but adds friction.

Code review
  • catch (err) with no type narrowing and no re-throw is usually hiding bugs.
  • Don't throw strings or numbers. Throw an Error — you want the stack trace.
  • In async: .catch(() => {}) silences errors and is almost always wrong. At minimum log.
  • On the server, let unexpected errors propagate to a top-level handler (Express error middleware, Next error boundary, Node process.on("uncaughtException") for last-resort logging before exit).
Self-check — re-throw and instanceof
1. A catch block handles NotFoundError and re-throws everything else. Write it.

if (!(err instanceof NotFoundError)) throw err; — always re-throw errors you don't own. Swallowing unknown errors hides bugs.

2. You catch (err) and check err instanceof Error — is that always true?

No. JS lets you throw any value — strings, numbers, plain objects. instanceof Error is only reliable if every throw site uses new Error() or a subclass. Third-party code may not. Always guard before accessing .message or .stack.

3. What's the difference between these two async patterns — and which one risks an unhandled rejection?
// A
async function run() { await fetchData(); }

// B
async function run() { fetchData(); }

Pattern B. Without await, the returned promise is floating — if fetchData rejects, there's no handler. Pattern A propagates the rejection to the caller of run() where it can be caught.
