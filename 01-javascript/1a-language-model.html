Part 1 · JavaScript · 1a

The Language Model — history, runtime, values, equality

This lesson makes you fluent in the shape of JS — the runtime, the value system, the equality rules, the legacy corners. Everything else (functions, async, React, Next) builds on this.

The 5-minute history

Brendan Eich designed JS in 10 days at Netscape in 1995. Originally Mocha, then LiveScript, then renamed to JavaScript to ride Java's marketing. The languages are unrelated. The spec is now called ECMAScript and updates yearly.

ES2015 ("ES6") was the inflection point — let, const, arrow functions, classes, Promises, modules, destructuring, template literals. Modern JS is a legitimately good language if you stick to the post-2015 subset.

Python bridge

Python was designed deliberately by one person over years. JS was designed in 10 days, then governed by committee under a strict "don't break the web" constraint. This explains most of the "weird JS" you'll encounter — it's fossils from that rushed design that cannot be removed without breaking existing websites.

The runtime model

JavaScript is single-threaded, event-loop-based, dynamically typed, garbage-collected, and JIT-compiled. Only one thing runs at a time. All concurrency happens through a task queue (covered in depth in 1f).

Python bridge

Python is also single-threaded (GIL) and dynamically typed. The key difference: Python uses threads with asyncio as an opt-in, while JS is non-blocking by default. If you block the JS thread, the entire program freezes — this shapes every JS API toward async.

Values vs references: two buckets

There are exactly two kinds of things in JS. The seven primitives (string, number, boolean, null, undefined, symbol, bigint) are passed and compared by value. Everything else — arrays, functions, dates, objects, Maps — is passed and compared by reference.

typeof null === "object" — a JS fossil from 1995. null is a primitive, but the type tag was never fixed. Check for null explicitly with === null, not typeof.

symbol creates a guaranteed-unique key: const id = Symbol("id"). Two calls with the same description are never equal. Symbols power the iterator protocol (Symbol.iterator) and other well-known hooks the runtime uses to extend built-in behaviour.

// Primitives: value equality
"hello" === "hello"   // true
42 === 42             // true

// Objects: reference equality only
{ a: 1 } === { a: 1 } // false — two distinct objects
[1, 2] === [1, 2]     // false

const x = { a: 1 };
const y = x;
x === y               // true — same reference
Gotcha

JS has no built-in deep equality. You write it yourself or reach for lodash.isEqual / assert.deepStrictEqual. Python's == on lists/dicts does value equality; JS's === on objects does not.

Equality: ==, ===, Object.is

Three operators, all different. == performs type coercion and produces pretzel logic. === is strict — no coercion. Object.is is like === but treats NaN and -0 differently.

// Why == is banned in practice:
0 == "0"           // true
0 == ""            // true
"" == false        // true
null == undefined  // true
[] == false        // true

// === is the real equality:
0 === "0"          // false
null === undefined // false
NaN === NaN        // false (the one weird case)
Object.is(NaN, NaN) // true
Rule

Always use ===. The only legitimate == is x != null, which uniquely catches both null and undefined in one check. Every respectable ESLint config enforces this via the eqeqeq rule.

Truthiness — the Python-developer trap

The eight falsy values: false, 0, -0, 0n, "", null, undefined, NaN. Everything else is truthy — including [] and {}.

Python bridge

In Python, if my_list: works as "is this non-empty?" because empty collections are falsy. In JS, if (arr) is true for []. The idiomatic JS check is if (arr.length) or if (arr.length > 0). This catches every Python dev at least once.

Your daily tools: ?? and ?.

Nullish coalescing ?? defaults only on null/undefined. Optional chaining ?. short-circuits on null/undefined without throwing.

// || treats 0 and "" as "missing" — often a bug:
const port = process.env.PORT || 3000;  // BUG if PORT is "" or "0"
const port = process.env.PORT ?? 3000;  // only falls back if unset

// Optional chaining:
const city = user?.address?.city;   // undefined if any link missing
callback?.();                        // only calls if defined
arr?.[0];                            // nil-safe index
Rule of thumb

Default to ?? for defaults. Use || only when you genuinely want to coalesce on all falsies (rare). Use ?. aggressively — it's the closest JS gets to Python's getattr(x, 'y', None) chains, and much nicer.

const is a binding, not a value

const arr = [1, 2, 3];
arr.push(4);      // legal — the binding is unchanged
arr = [];         // TypeError — rebinding forbidden

const means "this name always refers to the same value." It does not freeze the value. Immutability in JS is convention + spread operators + (optionally) tools like Immer. This matters enormously in React, where mutating state in place doesn't trigger re-renders.

Code review
  • var → reject. Use const; fall back to let when you need to reassign.
  • if (count) — rejects 0. Use if (count != null).
  • opts.x || default for config — almost always a bug. Use ??.
  • Object.freeze used as "security" — pointless. It's shallow and advisory.
  • Global isNaN(x) — broken (coerces). Use Number.isNaN(x).
Self-check — two questions
1. A colleague writes const ms = opts.timeoutMs || 5000;. What's the bug?

If the caller passes timeoutMs: 0 (a legitimate "no timeout" value in some APIs), they get 5000 instead. Fix: opts.timeoutMs ?? 5000.

2. if (user.preferences.darkMode) { ... } — two things can go wrong. Which two?

(a) If user.preferences is undefined, this throws TypeError. Use user.preferences?.darkMode. (b) If darkMode is the string "false" (from, say, a query param), the condition is truthy. Don't rely on coercion — explicitly check === true or parse the value.
