Part 1 · JavaScript · 1c

Objects, Prototypes, and Classes

JS has no "dict" and no "class" in the Python sense. Everything non-primitive is an object — a property bag with a chain of parent prototypes. class is syntactic sugar over the same mechanism.

Object literals — the everyday workhorse

const user = {
  name: "Pouyan",
  age: 30,
  greet() { return `hi, ${this.name}`; },   // shorthand method
  [dynamicKey]: "value",                      // computed key
  ...otherObj,                                // spread-copy
};

// Access:
user.name           // dot
user["name"]        // bracket
user?.address?.city // nil-safe chain

// Iterate:
Object.keys(user);    // string keys
Object.values(user);
Object.entries(user); // [[k, v], ...] — use with for...of

The prototype chain

Every object has an internal link ([[Prototype]]) to another object. Property lookup walks this chain. The chain ends at Object.prototype, then null.

const parent = { hello() { return "hi"; } };
const child = Object.create(parent);
child.hello();   // "hi" — walked up to parent

Object.getPrototypeOf(child) === parent;  // true

Classes — sugar, not a new concept

class User {
  #password;                    // private field (real private since ES2022)
  static defaultRole = "guest"; // static field

  constructor(name) {
    this.name = name;
  }
  greet() { return `hi, ${this.name}`; }
  get upperName() { return this.name.toUpperCase(); }   // computed property

  static fromRow(row) { return new User(row.name); }    // factory
}

class Admin extends User {
  constructor(name) { super(name); this.role = "admin"; }
}
Python bridge

JS classes look like Python classes but are subtly different. Python methods are "just functions stored on the class"; JS methods go on the prototype. Python has multiple inheritance and MRO; JS has single inheritance via extends. For "data classes," Python has @dataclass; JS just uses plain objects or TS interfaces. Use classes when you have real invariants, methods, or polymorphism — otherwise a plain object is often cleaner.

Destructuring

Destructuring pulls values out of objects or arrays into bindings. You'll see it everywhere — function parameters, imports, React hooks.

// Object destructuring
const { name, age } = user;
const { name: userName, role = "guest" } = user;  // rename + default
const { address: { city } } = user;               // nested

// Rest in objects
const { name, ...rest } = user;  // rest gets remaining own enumerable keys

// Array destructuring
const [first, second] = [10, 20, 30];
const [, second2] = [10, 20];    // skip first
const [head, ...tail] = arr;     // rest in arrays

// Function parameter form — the most common use in practice
function greet({ name, role = "guest" }) {
  return `${name} (${role})`;
}
greet({ name: "Pouyan" });         // "Pouyan (guest)"
Python bridge

Object destructuring is roughly Python's name, age = user["name"], user["age"] but cleaner. Array destructuring is Python's tuple unpacking: first, *rest = items. The default-value syntax (= "guest") only fires on undefined, not on null — a common gotcha.

Object spread and Object.assign

Spread copies own enumerable properties shallowly. "Last write wins" when keys conflict — put overrides last.

const defaults = { color: "blue", size: "medium", weight: 1 };
const overrides = { color: "red" };

const config = { ...defaults, ...overrides };
// { color: "red", size: "medium", weight: 1 }

// Object.assign is the pre-ES2018 equivalent (mutates the first argument):
const config2 = Object.assign({}, defaults, overrides);

// Common patterns:
const updated = { ...user, email: "new@example.com" }; // "update" a field
const clone   = { ...obj };                             // shallow copy
Shallow only

Both spread and Object.assign are one level deep. Nested objects are still shared by reference. For deep merging reach for a library (lodash.merge) or write it explicitly.

hasOwnProperty vs in

const obj = { a: 1 };

"a" in obj                    // true — own OR inherited
"toString" in obj             // true — inherited from Object.prototype

obj.hasOwnProperty("a")       // true — own only
obj.hasOwnProperty("toString") // false

// Safer alias (avoids prototype-shadowing edge cases):
Object.hasOwn(obj, "a");      // true — ES2022, prefer this

Use Object.hasOwn (ES2022) or Object.prototype.hasOwnProperty.call(obj, key) when you need to know if a key was explicitly set on the object — not inherited. Use in when you want to check the full prototype chain (e.g., "does this object support this method?").

Code review
  • Don't inherit deeply. The React and Node ecosystems are "composition over inheritance" — two levels max is a good rule.
  • Private fields (#foo) are real privacy, enforced at runtime. Use them over the old _foo naming convention.
  • Object.create(null) gives you a prototype-free "pure map" — useful when keys might collide with __proto__ / toString, e.g., caches keyed by user input. A Map is usually cleaner.
