Databases — ORMs, Migrations, Transactions

Connection URL anatomy

postgresql://user:password@host:5432/dbname?schema=public&connection_limit=10
#            ^^^^  ^^^^^^^^  ^^^^  ^^^^  ^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#            user  password  host  port  db      query params (Prisma-specific)

Put this in DATABASE_URL. Never commit it. In production, the password comes from a secret manager injected as an env var at runtime.

Connection pool — why it matters

Node is long-lived (unlike Python/PHP where each request can be a new process). A pool of, say, 10 persistent connections handles hundreds of requests per second without the overhead of TCP+TLS+auth per query. The right pool size is roughly cpu_cores * 2 per instance — too high and you saturate the DB; too low and requests queue. In serverless environments (Lambda, Vercel Functions) each instance is short-lived and can spin up many concurrent cold-starts simultaneously, overwhelming a traditional pool. Use PgBouncer or Prisma Accelerate as a connection proxy in front of the DB.

The three idioms

  • Prisma — schema-first, generates a typed client. Great DX. The de facto default for new Node apps. Migration tooling is strong. Downside: less flexible for unusual queries.
  • Drizzle — SQL-first schemas in TS, thin wrapper. If you like SQL, this is the one. Gaining ground fast.
  • Kysely — type-safe query builder. Closer to the metal; no heavy abstraction. Great when you want full SQL control with typing.
Python bridge

Prisma ≈ SQLAlchemy ORM + Alembic with better TS integration. Drizzle ≈ SQLAlchemy Core. Kysely ≈ bare sqlalchemy.select() with type stubs. Migration workflow: Alembic's alembic upgrade head = prisma migrate deploy; alembic revision --autogenerate = prisma migrate dev. The concepts (revision files, upgrade/downgrade, keeping them in VCS) are identical.

Drizzle — code example

// schema.ts
import { pgTable, serial, text, timestamp } from "drizzle-orm/pg-core";

export const users = pgTable("users", {
  id:           serial("id").primaryKey(),
  email:        text("email").notNull().unique(),
  passwordHash: text("password_hash").notNull(),
  createdAt:    timestamp("created_at").defaultNow().notNull(),
});

// db.ts
import { drizzle } from "drizzle-orm/node-postgres";
import { Pool } from "pg";
export const db = drizzle(new Pool({ connectionString: env.DATABASE_URL }));

// Repository usage
import { eq } from "drizzle-orm";
import { db } from "../lib/db";
import { users } from "../db/schema";

export async function findByEmail(email: string) {
  return db.select().from(users).where(eq(users.email, email)).limit(1).then(r => r[0]);
}
export async function create(data: typeof users.$inferInsert) {
  return db.insert(users).values(data).returning().then(r => r[0]);
}

Migrations

Migrations are VCS-tracked SQL files that describe schema changes incrementally. Never edit the DB by hand in any environment you care about.

CommandWhen to use
prisma migrate devLocal development — generates migration files, applies them, regenerates client.
prisma migrate deployCI/CD and production — applies pending migrations without prompting or generating new files. Safe to run as part of a deploy pipeline.
prisma migrate resetLocal only — drops the DB and replays all migrations. Never run in production.

Drizzle equivalent: drizzle-kit generate (generate migration SQL) + drizzle-kit migrate (apply). The deploy pattern is identical: generate locally, commit the SQL, apply in CI.

Transactions

// Prisma
await prisma.$transaction(async (tx) => {
  const user = await tx.user.create({ data: {...} });
  await tx.audit.create({ data: { userId: user.id, action: "created" } });
});

The N+1 problem

You query 100 users, then loop and query each user's posts one at a time. That's 101 queries. Solution: eager loading (Prisma: include, Drizzle: with), or batch fetch with an IN clause. In GraphQL, use DataLoader.

Review flags
  • Migrations not checked into VCS. Reject.
  • Direct SQL with string interpolation. SQL injection risk — use parameterized queries always.
  • Connection pools not sized for the deployment. Too high = DB dies; too low = app queues.
  • Long-running transactions. Acquire locks for as short a window as possible.
  • prisma migrate deploy missing from the deploy pipeline. Schema drift between DB and code causes 500s at runtime.
  • Default pool size (10) used unchanged in a serverless function that can fork 500 concurrent instances. Use a proxy.
Self-check — two questions
1. You run prisma migrate dev on a feature branch that adds a NOT NULL column with no default. It works locally on an empty DB but fails in staging. Why?

Staging has existing rows. Adding a NOT NULL column with no default requires either a DEFAULT value or a two-step migration: add nullable → backfill → add constraint. Prisma generates the SQL but it's your responsibility to handle existing data.

2. A colleague opens a transaction, calls an external HTTP API inside it, then commits. What's the risk?

The external call can be slow or hang, holding the transaction open and locking rows for the duration. Other requests queue waiting for the lock. Rule: never call external services inside a transaction — do the external call first, then open the transaction for DB writes.
