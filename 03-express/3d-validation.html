Part 3 · Express · 3d

Validation & Serialization

Never trust client input. The TS compiler doesn't run at runtime; a malicious or buggy client can send anything. Zod (or Valibot, or Joi) validates at runtime and produces typed, sanitized data.

import { z } from "zod";

const CreateUser = z.object({
  email: z.string().email(),
  password: z.string().min(8).max(200),
  age: z.coerce.number().int().positive().optional(),
});

// Extract the TypeScript type from the schema — single source of truth
type CreateUserInput = z.infer;
// Equivalent to: { email: string; password: string; age?: number }

function validate(schema: T) {
  return (req, res, next) => {
    const r = schema.safeParse(req.body);
    if (!r.success) return res.status(400).json({ issues: r.error.issues });
    req.body = r.data;   // now typed and clean
    next();
  };
}

app.post("/users", validate(CreateUser), controllers.createUser);

Validating params and query strings

// req.params — usually a numeric/UUID ID
const UserIdParam = z.object({ id: z.string().uuid() });

// req.query — everything arrives as string; coerce explicitly
const ListUsersQuery = z.object({
  page:   z.coerce.number().int().positive().default(1),
  limit:  z.coerce.number().int().min(1).max(100).default(20),
  search: z.string().max(100).optional(),
});

// Generic validate() extended to cover source
function validateSource(
  schema: T,
  source: "body" | "params" | "query",
) {
  return (req, res, next) => {
    const r = schema.safeParse(req[source]);
    if (!r.success) return res.status(400).json({ issues: r.error.issues });
    req[source] = r.data;
    next();
  };
}

usersRouter.get(
  "/:id",
  validateSource(UserIdParam, "params"),
  requireAuth,
  ctrl.getUser,
);

usersRouter.get(
  "/",
  validateSource(ListUsersQuery, "query"),
  ctrl.listUsers,
);

Response serialization — never return raw DB rows

// DB model has: id, email, passwordHash, createdAt, deletedAt, stripeCustomerId, ...
// We want to expose only a safe subset to the client.

const UserResponse = CreateUser.pick({ email: true }).extend({
  id:        z.string().uuid(),
  createdAt: z.string().datetime(),
});
type UserResponse = z.infer;

// In the controller:
res.json(UserResponse.parse(user));  // strips any field not in the schema
// If the DB row ever gains a new sensitive column, it's automatically excluded.
Python bridge

Zod schemas are the TypeScript equivalent of Pydantic models. z.infer<typeof Schema> is the same concept as a Pydantic model class being both a validator and a type annotation. schema.parse() = Model.model_validate(); schema.safeParse() = Model.model_validate() with raise_on_error=False. Response schemas = FastAPI's response_model= parameter.

Valibot — size-conscious alternative

If bundle size matters (e.g., edge functions, client-side validation), Valibot offers near-identical ergonomics at ~7 KB vs Zod's ~57 KB. The API differs slightly but the concepts — schemas, inference, parse vs safeParse — are the same.

Review flags
  • req.body.foo read directly without a validator. Reject.
  • Using any on the handler input. Validate; infer the type from the schema.
  • Validation scattered across routes instead of centralized in schemas. Build a schema registry.
  • Serializing raw DB rows (including password_hash, internal columns) in responses. Use a response schema and pick.
  • req.params.id used as a raw string in a DB query without UUID validation. A client that sends "../../etc/passwd" won't succeed here but validating params prevents unexpected behavior in path-sensitive logic.
  • req.query.limit passed as a string directly to .take(). Coerce with z.coerce.number() — SQL drivers don't coerce for you.
Self-check — two questions
1. A colleague writes type CreateUserInput = { email: string; password: string } in a separate file and imports it in the controller. You have a Zod CreateUser schema. What's the problem?

Two sources of truth. If the schema changes (e.g., adds a required role field), the type won't update automatically. Use type CreateUserInput = z.infer<typeof CreateUser> — one source.

2. UserResponse.parse(user) is in the controller. A DB column named internalScore gets added to the Prisma model. Is it safe to send without changing the controller?

Yes — .parse() strips any field not declared in the schema. The new column is silently excluded. This is the key advantage over spread/manual deletion.
