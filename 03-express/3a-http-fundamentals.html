HTTP Fundamentals

Before Express, the protocol it sits on. You'll debug HTTP your entire career; knowing the model well pays off.

Methods — semantics matter

MethodIdempotent?Body?Use for
GETYesNoRead
POSTNoYesCreate / action
PUTYesYesReplace
PATCHNo (usually)YesPartial update
DELETEYesMaybeRemove

Status codes — the ones that matter

  • 200 OK, 201 Created, 204 No Content
  • 301 Permanent redirect, 302/307 Temporary
  • 400 Bad Request (validation), 401 Unauthorized (not authenticated), 403 Forbidden (authenticated but not allowed), 404 Not Found, 409 Conflict, 422 Unprocessable, 429 Too Many Requests
  • 500 Internal, 502 Bad Gateway, 503 Unavailable, 504 Timeout
401 vs 403

Common confusion. 401 = "I don't know who you are — log in." 403 = "I know who you are, but you can't do this." Send the right one; tools and middleware depend on the distinction.

Request / response walkthrough — one GET over the wire

# 1. Client sends (TCP stream, then TLS, then HTTP/1.1)
GET /users/42 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGci...
Accept: application/json

# 2. Server responds
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=60
X-Request-Id: 3f2a1b

{"id":42,"email":"alice@example.com"}

Between step 1 and 2: DNS resolves the host, TCP handshake (or TLS 1.3 0-RTT resumption), request parsed by Node's HTTP parser, passed to Express, hits your middleware stack, reaches the route handler, service/repo fetches from DB, response serialized. That's the full picture. Debug from left to right when things break.

Headers and cookies

  • Content-Type: application/json, multipart/form-data, text/html...
  • Authorization: Bearer <token> for JWT.
  • Cookie / Set-Cookie: sessions. Flags: HttpOnly (no JS access — anti-XSS), Secure (HTTPS only), SameSite=Lax|Strict (CSRF mitigation).
  • Cache-Control: directive cheat-sheet below.

Cache-Control — the directives that actually matter

DirectiveMeaning
no-storeNever cache. Sensitive data (banking, health). Forces full round-trip every time.
no-cacheCache it, but always revalidate before serving. Uses an ETag or Last-Modified check. One round-trip, but cheaper than no-store if the resource hasn't changed.
max-age=NServe from cache for N seconds without checking. Good for static assets with content hashes in the filename.
s-maxage=NSame as max-age but applies only to shared caches (CDNs). Lets you cache at the edge longer than at the browser.
stale-while-revalidate=NServe stale for up to N seconds while fetching a fresh copy in the background. Best of both worlds for non-critical data: fast response + eventual freshness.
privateCDN must not cache; browser may. Use for user-specific responses.

HTTP/2 and HTTP/3 — one paragraph each

HTTP/2 uses a single TCP connection and multiplexes multiple requests/responses over it simultaneously (no head-of-line blocking per request). TLS is effectively required in practice. Node supports it natively; most reverse proxies (nginx, Caddy) terminate HTTP/2 for you.

HTTP/3 swaps TCP for QUIC (UDP-based), eliminating TCP head-of-line blocking entirely. Critical for mobile clients on lossy networks. Supported by Cloudflare, Fastly, and modern nginx/Caddy builds. Your Node code doesn't change; the transport is negotiated below you.

HTTP streaming — chunked transfer and SSE

Normal responses buffer the body, set Content-Length, then send. Streaming skips the buffer: data flows as it's produced, using Transfer-Encoding: chunked. Two common patterns:

// Chunked — arbitrary binary/text stream
app.get("/download", (req, res) => {
  res.setHeader("Content-Type", "text/plain");
  res.write("chunk one\n");
  setTimeout(() => {
    res.write("chunk two\n");
    res.end();           // flushes and closes
  }, 500);
});

// Server-Sent Events (SSE) — browser-native event stream
// Client uses: const es = new EventSource("/events");
app.get("/events", (req, res) => {
  res.setHeader("Content-Type", "text/event-stream");
  res.setHeader("Cache-Control", "no-cache");
  res.setHeader("Connection", "keep-alive");

  const send = (data: object) => res.write(`data: ${JSON.stringify(data)}\n\n`);

  send({ type: "connected" });
  const iv = setInterval(() => send({ type: "heartbeat", ts: Date.now() }), 15_000);
  req.on("close", () => clearInterval(iv));  // clean up when client disconnects
});

SSE is one-directional (server → client). Use it for live feeds, progress bars, and AI token streaming. For bidirectional, use WebSockets.

CORS in two paragraphs

By default, browsers block cross-origin JS from reading another origin's responses (same-origin policy). CORS is the server's opt-in: the server returns Access-Control-Allow-Origin (and friends) to say which origins may read. For "unsafe" methods or custom headers, the browser sends a preflight OPTIONS request first.

Most CORS pain is configuring the server to return the right headers. Use the cors middleware and configure explicit origins — never * on an authenticated API.

import cors from "cors";

const ALLOWED_ORIGINS = [
  "https://app.example.com",
  "https://admin.example.com",
  ...(process.env.NODE_ENV === "development" ? ["http://localhost:3000"] : []),
];

app.use(cors({
  origin: (origin, cb) => {
    // allow server-to-server calls (no origin header) and listed origins
    if (!origin || ALLOWED_ORIGINS.includes(origin)) return cb(null, true);
    cb(new Error(`CORS: origin ${origin} not allowed`));
  },
  credentials: true,          // required when client sends cookies/Authorization
  allowedHeaders: ["Content-Type", "Authorization"],
  maxAge: 86_400,             // preflight cached for 24h
}));
Self-check — two questions
1. A CDN sits in front of your API. You want the CDN to cache a user listing for 5 minutes but the browser to revalidate every time. Which Cache-Control header achieves that?

Cache-Control: no-cache, s-maxage=300. s-maxage controls the shared (CDN) cache; no-cache tells browsers to always revalidate.

2. Your SSE endpoint works locally but disconnects after 30 seconds in production (behind nginx). What nginx directive is almost certainly the cause?

proxy_read_timeout defaults to 60s; idle SSE connections get killed. Set proxy_read_timeout 3600s; and ensure proxy_buffering off; so chunks reach the client immediately rather than buffering.
