Part 3 · Express · 3e

Auth — Sessions, JWT, OAuth

Sessions (stateful, cookie-based)

Server stores session data keyed by an opaque session ID; client holds only the ID in an HttpOnly cookie. Simple, secure, revocable. Scales with a shared session store (Redis).

import session from "express-session";
import RedisStore from "connect-redis";
import { createClient } from "redis";

const redisClient = createClient({ url: env.REDIS_URL });
await redisClient.connect();

app.use(session({
  store: new RedisStore({ client: redisClient }),
  secret: env.SESSION_SECRET,   // rotate with key array: [newSecret, oldSecret]
  resave: false,
  saveUninitialized: false,
  cookie: {
    httpOnly: true,
    secure: env.NODE_ENV === "production",  // HTTPS only in prod
    sameSite: "lax",
    maxAge: 7 * 24 * 60 * 60 * 1000,       // 7 days
  },
}));

// Login handler sets session
app.post("/auth/login", async (req, res) => {
  const user = await verifyCredentials(req.body);
  req.session.userId = user.id;
  req.session.role   = user.role;
  res.json({ ok: true });
});

// requireAuth middleware for session-based auth
export function requireAuth(req, res, next) {
  if (!req.session?.userId) return res.status(401).json({ error: "unauthenticated" });
  res.locals.userId = req.session.userId;
  next();
}

JWT (stateless, bearer token)

Server signs a compact JSON payload containing claims. Client sends it in Authorization: Bearer .... Server verifies the signature; no DB lookup.

// JWT verification middleware using jose (Web Crypto API, works in edge runtimes)
// npm install jose
import { jwtVerify, SignJWT } from "jose";

const JWT_SECRET = new TextEncoder().encode(env.JWT_SECRET);

// Sign a token (at login)
export async function signToken(payload: { sub: string; role: string }) {
  return new SignJWT(payload)
    .setProtectedHeader({ alg: "HS256" })
    .setIssuedAt()
    .setExpirationTime("15m")   // short-lived access token
    .sign(JWT_SECRET);
}

// requireAuth middleware for JWT
export async function requireAuth(req, res, next) {
  const header = req.headers.authorization;
  if (!header?.startsWith("Bearer ")) {
    return res.status(401).json({ error: "unauthenticated" });
  }
  try {
    const { payload } = await jwtVerify(header.slice(7), JWT_SECRET);
    res.locals.userId = payload.sub as string;
    res.locals.role   = payload.role as string;
    next();
  } catch {
    res.status(401).json({ error: "invalid_token" });
  }
}
The JWT gotcha nobody tells you

JWTs are not revocable before expiry without adding a revocation list (which brings back server state, defeating the point). For session-like auth on your own app, sessions are usually the better choice. Use JWTs for short-lived access tokens, service-to-service auth, or where you genuinely have no shared session store.

Refresh token pattern

Short-lived access token (15 min) + long-lived refresh token (30 days). Access token goes in the Authorization header; refresh token lives in an HttpOnly cookie (unreachable by JS).

// POST /auth/login — issue both tokens
app.post("/auth/login", async (req, res) => {
  const user = await verifyCredentials(req.body);
  const accessToken  = await signToken({ sub: user.id, role: user.role });
  const refreshToken = await signRefreshToken({ sub: user.id });   // longer expiry, different secret

  res.cookie("refreshToken", refreshToken, {
    httpOnly: true,
    secure: env.NODE_ENV === "production",
    sameSite: "strict",
    maxAge: 30 * 24 * 60 * 60 * 1000,   // 30 days
    path: "/auth/refresh",               // only sent to this path
  });
  res.json({ accessToken });
});

// POST /auth/refresh — exchange refresh token for a new access token
app.post("/auth/refresh", async (req, res) => {
  const token = req.cookies.refreshToken;
  if (!token) return res.status(401).json({ error: "no_refresh_token" });
  try {
    const { payload } = await jwtVerify(token, REFRESH_SECRET);
    const accessToken = await signToken({ sub: payload.sub as string, role: payload.role as string });
    res.json({ accessToken });
  } catch {
    res.status(401).json({ error: "invalid_refresh_token" });
  }
});

OAuth 2.0 in two sentences

Delegate authentication to a provider (Google, GitHub). The user's browser is redirected to the provider, consents, and returns with a code; your server exchanges the code for tokens. Prefer openid-client (the OIDC spec implementation) over legacy passport strategies — it handles PKCE, token rotation, and well-known discovery automatically. passport has sharp edges around token refresh and PKCE; if you're starting fresh, openid-client or a hosted provider (Auth0, Clerk) is the better call.

Python bridge

Express sessions + Redis store ≈ Flask-Login + Flask-Session (or Django's session framework). The cookie carries only an opaque ID; data lives server-side — identical model. JWT middleware ≈ Flask-JWT-Extended's @jwt_required() decorator. openid-client ≈ authlib's OAuth/OIDC client. The refresh token pattern is language-agnostic; the implementation steps are identical in both ecosystems.

CSRF

Only applies to cookie-based auth. A malicious site can't read your cookies but the browser will send them on requests to your site. Mitigation: SameSite=Lax cookies (now default), plus a CSRF token for state-changing requests. Bearer tokens (JWT in Authorization header) are immune because the browser doesn't auto-attach them.

RBAC vs ABAC

  • RBAC — users have roles, roles have permissions. Simple, common, "admin / editor / viewer."
  • ABAC — decisions made on attributes (user.team === resource.team). Flexible, harder to audit. Use when RBAC hits its limits.
// Thin RBAC middleware factory
export function requireRole(...roles: string[]) {
  return (req, res, next) => {
    if (!roles.includes(res.locals.role)) {
      return res.status(403).json({ error: "forbidden" });
    }
    next();
  };
}

// Usage: requireAuth must run first to populate res.locals.role
router.delete("/:id", requireAuth, requireRole("admin"), ctrl.deleteUser);
Self-check — two questions
1. A user logs out. Their JWT access token still has 14 minutes left. Under a pure stateless JWT scheme, can you invalidate it?

No — without server state, you cannot revoke a signed JWT before it expires. Solutions: (a) very short expiry (~5 min) so the blast radius is small; (b) a Redis revocation list keyed by jti (JWT ID) — but now you have server state; (c) switch to sessions, which are revocable by deleting the session record.

2. You store the refresh token in localStorage instead of an HttpOnly cookie. What attack vector does this open that HttpOnly prevents?

XSS. Any injected script can read localStorage and exfiltrate the refresh token. An HttpOnly cookie is invisible to JavaScript; the browser attaches it automatically but scripts cannot access it.
