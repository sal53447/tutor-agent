Express Core — Routing & Middleware

The hello world, then the real structure

import express from "express";
const app = express();

app.use(express.json());                    // parses JSON body

app.get("/users/:id", async (req, res) => {
  const user = await db.users.findById(req.params.id);
  if (!user) return res.status(404).json({ error: "not_found" });
  res.json(user);
});

app.listen(3000);

Middleware — the signature pattern of Express

Every Express handler is a middleware. The signature is (req, res, next) => void. Middlewares run in order. Call next() to continue, next(err) to jump to error handlers, or end the response (res.send()) to stop the chain.

// Log every request
app.use((req, res, next) => {
  console.log(`${req.method} ${req.url}`);
  next();
});

// Auth on a subtree
app.use("/admin", requireAdmin);

// Error middleware — note the FOUR arguments (err, req, res, next)
app.use((err, req, res, next) => {
  console.error(err);
  res.status(err.status || 500).json({ error: err.message });
});
Analogy

Middleware is an airport security checkpoint chain. Every passenger (request) goes through each station in order. Any station can reject, stamp, or wave through. The final "gate" is your route handler. Error middleware is the supervisor called when any station rejects.

Body parsers

app.use(express.json());                    // Content-Type: application/json
app.use(express.urlencoded({ extended: true }));  // Content-Type: application/x-www-form-urlencoded
// extended: true uses the qs library (nested objects); false uses querystring (flat only)

Both are needed if your API accepts HTML form POSTs or OAuth callbacks as well as JSON clients.

Splitting routes into files with express.Router()

// routes/users.routes.ts
import { Router } from "express";
import { requireAuth } from "../middleware/auth";
import * as ctrl from "../controllers/users.controller";

export const usersRouter = Router();

usersRouter.post("/",        validate(CreateUser), ctrl.createUser);
usersRouter.get("/:id",      requireAuth,          ctrl.getUser);
usersRouter.patch("/:id",    requireAuth,          ctrl.updateUser);
usersRouter.delete("/:id",   requireAuth,          ctrl.deleteUser);

// app.ts — mount the router
import { usersRouter } from "./routes/users.routes";
app.use("/users", usersRouter);     // → /users, /users/:id, etc.

Each resource gets its own file. app.ts becomes a list of app.use() mounts — nothing more.

Typed AppError

// errors/AppError.ts
export class AppError extends Error {
  constructor(
    public readonly status: number,
    message: string,
    public readonly code?: string,
  ) {
    super(message);
    this.name = "AppError";
  }
}

// Usage
throw new AppError(404, "User not found", "USER_NOT_FOUND");
throw new AppError(409, "Email already registered", "EMAIL_CONFLICT");

// Error middleware picks it up
app.use((err: unknown, req, res, next) => {
  if (err instanceof AppError) {
    return res.status(err.status).json({ error: err.message, code: err.code });
  }
  log.error({ err }, "unhandled error");
  res.status(500).json({ error: "internal_error" });
});

Request-ID middleware

// middleware/requestId.ts
import { randomUUID } from "crypto";

export function requestId(req, res, next) {
  const id = (req.headers["x-request-id"] as string) ?? randomUUID();
  res.locals.requestId = id;
  res.setHeader("X-Request-Id", id);
  // Attach child logger so every log from this request carries the ID
  res.locals.log = log.child({ requestId: id });
  next();
}

// app.ts — mount before all routes
app.use(requestId);

Rate limiting

import rateLimit from "express-rate-limit";

// Global limiter — blunt instrument, protects against runaway clients
app.use(rateLimit({ windowMs: 60_000, max: 100 }));

// Tighter on auth endpoints
app.use("/auth", rateLimit({
  windowMs: 15 * 60_000,   // 15 minutes
  max: 10,
  message: { error: "too_many_requests" },
  standardHeaders: true,   // adds RateLimit-* headers (draft-6)
  legacyHeaders: false,
}));

Async error-handling pitfall

// BROKEN in Express 4: async errors don't automatically reach error middleware
app.get("/x", async (req, res) => {
  const data = await mightThrow();   // if this rejects, Node sees unhandled rejection
  res.json(data);
});

// Fix in Express 4: wrap, or use express-async-errors package
app.get("/x", async (req, res, next) => {
  try { res.json(await mightThrow()); } catch (e) { next(e); }
});

// Express 5 (2024): async errors are captured automatically. Use Express 5.
Self-check — two questions
1. You mount app.use("/api", authMiddleware, apiRouter). A route inside apiRouter calls next("route") instead of next(). What happens?

next("route") skips the remaining handlers in the current route stack and moves to the next matching route. It does not skip the entire middleware chain — authMiddleware has already run. Use next("route") carefully; in most cases next() or returning a response is clearer.

2. Express receives a request for POST /users. Your middleware order is: (1) express.json(), (2) requestId, (3) rateLimit, (4) validate(CreateUser), (5) ctrl.createUser. What is the correct order in production, and why would you move rate limiting earlier?

Rate limiting should come before body parsing (move to position 1). Parsing the body allocates memory; a flood of large requests can exhaust memory before the rate limiter fires. The correct order: rate limiting → request ID → body parsing → validation → handler.
