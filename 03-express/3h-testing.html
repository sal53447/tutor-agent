Testing — Unit, Integration, Supertest

For new projects: use Vitest. It's faster than Jest, supports ESM natively, and has Jest-compatible APIs so migration is mechanical. Jest is fine if the project is already using it — no need to switch mid-flight.

Layers = testing strategy

  • Services — pure logic, easy unit tests. Mock the repo, test branches.
  • Repositories — test against a real DB (testcontainers or a local Postgres). Don't mock.
  • Routes — integration test with supertest. Start the app, hit endpoints, assert responses.
import request from "supertest";
import { createApp } from "../src/app";

test("POST /users creates a user", async () => {
  const app = createApp({ db: testDb, mailer: fakeMailer });
  const res = await request(app)
    .post("/users")
    .send({ email: "a@b.c", password: "hunter22!" });
  expect(res.status).toBe(201);
  expect(res.body.id).toBeDefined();
});

Testing auth-protected routes

// Helper — mint a real JWT the same way the app does
import { signToken } from "../src/middleware/auth";

async function authHeader(userId = "test-user-id", role = "user") {
  const token = await signToken({ sub: userId, role });
  return { Authorization: `Bearer ${token}` };
}

test("GET /users/:id requires auth", async () => {
  const app = createApp({ db: testDb });
  const res = await request(app).get("/users/some-id");
  expect(res.status).toBe(401);
});

test("GET /users/:id returns user when authenticated", async () => {
  const app = createApp({ db: testDb });
  await testDb.user.create({ data: { id: "some-id", email: "a@b.c", passwordHash: "x" } });
  const res = await request(app)
    .get("/users/some-id")
    .set(await authHeader("some-id", "user"));
  expect(res.status).toBe(200);
  expect(res.body.email).toBe("a@b.c");
  expect(res.body.passwordHash).toBeUndefined();  // confirm serialization strip
});

// Session-based auth: set the cookie instead
test("GET /profile with session cookie", async () => {
  const agent = request.agent(app);  // agent persists cookies across requests
  await agent.post("/auth/login").send({ email: "a@b.c", password: "hunter22!" });
  const res = await agent.get("/profile");
  expect(res.status).toBe(200);
});

Python bridge

supertest ≈ httpx.AsyncClient(app=app) in FastAPI or TestClient(app) in Starlette/Flask. Both create an in-process HTTP client that hits the real application stack without binding a port. Mocking the DB at the service boundary ≈ pytest fixtures with monkeypatch or unittest.mock.patch. The test-DB transaction rollback strategy has a direct analogue: pytest's db_session fixture that rolls back after each test.

Test-DB strategies
  • Wrap-each-test-in-a-transaction-and-rollback. Fastest. Doesn't support code that commits internally.
  • Truncate-tables-between-tests. Simple. Works with commits.
  • Spin-up-fresh-container-per-suite. Isolation. Slower.
Self-check — two questions
1. A service test mocks the repository and the test passes. Later, the real repository method is renamed but the mock still uses the old name. What's the failure mode?

The test continues passing against the mock while production fails at runtime — the classic mock/reality divergence. Remedies: (a) repository integration tests that verify the real method signature; (b) TypeScript typed mocks (vi.mocked()) that fail to compile if the mock no longer matches the type.

2. Why does the auth-route test use signToken() (the real app function) rather than a hard-coded token string?

If the signing algorithm, secret, or claims change, a hard-coded token becomes stale and the test fails for the wrong reason (bad fixture, not a real regression). Using signToken() means the test always produces a token that matches whatever the current verification logic expects.
