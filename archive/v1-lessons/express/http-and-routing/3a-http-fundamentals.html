HTTP Fundamentals

Express (3b) is a thin layer over Node's HTTP parser; everything it hands you — req.method, req.headers, a body that arrives as a stream, res.status() — is a field of the protocol. The rest of Part 3 assumes you can read a raw request, pick the right status code without looking it up, and say what Cache-Control a response needs. Next.js caching (5d) and the cors/cookie decisions in 3e are the same protocol seen from the other side.

Request / response anatomy — one GET over the wire

A request is three parts: a request line (method, path, version), headers (one per line, case-insensitive names), a blank line, then an optional body. A response mirrors it: status line, headers, blank line, body. That is the whole format; everything else is convention about which headers mean what.

# 1. Client sends (TCP stream, then TLS, then HTTP/1.1)
GET /users/42 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGci...
Accept: application/json

# 2. Server responds
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=60
X-Request-Id: 3f2a1b

{"id":42,"email":"alice@example.com"}

Between 1 and 2: DNS resolves the host, TCP handshake (then TLS — 1.3 needs one round-trip, 0-RTT on resumption), Node's parser turns bytes into req, the request walks your middleware stack, reaches the route handler, the service hits the DB, the response is serialised. When something breaks, debug left to right along that path: DNS → connection → TLS → status line → headers → body.

Mechanism

Request (top) and response (bottom) have the same three-part shape: first line, headers, blank line, body. Headers come before the body on both sides — which is why res.set() after res.json() throws (3b).

Step through
Python bridge

WSGI hands your app an environ dict and a start_response(status, headers) callable; Node hands you req and res streams. environ["wsgi.input"].read() ≈ consuming the req stream — which is why Express has body-parser middleware (express.json(), 3b) where Flask gives you request.get_json() on demand. start_response("201 Created", [("Content-Type", "application/json")]) ≈ res.writeHead(201, {…}); Express's res.status(201).type("json").send(…) ≈ Starlette's Response(content, status_code=201, media_type=…). FastAPI's status_code=201 on the decorator and raise HTTPException(404) have no decorator-level equivalent — in Express the handler sets the status every time (res.status(404)), or throws an error that error middleware maps (3b). Cookies: response.set_cookie(k, v, httponly=True, samesite="lax") ≈ res.cookie(k, v, { httpOnly: true, sameSite: "lax" }).

Methods — semantics matter

MethodIdempotent?Body?Use for
GETYes (and safe)NoRead
POSTNoYesCreate / action
PUTYesYesReplace
PATCHNo (usually)YesPartial update
DELETEYesMaybeRemove

Idempotent means repeating the request leaves the server in the same state — not that the response is the same (a second DELETE returns 404; still idempotent). Safe (GET, HEAD, OPTIONS) means no state change at all. Proxies, browsers and retry libraries act on these promises: a client that times out will retry an idempotent request automatically and will not retry a POST — so a POST that times out after the write succeeded is a duplicate waiting to happen. The fix is an Idempotency-Key header the server remembers.

Status codes — families, then the ones that matter

The first digit is the contract: 2xx it worked, 3xx look elsewhere, 4xx the client's fault (don't retry unchanged), 5xx the server's fault (retry with backoff). Clients, proxies and monitoring key off the family; the exact number is for humans and specific behaviours.

  • 200 OK, 201 Created (+ Location header of the new resource), 204 No Content (success, empty body — the DELETE response)
  • 301/308 Permanent redirect, 302/307 Temporary. 307/308 keep the method and body; 301/302 let browsers turn a POST into a GET.
  • 400 Bad Request (malformed, validation), 401 Unauthorized (not authenticated), 403 Forbidden (authenticated but not allowed), 404 Not Found, 409 Conflict (duplicate, version mismatch), 422 Unprocessable (well-formed, semantically wrong), 429 Too Many Requests (+ Retry-After)
  • 500 Internal, 502 Bad Gateway (upstream returned garbage), 503 Unavailable (overloaded, shutting down), 504 Gateway Timeout (upstream too slow)
401 vs 403

Common confusion. 401 = "I don't know who you are — log in." 403 = "I know who you are, but you can't do this." Send the right one: an API client refreshes its token on 401 and gives up on 403; retrying a 403 with a fresh token is wasted work, and a 401 for a permissions problem sends the user into a login loop.

Check order leaks data

Checking "does it exist" before "are you logged in" lets anonymous clients enumerate ids: 404 vs 401 tells them which records exist. Authenticate first, then authorise, then look up — or return 404 for both "no such row" and "not yours".

Mechanism

The family is the contract clients act on: 4xx says "the request is wrong, retrying as-is won't help", 5xx says "we are wrong, try again later". Sending 500 for a validation error makes clients retry a request that can never succeed.

Headers and cookies

  • Content-Type: application/json, multipart/form-data (uploads), application/x-www-form-urlencoded (HTML forms), text/html. The body parser you need in 3b is chosen by this header.
  • Authorization: Bearer <token> for JWT / API keys. Never cached by shared caches, never sent cross-origin without credentials (CORS below).
  • Cookie / Set-Cookie: sessions. Flags: HttpOnly (no JS access — anti-XSS), Secure (HTTPS only), SameSite=Lax|Strict (CSRF mitigation; Lax is the browser default and still sends the cookie on top-level navigations). 3e builds on these.
  • Accept / Accept-Encoding: what the client can take back. Vary tells caches which request headers changed the response — forget Vary: Origin and a CDN serves one origin's CORS headers to another.
  • Cache-Control: directive cheat-sheet below.

Header names are case-insensitive; Node lowercases them on the way in (req.headers.authorization, req.get("Authorization") both work). Values are strings — req.get("content-length") is "42", not 42.

Cache-Control — the directives that actually matter

DirectiveMeaning
no-storeNever cache. Sensitive data (banking, health). Forces a full round-trip every time.
no-cacheCache it, but always revalidate before serving. Uses an ETag or Last-Modified check. One round-trip, but cheaper than no-store if the resource hasn't changed (304, no body).
max-age=NServe from cache for N seconds without checking. Good for static assets with content hashes in the filename (max-age=31536000, immutable).
s-maxage=NSame as max-age but applies only to shared caches (CDNs). Lets you cache at the edge longer than at the browser.
stale-while-revalidate=NServe stale for up to N seconds while fetching a fresh copy in the background. Fast response + eventual freshness for non-critical data.
privateCDN must not cache; browser may. Mandatory on any user-specific response — without it a CDN with a cache rule can serve one user's data to another.

No header at all is not "no caching": browsers apply heuristic freshness to responses with a Last-Modified. State it explicitly. Default for an authenticated JSON API: no-store or private, no-cache.

HTTP/2 and HTTP/3 — one paragraph each

HTTP/2 uses a single TCP connection and multiplexes many requests/responses over it (no per-request head-of-line blocking; one handshake). Headers are compressed (HPACK). TLS is effectively required. Node supports it natively; in practice the reverse proxy (nginx, Caddy, the load balancer) terminates HTTP/2 and talks HTTP/1.1 to Node. Your Express code does not change.

HTTP/3 swaps TCP for QUIC (UDP-based), eliminating TCP head-of-line blocking entirely and folding the transport and TLS handshakes into one. Critical for mobile clients on lossy networks. Supported by Cloudflare, Fastly, and modern nginx/Caddy builds. Again: negotiated below you; the semantics above (methods, status codes, headers) are identical across all three versions.

HTTP streaming — chunked transfer and SSE

Normal responses buffer the body, set Content-Length, then send. Streaming skips the buffer: data flows as it's produced, using Transfer-Encoding: chunked. Two common patterns (real Node res API — res.write and req.on("close") are stream methods the in-page shim does not model):

// Chunked — arbitrary binary/text stream
app.get("/download", (req, res) => {
  res.setHeader("Content-Type", "text/plain");
  res.write("chunk one\n");
  setTimeout(() => {
    res.write("chunk two\n");
    res.end();           // flushes and closes
  }, 500);
});

// Server-Sent Events (SSE) — browser-native event stream
// Client uses: const es = new EventSource("/events");
app.get("/events", (req, res) => {
  res.setHeader("Content-Type", "text/event-stream");
  res.setHeader("Cache-Control", "no-cache");
  res.setHeader("Connection", "keep-alive");
  res.flushHeaders();   // send the status + headers now, before any event

  const send = (data: object) => res.write(`data: ${JSON.stringify(data)}\n\n`);

  send({ type: "connected" });
  const iv = setInterval(() => send({ type: "heartbeat", ts: Date.now() }), 15_000);
  req.on("close", () => clearInterval(iv));  // clean up when client disconnects
});

SSE is one-directional (server → client), reconnects automatically, and is plain HTTP — it goes through every proxy and CDN that WebSockets don't. Use it for live feeds, progress bars, and AI token streaming. For bidirectional, use WebSockets. Once res.write has run, the status and headers are on the wire: an error mid-stream cannot become a 500 any more, only a truncated body — stream errors must be reported in-band.

CORS in two paragraphs

By default, browsers block cross-origin JS from reading another origin's responses (same-origin policy; the request itself is usually sent). CORS is the server's opt-in: it returns Access-Control-Allow-Origin (and friends) to say which origins may read. For "unsafe" methods (anything but GET/HEAD/POST-with-form-types) or custom headers (Authorization, Content-Type: application/json), the browser first sends a preflight OPTIONS request and expects Access-Control-Allow-Methods / -Headers back; Access-Control-Max-Age says how long to remember the answer. Cookies and Authorization cross origins only with Access-Control-Allow-Credentials: true, and then the allowed origin must be explicit — * is rejected by the browser.

Most CORS pain is configuring the server to return the right headers. Use the cors middleware and configure explicit origins — never * on an authenticated API. CORS protects browsers' users, not your server: curl and other servers send no Origin and ignore the headers entirely.

import cors from "cors";

const ALLOWED_ORIGINS = [
  "https://app.example.com",
  "https://admin.example.com",
  ...(process.env.NODE_ENV === "development" ? ["http://localhost:3000"] : []),
];

app.use(cors({
  origin: (origin, cb) => {
    // allow server-to-server calls (no origin header) and listed origins
    if (!origin || ALLOWED_ORIGINS.includes(origin)) return cb(null, true);
    cb(new Error(`CORS: origin ${origin} not allowed`));
  },
  credentials: true,          // required when client sends cookies/Authorization
  allowedHeaders: ["Content-Type", "Authorization"],
  maxAge: 86_400,             // preflight cached for 24h
}));

Code review
  • 200 with { error } in the body. res.ok is true, caches store it, dashboards stay green. Use the family that matches the failure; the body carries detail, the status carries meaning.
  • 500 for client mistakes. A validation failure returned as 5xx pages on-call and tells clients to retry. 400/422 for bad input, 409 for conflicts, 404 for missing.
  • No Cache-Control on authenticated responses. Heuristic caching and CDN rules fill the gap. Default to no-store or private, no-cache; only public, user-independent responses get s-maxage.
  • Existence checked before authentication. 404-vs-401 enumerates ids. Auth → authz → lookup, or 404 for both.
  • Access-Control-Allow-Origin: * on an API that uses cookies or Authorization. Browsers refuse credentials with *, so someone "fixes" it by reflecting any origin — which is the actual vulnerability. Allowlist, and send Vary: Origin.
  • Non-idempotent POST with client retries. Timeouts duplicate orders and payments. Accept an Idempotency-Key and replay the stored response.
  • SSE behind a buffering proxy. nginx buffers and times out idle connections by default: proxy_buffering off; proxy_read_timeout 3600s; and send heartbeats.

Recall
A CDN sits in front of your API. You want the CDN to cache a public listing for 5 minutes but the browser to revalidate every time. Which Cache-Control header achieves that?

Cache-Control: no-cache, s-maxage=300. s-maxage controls the shared (CDN) cache; no-cache tells browsers to always revalidate.

Your SSE endpoint works locally but disconnects after 60 seconds in production (behind nginx). What nginx directive is almost certainly the cause?

proxy_read_timeout defaults to 60s; idle SSE connections get killed. Set proxy_read_timeout 3600s;, proxy_buffering off; so chunks reach the client immediately, and send heartbeats.

401 or 403: the user is logged in but tries to delete another user's post.

403 Forbidden — identity is known, permission is missing. 401 means "not authenticated"; clients react to it by re-authenticating, which would not help here.

no-cache vs no-store — which one still saves a copy?

no-cache stores the response but revalidates (ETag / Last-Modified → 304) before every reuse. no-store never writes it to any cache. Use no-store for sensitive data.

Which methods are idempotent, and what does that promise to a retrying client?

GET, HEAD, PUT, DELETE (and OPTIONS). Repeating the request leaves the server state unchanged — so timeouts can be retried blindly. POST and PATCH make no such promise; use an Idempotency-Key if they must be retried.

A handler checks "does the row exist → 404" before "is there a token → 401". What is the production problem?

Anonymous clients can enumerate ids: 404 vs 401 reveals which rows exist. Authenticate first, authorise second, look up last — or return 404 for both "missing" and "not yours".

What does the browser send before a cross-origin DELETE with an Authorization header, and which response headers must answer it?

A preflight OPTIONS request. The server answers with Access-Control-Allow-Origin (the specific origin, plus Vary: Origin), Access-Control-Allow-Methods including DELETE, Access-Control-Allow-Headers including Authorization, Access-Control-Allow-Credentials: true, optionally Access-Control-Max-Age — typically a 204 with no body.
