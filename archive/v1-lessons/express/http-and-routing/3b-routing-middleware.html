Express Core — Routing & Middleware

Express is one mechanism: an ordered list of functions, each handed (req, res, next), each choosing to respond, pass on, or fail. Routing, body parsing, auth, error mapping, logging — all of it is that list. Everything in 3c–3g (where code lives, validation, auth, observability) is a question of what goes in the list and in which order. Baseline is Express 5 (npm i express since 2025): async handlers are first-class, which removes a whole category of Express 4 bugs — noted where it matters.

The hello world, then the real structure

import express from "express";
const app = express();

app.use(express.json());                    // parses JSON bodies into req.body

app.get("/users/:id", async (req, res) => {
  const user = await db.users.findById(req.params.id);
  if (!user) return res.status(404).json({ error: "not_found" });
  res.json(user);
});

app.listen(3000);

Four things to see: app.use registers something for every request; app.get(path, handler) registers for one method + path; :id becomes req.params.id (always a string); and the return before res.status(404) is load-bearing — without it the function continues to res.json(user) and Node throws ERR_HTTP_HEADERS_SENT.

Middleware — the signature pattern of Express

Every handler is a middleware: (req, res, next) => void. The app holds them in registration order and walks the list per request, skipping entries whose path/method don't match. Each one has exactly three ways out:

  • Respond — res.json(), res.send(), res.end(), res.redirect(). The chain stops; later middleware never sees this request.
  • next() — continue to the next matching entry. Mutate req (req.user, req.body) or res.locals first if later layers need something.
  • next(err) or throw — skip every ordinary entry and jump to the next error middleware (below).

Do none of the three and the request hangs until the client gives up. That is the first thing to check when an endpoint "never responds".

// Log every request
app.use((req, res, next) => {
  console.log(`${req.method} ${req.url}`);
  next();
});

// Auth on a subtree: app.use(path) is a *prefix* match — /admin, /admin/users, /admin/x/y
app.use("/admin", requireAdmin);

// Several handlers on one route run left to right; each must call next() to reach the next
app.post("/users", validate(CreateUser), requireAuth, createUser);
Order is everything

The list is walked top to bottom as registered. express.json() mounted after the routes parses nothing; a logger after the routes only sees requests nothing answered; cors() after the routers means the preflight OPTIONS hits a 404. Put cross-cutting middleware first, routers next, the 404 and error handlers last.

Route matching: first match wins, params are strings

A route is method + path pattern. Patterns are compared in registration order and the first match handles the request (unless it calls next(), which resumes the walk at the next entry). :name captures one path segment into req.params.name — always a string, so Number(req.params.id) or a schema (3d) before using it. The query string is parsed into req.query (also strings). No route matched → Express's built-in 404.

app.get("/users/me", meHandler);       // must come first…
app.get("/users/:id", userHandler);    // …or :id captures "me"

app.get("/search", (req, res) => {
  const { q = "", page = "1" } = req.query;   // GET /search?q=ada&page=2 → "ada", "2"
  res.json({ q, page: Number(page) });
});

app.all("/legacy/*rest", (req, res) => res.status(410).end());   // Express 5: wildcards are named
Express 5 path syntax

Express 5 upgraded path-to-regexp: a bare * is a syntax error (/files/*path), optional segments are {/:id} not /:id?, and regex characters in string paths are rejected — pass a RegExp instead. Snippets copied from Express 4 tutorials fail at startup, which is at least loud.

Body parsers

app.use(express.json({ limit: "100kb" }));        // Content-Type: application/json (100kb is the default)
app.use(express.urlencoded({ extended: true }));  // Content-Type: application/x-www-form-urlencoded
// extended: true uses the qs library (nested objects); false uses querystring (flat only)

// Webhooks that verify a signature need the raw bytes — on that route only
app.post("/webhooks/stripe", express.raw({ type: "application/json" }), stripeWebhook);

Both are needed if your API accepts HTML form POSTs or OAuth callbacks as well as JSON clients. Each parser checks Content-Type and skips silently when it doesn't match — a client that forgets the header gets req.body === undefined (Express 5; Express 4 gave {}) and a confusing validation error, not a 415. Parsing happens where the parser is mounted: a parser after the routes parses nothing.

Splitting routes into files with express.Router()

// routes/users.routes.ts
import { Router } from "express";
import { requireAuth } from "../middleware/auth";
import * as ctrl from "../controllers/users.controller";

export const usersRouter = Router();

usersRouter.post("/",        validate(CreateUser), ctrl.createUser);
usersRouter.get("/:id",      requireAuth,          ctrl.getUser);
usersRouter.patch("/:id",    requireAuth,          ctrl.updateUser);
usersRouter.delete("/:id",   requireAuth,          ctrl.deleteUser);

// app.ts — mount the router
import { usersRouter } from "./routes/users.routes";
app.use("/users", usersRouter);     // → /users, /users/:id, etc.

A Router is a mini-app: its own ordered list, its own router.use() middleware that only runs for requests that reach it. Mounting strips the prefix — inside usersRouter, req.path is /42 while req.originalUrl is still /users/42 (log the latter). Each resource gets its own file; app.ts becomes a list of app.use() mounts — nothing more. Params from the mount path (app.use("/teams/:teamId", teamRouter)) are only visible inside with Router({ mergeParams: true }).

Error middleware: next(err) and the four-argument rule

Express distinguishes error handlers from everything else by arity: a function declared with four parameters (err, req, res, next) is an error handler; with three it is ordinary middleware. Nothing else marks it — not its name, not where it is registered. When any layer calls next(err) (or throws, or rejects — below), the walk skips every ordinary entry and resumes at the next four-arity one. Register them last: the walk never goes backwards, so an error handler above the route that failed is never reached.

// Error middleware — exactly FOUR parameters, even if next is unused
app.use((err, req, res, _next) => {
  if (res.headersSent) return _next(err);               // response already streaming: let Node close it
  const status = err.status ?? 500;
  if (status >= 500) console.error(err);               // log the real thing…
  res.status(status).json({ error: status >= 500 ? "internal_error" : err.message });  // …never send it
});

An error handler has the same three exits: respond, next(err) to the next error handler, or hang. Without any of yours, Express's default one answers with err.status || 500 and — in development — the stack trace in the body.

Gotcha

app.use((err, req, res) => …) — three parameters because next was "unused" — is silently a normal middleware. It runs on every request with err = req, req = res, res = next, and real errors sail past it to the default handler. Keep the fourth parameter; name it _next for the linter.

Mechanism

Two tracks through one list. Ordinary entries are walked via next(); next(err), a throw, or a rejected async handler (Express 5) jumps over every remaining ordinary entry to the next four-arity one. Nothing matched at all → the built-in 404.

Typed AppError

// errors/AppError.ts
export class AppError extends Error {
  constructor(
    public readonly status: number,
    message: string,
    public readonly code?: string,
  ) {
    super(message);
    this.name = "AppError";
  }
}

// Usage — anywhere in a handler or service; Express 5 routes the rejection to error middleware
throw new AppError(404, "User not found", "USER_NOT_FOUND");
throw new AppError(409, "Email already registered", "EMAIL_CONFLICT");

// Error middleware picks it up
app.use((err: unknown, req: Request, res: Response, _next: NextFunction) => {
  if (err instanceof AppError) {
    return res.status(err.status).json({ error: err.message, code: err.code });
  }
  log.error({ err }, "unhandled error");
  res.status(500).json({ error: "internal_error" });
});

One class, two fields the boundary needs: status to pick the response, code for clients to branch on (never the message — 1g). Anything that is not an AppError is by definition unexpected: log it with the request id, send a generic 500.

Async handlers: Express 5 vs 4

In Express 5 a handler that returns a promise is awaited by the router; a rejection is passed to next(err). throw new AppError(…) inside an async handler, or an await db.query() that rejects, lands in your error middleware with no wrapper. That is the baseline for every snippet in Part 3.

// Express 5 — this is complete
app.get("/x", async (req, res) => {
  res.json(await mightThrow());       // rejection → next(err) → error middleware
});

// Express 4 — the same code was a bug: the rejection reached nobody (unhandledRejection, 1g-11),
// the client hung until timeout. Every codebase grew one of these:
const asyncHandler = (fn) => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);
app.get("/x", asyncHandler(async (req, res) => res.json(await mightThrow())));
// …or `import "express-async-errors"` patched Router.prototype to do the same.

Still not covered in Express 5 — the "nowhere" channel from 1g-23: a throw inside a callback the handler registered (setTimeout, a stream's "data" event, an EventEmitter) runs on an empty stack after the handler has returned. Express never sees it. Wrap such code in a promise you await, or handle inside the callback.

Migrating

On Express 5, asyncHandler wrappers and express-async-errors are dead weight: delete them. Keep the test that proves a rejected handler produces a mapped error response — it is what guarantees the behaviour either way.

Request-ID middleware

// middleware/requestId.ts
import { randomUUID } from "node:crypto";

export function requestId(req: Request, res: Response, next: NextFunction) {
  const id = req.get("x-request-id") ?? randomUUID();   // honour the proxy's id if it sent one
  res.locals.requestId = id;
  res.set("X-Request-Id", id);
  // Attach a child logger so every log line from this request carries the id
  res.locals.log = log.child({ requestId: id });
  next();
}

// app.ts — mount before all routes
app.use(requestId);

res.locals is the per-request scratch space Express gives you: an object that lives exactly as long as this request, visible to every later layer and to the error handler. Put the request id, the child logger and the authenticated user there (or on req — both work; pick one convention). The header must be set before anything responds, which is why this is the first middleware.

Rate limiting

import rateLimit from "express-rate-limit";

// Global limiter — blunt instrument, protects against runaway clients. Mount BEFORE body parsing.
app.use(rateLimit({ windowMs: 60_000, limit: 100 }));

// Tighter on auth endpoints
app.use("/auth", rateLimit({
  windowMs: 15 * 60_000,   // 15 minutes
  limit: 10,
  message: { error: "too_many_requests" },
  standardHeaders: "draft-7",   // RateLimit / RateLimit-Policy headers
  legacyHeaders: false,         // no X-RateLimit-*
}));

The mechanism is a counter per key (client IP by default) per window; over the limit → 429 with Retry-After. Two production details: the key must be the real client IP, which behind a proxy means app.set("trust proxy", 1) so req.ip reads X-Forwarded-For (otherwise every user shares the load balancer's address); and an in-memory store resets on deploy and is per-instance — use the Redis store once you run more than one process.

Code review
  • Error handler with three parameters, or registered before the routes. Both make it unreachable; errors fall through to Express's default handler, which leaks err.message (and the stack in development). Four parameters, mounted last, with a test that a thrown AppError produces the mapped JSON.
  • Missing return before an early res.status(4xx).json(). The function continues to the success branch → ERR_HTTP_HEADERS_SENT in the logs and a half-written response. Also: next() after a response.
  • /users/:id registered above /users/me. First match wins; literal routes before parametric ones.
  • Body parsing mounted before rate limiting, or globally when one route needs raw bytes (webhook signatures). Limiter first, parsers next, express.raw() on the one route that needs it.
  • asyncHandler / express-async-errors on Express 5. Dead weight that hides what the framework does. Remove; keep the test.
  • Rate limiter / IP logging without trust proxy. Behind a load balancer req.ip is the balancer, so one bucket is shared by every user. app.set("trust proxy", 1) — exactly one hop, never true on an internet-facing box.
  • 500 responses that include err.message. Driver errors contain table names, hosts, sometimes query fragments. Generic body, full detail in the log under the request id.

An app mounts, in this order: (1) express.json(), (2) requestId, (3) rateLimit, (4) validate(CreateUser), (5) the handler. During a flood of 5 MB POSTs the process runs out of memory before most requests are rejected. Which change fixes that?

Recall
You mount app.use("/api", authMiddleware, apiRouter). A route inside apiRouter calls next("route") instead of next(). What happens?

next("route") skips the remaining handlers in the current route stack and moves to the next matching route. It does not skip the entire middleware chain — authMiddleware has already run. Use next("route") carefully; in most cases next() or returning a response is clearer.

Express receives POST /users. Middleware order: (1) express.json(), (2) requestId, (3) rateLimit, (4) validate(CreateUser), (5) ctrl.createUser. What is the correct production order, and why does rate limiting move earlier?

Rate limiting first. Parsing the body allocates memory; a flood of large requests can exhaust memory before the limiter fires. Correct order: rate limiting → request id → body parsing → validation → handler.

How does Express tell an error handler apart from ordinary middleware?

By arity only: a function with four parameters (err, req, res, next) is an error handler. Three parameters — even if the first is named err — is ordinary middleware and is skipped while an error is in flight.

What are the three legal ways out of a middleware, and what happens if it does none of them?

Respond (res.json/send/end), next() to continue, or next(err)/throw to jump to the error handlers. Doing none leaves the request hanging until the client times out.

An async route handler rejects. Where does the error go in Express 5, and where did it go in Express 4?

Express 5 awaits the returned promise and passes a rejection to next(err) → your error middleware. Express 4 ignored the promise: an unhandled rejection and a client that hung — hence asyncHandler wrappers and express-async-errors, now unnecessary.

What kind of throw does Express 5 still not catch?

A throw inside a callback registered by the handler — setTimeout, a stream "data" listener, an event emitter. It runs on an empty stack after the handler returned; wrap it in a promise you await or handle inside the callback.

Inside a router mounted with app.use("/users", usersRouter), what are req.path and req.originalUrl for GET /users/42?

req.path is /42 (the mount prefix is stripped); req.originalUrl is /users/42. Log originalUrl.

What does req.body hold on a POST when no body-parsing middleware ran before the route?

undefined in Express 5 (Express 4 gave {}). The parser must be mounted above the route and the request's Content-Type must match the parser.
