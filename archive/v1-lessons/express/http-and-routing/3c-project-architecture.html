Project Architecture — Where Code Lives

Express is unopinionated. It gives you a router; you decide how to structure everything else. The layered architecture below scales well for most teams.

src/
  app.ts                # express app factory
  server.ts             # bootstrap (port, signals, shutdown)
  config/               # env parsing (zod-validated)
  routes/
    users.routes.ts     # thin: routing + middleware wiring
  controllers/
    users.controller.ts # thin: parse req, call service, shape res
  services/
    users.service.ts    # business logic — testable in isolation
  repositories/
    users.repo.ts       # DB access only (Prisma/Drizzle calls)
  middleware/
    auth.ts requireAuth.ts etc.
  lib/                  # pure utilities
  types/                # shared types
  errors/               # custom error classes

app.ts vs server.ts — why the split

// app.ts — exports a factory function, never binds a port
import express from "express";
export function createApp(deps: AppDeps) {
  const app = express();
  app.use(express.json());
  app.use(requestId);
  app.use("/users", makeUsersRouter(deps));
  app.use(errorHandler);
  return app;
}

// server.ts — the entry point; owns the port and shutdown signals
import { createApp } from "./app";
import { db } from "./lib/db";

const app = createApp({ db, mailer: realMailer });
const server = app.listen(process.env.PORT ?? 3000, () =>
  log.info({ port: process.env.PORT ?? 3000 }, "listening"),
);

Why? Tests call createApp() with fake deps — no port conflict, no real DB required. server.ts is never imported by tests. This is the pattern supertest and Vitest assume.

Config parsing at startup

// config/env.ts
import { z } from "zod";

const EnvSchema = z.object({
  NODE_ENV:     z.enum(["development", "test", "production"]).default("development"),
  PORT:         z.coerce.number().default(3000),
  DATABASE_URL: z.string().url(),
  JWT_SECRET:   z.string().min(32),
  LOG_LEVEL:    z.enum(["trace","debug","info","warn","error"]).default("info"),
});

export const env = EnvSchema.parse(process.env);  // throws on startup if invalid

Call this once at startup before anything else imports config. A mis-configured container crashes immediately with a clear error rather than failing silently at request time.

Worked call trace: create a user

// 1. Route (routes/users.routes.ts) — wires middleware + handler
usersRouter.post("/", validate(CreateUser), ctrl.createUser);

// 2. Controller (controllers/users.controller.ts) — req → service → res
export async function createUser(req: Request, res: Response) {
  // req.body is already validated + typed (CreateUserInput) by validate()
  const user = await usersService.register(req.body);
  res.status(201).json(UserResponse.parse(user));  // strip internal fields
}

// 3. Service (services/users.service.ts) — business logic, no req/res
export async function register(input: CreateUserInput) {
  const exists = await usersRepo.findByEmail(input.email);
  if (exists) throw new AppError(409, "Email already registered", "EMAIL_CONFLICT");
  const hash = await bcrypt.hash(input.password, 12);
  const user = await usersRepo.create({ ...input, passwordHash: hash });
  await mailer.sendWelcome(user.email);
  return user;
}

// 4. Repository (repositories/users.repo.ts) — DB access only
export async function create(data: NewUser) {
  return prisma.user.create({ data });
}
export async function findByEmail(email: string) {
  return prisma.user.findUnique({ where: { email } });
}

Notice what never crosses a layer boundary: req/res never enters the service; Prisma types never leak into the controller; the route never calls prisma directly.

The rules that keep it clean

  • Routes don't know about the DB. Controllers don't either. Services do (via repositories).
  • Services are pure(ish). They take data and return data. No req, no res.
  • Repositories are the only place DB details leak. Swap Prisma for Drizzle — only repositories change.

DI without a framework

// Function factories are the simplest DI
export function makeUsersService(repo: UsersRepo, mailer: Mailer) {
  return {
    async register(input: RegisterInput) {
      const user = await repo.create(input);
      await mailer.sendWelcome(user.email);
      return user;
    },
  };
}
// In tests, pass fakes. In prod, pass real implementations.
Flags in review
  • Business logic in a route handler. Move it to a service.
  • DB calls from a controller. Push through the service → repo layers.
  • Cross-service direct DB access. Services should call each other via their public APIs or shared events, not reach into another service's tables.
  • req/res threaded five layers deep. Usually a sign the layer boundaries have crumbled.
