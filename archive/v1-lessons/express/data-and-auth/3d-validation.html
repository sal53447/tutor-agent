Validation & Serialization

TypeScript types vanish at compile time; the JSON a client sends is unknown until something checks it. This lesson puts a schema at the two edges of every handler — parse the request on the way in, serialize the row on the way out — so the code between them works on typed, clean data. 3e (auth) and 3f (databases) assume this boundary exists: req.body in a handler is already validated, and a DB row never reaches res.json unfiltered.

Validate at the boundary: schema → typed data

Never trust client input. The TS compiler doesn't run at runtime; a malicious or buggy client can send anything. Zod (or Valibot, or ArkType) validates at runtime and produces typed, sanitized data. One schema is the single source of truth: z.infer derives the static type from it, so the validator and the type can't drift.

import { z } from "zod";                         // Zod 4
import type { Request, Response, NextFunction } from "express";

const CreateUser = z.object({
  email:    z.email(),                           // Zod 4: top-level formats (z.string().email() is deprecated)
  password: z.string().min(8).max(200),
  age:      z.coerce.number().int().positive().optional(),
});

type CreateUserInput = z.infer<typeof CreateUser>;
// { email: string; password: string; age?: number }

function validate<T extends z.ZodType>(schema: T) {
  return (req: Request, res: Response, next: NextFunction) => {
    const r = schema.safeParse(req.body);
    if (!r.success) return res.status(400).json({ issues: r.error.issues });
    req.body = r.data;                           // typed, coerced, unknown keys stripped
    next();
  };
}

app.post("/users", validate(CreateUser), controllers.createUser);

safeParse returns a discriminated union ({ success: true, data } | { success: false, error }) and never throws — the right shape for a boundary. parse throws a ZodError; use it where a failure is a programming error, not a client error. By default z.object strips keys that aren't in the schema (z.strictObject rejects them, z.looseObject keeps them).

Mechanism

Two schemas bracket the handler: after express.json(), the request schema turns the unknown body into a typed value or a 400 before any business code runs; the response schema decides what leaves, so new DB columns are invisible by default.

Python bridge

Zod is Pydantic for TypeScript. A schema is both the validator and the type, the way a BaseModel subclass is: z.infer<typeof CreateUser> ≈ using the model class as an annotation. CreateUser.parse(x) ≈ CreateUser.model_validate(x) (raises on failure); safeParse has no Pydantic twin — it's the try: … except ValidationError as e: e.errors() block folded into a return value. validate(CreateUser) as middleware is what FastAPI does for you when a parameter is typed as a model (422 instead of 400); a response schema is response_model=. One difference that bites: Pydantic is lax by default ("36" becomes 36), Zod is strict — coercion is opt-in with z.coerce.number(), which is why query strings need it explicitly.

// --- tiny stand-in for zod (leave as is). A check returns { value } or { error }.
const s = {
  string: (o = {}) => (v) =>
    typeof v !== "string" ? { error: "expected string" } :
    o.min && v.length < o.min ? { error: `at least ${o.min} chars` } :
    o.email && !/^\S+@\S+\.\S+$/.test(v) ? { error: "invalid email" } : { value: v },
  number: (o = {}) => (v) => {
    const n = o.coerce ? Number(v) : v;
    return typeof n !== "number" || Number.isNaN(n) ? { error: "expected number" } :
      o.int && !Number.isInteger(n) ? { error: "expected integer" } :
      o.min != null && n < o.min ? { error: `at least ${o.min}` } :
      o.max != null && n > o.max ? { error: `at most ${o.max}` } : { value: n };
  },
  optional: (check, fallback) => (v) => v === undefined ? { value: fallback } : check(v),
  object: (shape) => ({
    safeParse(input = {}) {
      const data = {}, issues = [];
      for (const [key, check] of Object.entries(shape)) {
        const r = check(input[key]);
        if (r.error) issues.push({ path: [key], message: r.error });
        else if (r.value !== undefined) data[key] = r.value;
      }
      return issues.length ? { success: false, issues } : { success: true, data };  // unknown keys are dropped
    },
    parse(input) {
      const r = this.safeParse(input);
      if (!r.success) throw Object.assign(new Error("validation failed"), { issues: r.issues });
      return r.data;
    },
  }),
};

const CreateUser = s.object({
  email:    s.string({ email: true }),
  password: s.string({ min: 8 }),
  age:      s.optional(s.number({ int: true, coerce: true })),
});

function validate(schema) {
  return (req, res, next) => {
    const r = schema.safeParse(req.body);
    if (!r.success) return res.status(400).json({ issues: r.issues });
    req.body = r.data;                  // validated, coerced, unknown keys dropped
    next();
  };
}

const app = express();
app.use(express.json());
// (in-page shim: one function per app.post call — real Express takes them as extra arguments)

const app = express();

function requireFields(...fields) {

Validating params and query strings

Everything in req.params and req.query arrives as a string. A schema with z.coerce is where "20" becomes 20 and "abc" becomes a 400 — not somewhere deep in a repository call.

// req.params — usually a numeric or UUID id
const UserIdParam = z.object({ id: z.uuid() });

// req.query — coerce explicitly; apply defaults here, not in the handler
const ListUsersQuery = z.object({
  page:   z.coerce.number().int().positive().default(1),
  limit:  z.coerce.number().int().min(1).max(100).default(20),
  search: z.string().max(100).optional(),
});

type Source = "body" | "params" | "query";

function validateSource<T extends z.ZodType>(schema: T, source: Source) {
  return (req: Request, res: Response, next: NextFunction) => {
    const r = schema.safeParse(req[source]);
    if (!r.success) return res.status(400).json({ issues: r.error.issues });
    res.locals[source] = r.data;                 // see the Express 5 note below
    next();
  };
}

usersRouter.get("/:id", validateSource(UserIdParam, "params"), requireAuth, ctrl.getUser);
usersRouter.get("/",    validateSource(ListUsersQuery, "query"), ctrl.listUsers);

// in ctrl.listUsers:
const { page, limit } = res.locals.query as z.infer<typeof ListUsersQuery>;
Express 5: req.query is a getter

In Express 5 req.query is re-parsed from the URL on every access and can't be assigned to — req.query = r.data is silently ignored or throws, depending on strict mode. Put parsed values on res.locals (or a req.validated property you declare via module augmentation). req.body is a plain property and can be replaced.

Response serialization — never return raw DB rows

// DB model has: id, email, passwordHash, createdAt, deletedAt, stripeCustomerId, ...
// Expose only a safe subset to the client.

const UserResponse = CreateUser.pick({ email: true }).extend({
  id:        z.uuid(),
  createdAt: z.iso.datetime(),                   // Zod 4: z.iso.datetime(), z.iso.date()
});
type UserResponse = z.infer<typeof UserResponse>;

// In the controller:
res.json(UserResponse.parse(user));              // strips any field not in the schema
// If the DB row ever gains a new sensitive column, it's excluded automatically.

parse here, not safeParse: a row that fails its own response schema is a server bug (a migration renamed a column, a nullable field you declared required) and should surface as a 500 in your error handler, not be quietly dropped. The strip-by-default behaviour is the whole point — a manual { id: user.id, email: user.email } is correct today and leaks the next time someone spreads ...user into it.

Bundle size

Zod 4 ships zod/mini (tree-shakeable, function-style API) for edge functions and client bundles; Valibot is the other size-conscious option. Same concepts — schema, inference, parse vs safeParse — different surface. On a Node server the size doesn't matter; pick by ergonomics.

Code review
  • req.body.foo read without a validator. Reject. Any handler that reads req.body, req.query or req.params directly is a boundary with no guard; @typescript-eslint/no-unsafe-member-access flags the any it produces.
  • any (or a hand-written interface) as the handler's input type. Validate, then z.infer the type from the schema. Two sources of truth drift the first time a field is added.
  • Validation scattered across routes. Schemas live in one module per resource (schemas/user.ts) and are reused by the request validator, the response serializer and the tests.
  • Raw DB rows in res.json. password_hash, soft-delete flags, billing ids. A response schema with pick/extend is the allow-list; parse strips the rest.
  • req.query.limit passed as a string to take(). Prisma rejects it (PrismaClientValidationError → 500), pg may silently cast. z.coerce.number() at the boundary, with max, or a client asks for a million rows.
  • schema.parse inside the handler with no ZodError mapping. A bad client body becomes a 500 and pages someone. Use safeParse in middleware, or map ZodError → 400 in the error handler.
  • req.params.id used unvalidated in a query. z.uuid() / z.coerce.number().int() at the boundary; a 400 for "../../etc/passwd" is cheaper than finding out what the ORM does with it.
Check

A controller ends with res.json(UserResponse.parse(row)). A migration adds a stripeCustomerId column to the users table and nobody touches the controller. What happens on the next request?

Recall
A colleague writes type CreateUserInput = { email: string; password: string } in a separate file and imports it in the controller. You have a Zod CreateUser schema. What's the problem?

Two sources of truth. If the schema changes (e.g., adds a required role field), the type won't update automatically. Use type CreateUserInput = z.infer<typeof CreateUser> — one source.

UserResponse.parse(user) is in the controller. A DB column named internalScore gets added to the model. Is it safe to send without changing the controller?

Yes — parse() strips any field not declared in the schema. The new column is silently excluded. This is the key advantage over spread/manual deletion.

safeParse vs parse — which goes at the request boundary, which at the response boundary, and why?
safeParse for requests: a bad body is a client error → 400, no throw. parse for responses: a row that fails its own schema is a server bug → let it throw into the error handler as a 500.
Why does ListUsersQuery need z.coerce.number() when CreateUser doesn't?
Query strings and params are always strings; Zod is strict by default (unlike Pydantic's lax mode), so "20" fails z.number() without coerce. A JSON body already carries real numbers.
In Express 5, why does req.query = parsed in a validator not work, and what do you do instead?
req.query is a getter re-parsed from the URL; assignment is ignored or throws. Store the parsed object on res.locals.query (or a declared req.validated).
A body parser, then requireFields("email", "password"), then a handler that increments handlerRuns. Requests: { email } only; a valid JSON string with an extra role; the string "{not json". Statuses and final handlerRuns?
400 (missing field, handler skipped), 201 (parsed, valid), 400 (parser forwards a 400 error — validator never runs). handlerRuns is 1.
What are the three z.object behaviours for undeclared keys, and which is the default?
Strip (default, z.object), reject (z.strictObject), keep (z.looseObject). The default is what makes a response schema an allow-list.
