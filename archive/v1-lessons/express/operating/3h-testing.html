Testing — Unit, Integration, Supertest

The layered architecture from 3c exists for this lesson: each layer gets the cheapest test that can catch its bugs, and the createApp(deps) seam is what lets a route test run the whole stack in-process with a fake database. Runner: Vitest — ESM-native, Jest-compatible API (describe / it / expect / vi), so migration from Jest is mechanical. Stay on Jest only if the project already is. 4m applies the same ideas to React.

Layers = testing strategy

  • Services — pure logic. Unit test with a fake repository; cover every branch. Milliseconds each, hundreds of them.
  • Repositories — the SQL. Integration test against a real Postgres (testcontainers or a local instance). Don't mock the driver: a mocked prisma.user.findUnique proves the mock was called, not that the query works.
  • Routes — the wiring: middleware order, validation, status codes, serialization. Integration test with supertest: build the app in-process, send requests, assert on responses. No port, no network.
  • End-to-end — a handful of flows through the deployed stack (Playwright against a staging URL). Slow and flaky by nature; keep to the money paths.
import request from "supertest";
import { createApp } from "../src/app";

test("POST /users creates a user", async () => {
  const app = createApp({ db: testDb, mailer: fakeMailer });   // fresh app per test
  const res = await request(app)
    .post("/users")
    .send({ email: "a@b.c", password: "hunter22!" });
  expect(res.status).toBe(201);
  expect(res.body.id).toBeDefined();
  expect(fakeMailer.sent).toHaveLength(1);
});

supertest takes the Express app object directly — it binds an ephemeral port internally — so nothing is listening, nothing is shared between test files, and Vitest can run files in parallel workers.

Mechanism

Each layer down is cheaper and more precise; a bug caught at the bottom never needs the slow layer above to find it. Repositories are the exception: their only bug class is SQL, and only a real database can catch it.

The seam: createApp(deps) and test doubles

A test can only replace what is injected. createApp({ db, mailer, clock }) from 3c takes every side-effecting dependency as a parameter, so a route test passes an in-memory repository and a recording mailer, and asserts on them afterwards. Module-level singletons (export const prisma = new PrismaClient() imported directly by the service) are the thing that makes a codebase untestable: the only way to replace them is vi.mock, which patches the module graph and makes tests order-sensitive.

// src/app.ts
export function createApp({ users, mailer }: Deps) {
  const app = express();
  app.use(express.json());
  app.post("/users", async (req, res) => {
    const user = await users.create(req.body);
    await mailer.send(user.email, "Welcome");
    res.status(201).json({ id: user.id });
  });
  return app;
}

// test/doubles.ts — hand-written fakes beat vi.fn() when the contract is more than one call
export function memoryUsers(seed: User[] = []) {
  const rows = [...seed];
  return {
    async create(data: NewUser) { const u = { id: rows.length + 1, ...data }; rows.push(u); return u; },
    async findById(id: number) { return rows.find(u => u.id === id) ?? null; },
    rows,
  };
}
export function recordingMailer() {
  const sent: { to: string; subject: string }[] = [];
  return { sent, async send(to: string, subject: string) { sent.push({ to, subject }); } };
}
vi.mock is hoisted

vi.mock("../src/db", () => …) runs before every import in the file, regardless of where it is written — so a factory that references a const declared above it throws ReferenceError. Use vi.hoisted(() => …) for values the factory needs, or avoid module mocking entirely by injecting. Reserve vi.mock for third-party modules you don't own (stripe, @aws-sdk/*).

Python bridge

supertest ≈ Starlette/FastAPI TestClient(app) or httpx.AsyncClient(transport=ASGITransport(app)): an in-process client through the real middleware stack. Vitest's beforeEach + a factory function ≈ a pytest fixture — but there is no dependency-injected fixture graph; you call memoryUsers() yourself in each test or in beforeEach. vi.spyOn(obj, "method") ≈ monkeypatch.setattr; vi.mock("module") ≈ unittest.mock.patch("pkg.module") with the same hoisting surprise as patching at import time. conftest.py ≈ setupFiles in vitest.config.ts. The transaction-rollback test DB ≈ pytest-django's db fixture / SQLAlchemy's nested-transaction session fixture.

function createApp({ users, mailer }) {
  const app = express();
  app.use(express.json());
  app.post("/users", async (req, res) => {
    if (!req.body?.email) return res.status(400).json({ error: "email required" });
    const user = await users.create(req.body);
    await mailer.send(user.email, "Welcome");
    res.status(201).json({ id: user.id });
  });
  app.get("/users/:id", async (req, res) => {
    const user = await users.findById(Number(req.params.id));
    user ? res.json(user) : res.status(404).json({ error: "not found" });
  });
  return app;
}

function memoryUsers(seed = []) {
  const rows = [...seed];
  return {
    rows,
    async create(data) { const u = { id: rows.length + 1, ...data }; rows.push(u); return u; },
    async findById(id) { return rows.find(u => u.id === id) ?? null; },
  };
}
const recordingMailer = () => { const sent = []; return { sent, async send(to, subject) { sent.push({ to, subject }); } }; };

// test 1 — fresh deps
{
  const users = memoryUsers(), mailer = recordingMailer();
  const app = createApp({ users, mailer });
  const res = await request(app, { method: "POST", path: "/users", body: { email: "a@b.c" } });
  assert.equal(res.status, 201);
  assert.equal(res.body, { id: 1 });
  assert.equal(mailer.sent, [{ to: "a@b.c", subject: "Welcome" }]);
  console.log("✓ POST /users creates and mails");
}
// test 2 — fresh deps again, so ids start at 1 regardless of test order
{
  const users = memoryUsers([{ id: 1, email: "seed@x.y" }]), mailer = recordingMailer();
  const app = createApp({ users, mailer });
  const res = await request(app, { path: "/users/1" });
  assert.equal(res.status, 200);
  assert.equal(res.body.email, "seed@x.y");
  assert.equal((await request(app, { path: "/users/9" })).status, 404);
  console.log("✓ GET /users/:id finds seeded user, 404 otherwise");
}

Testing auth-protected routes

// Helper — mint a real JWT the same way the app does
import { signToken } from "../src/middleware/auth";

async function authHeader(userId = "test-user-id", role = "user") {
  const token = await signToken({ sub: userId, role });
  return { Authorization: `Bearer ${token}` };
}

test("GET /users/:id requires auth", async () => {
  const app = createApp({ db: testDb });
  const res = await request(app).get("/users/some-id");
  expect(res.status).toBe(401);
});

test("GET /users/:id returns user when authenticated", async () => {
  const app = createApp({ db: testDb });
  await testDb.user.create({ data: { id: "some-id", email: "a@b.c", passwordHash: "x" } });
  const res = await request(app)
    .get("/users/some-id")
    .set(await authHeader("some-id", "user"));
  expect(res.status).toBe(200);
  expect(res.body.email).toBe("a@b.c");
  expect(res.body.passwordHash).toBeUndefined();  // confirm serialization strip
});

// Session-based auth: an agent persists cookies across requests
test("GET /profile with session cookie", async () => {
  const agent = request.agent(createApp({ db: testDb }));
  await agent.post("/auth/login").send({ email: "a@b.c", password: "hunter22!" });
  const res = await agent.get("/profile");
  expect(res.status).toBe(200);
});

Mint tokens with the app's own signToken, never a pasted string: when the secret, algorithm or claims change, a hard-coded token fails for the wrong reason. The passwordHash assertion is the one that earns its keep — serialization leaks are invisible in unit tests and obvious in a route test.

Test-DB strategies
  • Transaction per test, rolled back. Fastest. Breaks for code that commits internally or opens a second connection.
  • Truncate tables between tests. Simple, works with commits. Serialize the test files that touch the DB (fileParallelism: false or one schema per worker).
  • Fresh container per suite (testcontainers). Full isolation, slowest start; the right choice for repository tests in CI.
Code review
  • Mocking the repository in a repository test. vi.mock("@prisma/client") proves the mock was called; a renamed column or a wrong where passes green. Repository tests hit a real database.
  • Shared app or store across tests. A module-level const app = createApp(…) makes tests order-dependent and breaks under Vitest's parallel workers. Factory per test, or beforeEach.
  • Un-awaited supertest calls. Assertions run against a Promise and pass or fail for unrelated reasons. @typescript-eslint/no-floating-promises, and expect.assertions(n) in tests that assert inside callbacks.
  • Hard-coded tokens and timestamps. Tests that expire or break when the secret rotates. Mint with the app's signToken; inject a clock and use vi.useFakeTimers.
  • Mock drift. A service test's fake still matches the old repository signature. Type the fakes (satisfies UserRepo) so renames fail to compile.
  • Coverage as the goal. 80 % lines with assertions-free tests is worse than 60 % with real ones. Reviewers read the assertions, not the number.
  • jsdom for a backend. Unhandled rejections that crash Node pass silently in a browser-like environment (1f). environment: "node" for Express projects.
Check

A PR adds repository tests that vi.mock("@prisma/client") and assert prisma.user.findUnique was called with { where: { email } }. All green. A week later a migration renames the column to email_address and the Prisma schema is updated. What do these tests do?

Recall
1. A service test mocks the repository and the test passes. Later, the real repository method is renamed but the mock still uses the old name. What's the failure mode?

The test continues passing against the mock while production fails at runtime — the classic mock/reality divergence. Remedies: (a) repository integration tests that verify the real method signature; (b) TypeScript typed mocks (vi.mocked(), satisfies UserRepo) that fail to compile if the mock no longer matches the type.

2. Why does the auth-route test use signToken() (the real app function) rather than a hard-coded token string?

If the signing algorithm, secret, or claims change, a hard-coded token becomes stale and the test fails for the wrong reason (bad fixture, not a real regression). Using signToken() means the test always produces a token that matches whatever the current verification logic expects.

Which layer of an Express app should be tested against a real database, and why not with a mock?
Repositories. Their only bug class is SQL/schema drift; a mocked client proves the call happened, not that the query is right.
What does supertest do with the app object you pass it?
Binds an ephemeral port internally and sends real HTTP through the full middleware stack, in-process — no listen, no shared server between test files.
Why is createApp(deps) the seam that makes route tests possible?
A test can only replace what is injected. With dependencies as parameters each test passes its own fakes; with module-level singletons the only option is vi.mock, which patches the module graph and makes tests order-sensitive.

What surprises people about vi.mock, and what is the escape hatch?
It is hoisted above all imports, so its factory can't reference variables declared later in the file. vi.hoisted() for values it needs — or inject the dependency instead of mocking the module.
Name the three test-database strategies and the trade-off of the fastest one.
Transaction-per-test rollback (fastest; breaks when code commits or uses a second connection), truncate between tests (works with commits; serialize DB test files), fresh container per suite (full isolation; slowest start).
Why environment: "node" rather than jsdom for an Express project's Vitest config?
Unhandled promise rejections crash Node but only log in a browser-like environment, so jsdom hides a class of production crashes.
