Observability — Logs, Metrics, Traces

A service you can't see into is a service you debug by redeploying. Three signals cover it: logs (what happened, one JSON event per line), metrics (how often / how slow, aggregated), traces (one request's path across services). All three hang off the same thread: a request id minted at the edge and carried into every log line, span and downstream call. 3h tests the logger as a dependency; 3i's health probes and graceful shutdown assume the structure built here.

Structured logging with pino

import pino from "pino";
const log = pino({ level: process.env.LOG_LEVEL ?? "info" });

log.info({ userId, orderId }, "order created");
log.error({ err }, "failed to charge card");
// {"level":30,"time":1712345678901,"pid":4242,"userId":"u1","orderId":"o9","msg":"order created"}

Fields first, message second — the fields are what you query on. One JSON object per line, ingested as-is by Datadog, Grafana Loki, CloudWatch. level is numeric (30 = info, 40 = warn, 50 = error); anything below the configured level is a no-op, so a log.debug in a hot path costs one comparison in production.

A child logger carries bound fields into every line written through it. That is how a request id reaches a log call four functions deep without being threaded as a parameter:

const reqLog = log.child({ requestId: req.id });
reqLog.info("lookup");                        // {"requestId":"…","msg":"lookup"}
reqLog.child({ table: "orders" }).warn("slow"); // {"requestId":"…","table":"orders","msg":"slow"}
Errors need a serializer

JSON.stringify(err) is {} — message and stack are non-enumerable (1g). pino's err key runs an error serializer that emits type, message, stack; log under any other key and you get an empty object. console.log in server code has none of this: no level, no structure, no correlation, and it writes synchronously to stdout.

Python bridge

pino ≈ structlog, or stdlib logging with a JSON formatter. log.child({ requestId }) ≈ logger.bind(request_id=…): both return a new logger that carries the fields. The difference is in how context travels. Python gets the request id into deep calls with contextvars (structlog's contextvars.bind_contextvars); Node's equivalent is AsyncLocalStorage from node:async_hooks — a store that follows the async call chain across awaits, which pino-http and OpenTelemetry both use under the hood. logging.getLogger(__name__)'s module hierarchy has no pino counterpart; use a bound module field instead.

Try it

A 15-line structured logger with the shape pino has: levels, a sink, children that inherit bound fields. Try: set level: "warn" and see info lines disappear; bind a child of a child; log an Error under err and see what survives JSON.stringify with and without the serializer.

const LEVELS = { debug: 20, info: 30, warn: 40, error: 50 };

function createLogger(sink, { level = "info", base = {} } = {}) {
  const write = (lvl) => (fields, msg) => {
    if (LEVELS[lvl] < LEVELS[level]) return;
    if (typeof fields === "string") { msg = fields; fields = {}; }
    if (fields.err instanceof Error) fields = { ...fields, err: { type: fields.err.name, message: fields.err.message } };
    sink.push({ level: LEVELS[lvl], ...base, ...fields, msg });
  };
  return {
    debug: write("debug"), info: write("info"), warn: write("warn"), error: write("error"),
    child: (bindings) => createLogger(sink, { level, base: { ...base, ...bindings } }),
  };
}

const lines = [];
const log = createLogger(lines, { level: "info", base: { service: "orders" } });
log.debug("not emitted");
log.info({ orderId: "o9" }, "order created");

const reqLog = log.child({ requestId: "req-1" });
reqLog.warn({ ms: 812 }, "slow query");
reqLog.error({ err: new Error("card declined") }, "charge failed");

for (const l of lines) console.log(JSON.stringify(l));
{"level":30,"service":"orders","orderId":"o9","msg":"order created"} {"level":40,"service":"orders","requestId":"req-1","ms":812,"msg":"slow query"} {"level":50,"service":"orders","requestId":"req-1","err":{"type":"Error","message":"card declined"},"msg":"charge failed"}

Request IDs and correlation

Mint one id per request at the first middleware, reuse an incoming X-Request-Id if a trusted proxy already set one, echo it on the response so the client can quote it, and bind it to a child logger. Every line that request writes — handler, service, repository — now shares one field, and one grep gives the whole trail.

import { randomUUID } from "node:crypto";

export function requestId(req: Request, res: Response, next: NextFunction) {
  req.id = req.get("x-request-id") ?? randomUUID();
  res.set("x-request-id", req.id);
  req.log = log.child({ requestId: req.id });   // everything downstream uses req.log
  next();
}
app.use(requestId);                             // first — before pino-http, routes, everything

Propagate it outward too: set x-request-id on every outbound fetch to a sibling service, and pass it as a comment or app-name on the DB connection if the driver supports it. That is the manual version of what a tracer does automatically with a traceparent header.

Trust

Honouring the incoming header means any client can choose its own id. Harmless for correlation (ids only need to be unique-ish), but validate the shape (/^[\w-]{8,64}$/) before logging it — log injection via a header that contains newlines is the classic attack on plain-text log pipelines.

pino-http — automatic request logging

import pinoHttp from "pino-http";

// Mount after requestId and before routes, so every request gets one completion line
app.use(pinoHttp({
  logger: log,
  genReqId: (req) => req.id,                     // reuse the id requestId minted
  customLogLevel: (req, res, err) => {
    if (err || res.statusCode >= 500) return "error";
    if (res.statusCode >= 400) return "warn";
    return "info";
  },
  redact: ["req.headers.authorization", "req.headers.cookie", "req.body.password"],
}));
// Each response logs: req { id, method, url }, res { statusCode }, responseTime, msg: "request completed"

It also sets req.log to a child bound with the id, so handlers write req.log.info(…) and the correlation is free. The completion line is written on the response's finish event — the only moment at which status and duration are both known.

Don't
app.use((req, res, next) => {
  log.info({ url: req.url, status: res.statusCode, headers: req.headers }, "request");
  next();
});

Logged before the handler ran: status is always 200, duration is unknowable, and headers ships the bearer token to the log store.

Do
app.use((req, res, next) => {
  const start = performance.now();
  res.on("finish", () => req.log.info({ method: req.method, url: req.url, status: res.statusCode, ms: Math.round(performance.now() - start) }, "request completed"));
  next();
});

Health and readiness endpoints

// /healthz — liveness: is the process alive and not deadlocked?
// Kubernetes kills and restarts the pod if this fails.
app.get("/healthz", (req, res) => res.json({ ok: true }));

// /readyz — readiness: can this instance accept traffic right now?
// Kubernetes stops routing to the pod while this returns non-200; the pod stays up.
app.get("/readyz", async (req, res) => {
  try {
    await prisma.$queryRaw`SELECT 1`;           // check DB
    await redisClient.ping();                    // check cache
    res.json({ ok: true });
  } catch (err) {
    res.status(503).json({ ok: false, error: String(err) });
  }
});

Keep /healthz trivial — it must never fail because a dependency is down, because the remedy for a failed liveness probe is a restart, and restarting the app does nothing for a dead database. /readyz is where dependencies are checked; a failing readiness probe takes the instance out of the load balancer until the dependency recovers. Both are exempt from auth and from request logging (they fire every few seconds and would drown the log).

Metrics and tracing

  • Metrics — counters, gauges, histograms, pre-aggregated and cheap to keep forever. prom-client exposes /metrics for Prometheus; managed stacks (Datadog, New Relic) scrape or push. The default dashboard is RED: request Rate, Error rate, Duration histogram per route.
  • Tracing — OpenTelemetry. Each request is a trace; each unit of work (handler, DB query, outbound call) is a span with a parent. The traceparent header carries trace id + parent span id across services, the same way x-request-id carries the request id — and the trace id belongs in every log line too, so a slow span links to its logs.
  • Error tracking — Sentry. Captures exceptions with source maps, breadcrumbs and the request context; groups by stack fingerprint.
import { Counter, Histogram, register } from "prom-client";
const httpDuration = new Histogram({ name: "http_request_duration_seconds", help: "…", labelNames: ["method", "route", "status"] });

app.use((req, res, next) => {
  const end = httpDuration.startTimer();
  res.on("finish", () => end({ method: req.method, route: req.route?.path ?? "unmatched", status: res.statusCode }));
  next();
});
app.get("/metrics", async (req, res) => res.type(register.contentType).send(await register.metrics()));
Label cardinality

Label the metric with the route pattern (/users/:id), never the URL (/users/42). Every distinct label set is a separate time series; a user-id label on a histogram with 12 buckets is a memory leak in Prometheus.

Mechanism

Logs answer "what happened to this request", metrics answer "how is the fleet doing", traces answer "where did the time go" — and one id, carried in the log lines and the spans, links the three stores.

Code review
  • console.log in server code. No level, no fields, no request id, synchronous stdout. ESLint no-console with pino as the only logger import.
  • Request-id middleware not first. Anything mounted before it logs without correlation; pino-http needs it before. Reviewers read the app.use order top to bottom.
  • Completion line logged before finish. Status is always 200, duration missing. Use pino-http or res.on("finish").
  • Secrets in logs. req.headers, req.body spread into a log call. Configure pino redact for authorization, cookie, password, token; log named fields, not whole objects.
  • Errors logged under the wrong key. log.error({ error: err }) serializes to {}. The key is err, and the serializer must walk cause (1g).
  • Dependency checks in /healthz. A DB outage becomes a fleet-wide restart loop. Liveness is trivial; dependencies go in /readyz.
  • High-cardinality metric labels. URL, user id or email as a label = unbounded time series. Label by route pattern and status class.

A team puts the SELECT 1 database check into /healthz (the Kubernetes liveness probe) instead of /readyz. The database becomes unreachable for two minutes. What happens to the API pods?

Recall
In a pino call, what is the argument order and why?
log.info({ fields }, "msg") — the object first because fields are what the log store indexes and queries; the message is for humans.
What does log.child({ requestId }) give you, and what problem does it solve?
A new logger that adds requestId to every line written through it. Deep code (repositories, services) can log with correlation without the id being threaded as a parameter.
Why does log.error({ error: err }, "failed") lose the message and stack?
message, stack and cause are non-enumerable, so JSON.stringify(err) is {}. pino's error serializer runs only on the err key.
Where must the request-id middleware be mounted, and what does it do with an incoming X-Request-Id?
First, via app.use before pino-http and routes. It reuses a (validated) incoming id, otherwise mints a UUID; it sets the id on the response header and binds req.log = log.child({ requestId }).

When should a request-completion log line be written, and what Express event gives you that moment?
After the response is flushed — res.on("finish", …). Only then are statusCode and duration known; logging on the way in records 200 for every request.
Liveness vs readiness: which one checks the database, and what is the consequence of getting it backwards?
Readiness (/readyz) checks dependencies and only pulls the pod from the load balancer. Liveness (/healthz) must be trivial — a dependency check there turns a DB outage into a fleet-wide restart loop.
Logs, metrics, traces — one phrase each for the question they answer.
Logs: what happened to this request. Metrics: how is the fleet doing (rate, errors, duration). Traces: where did the time go across spans and services. A shared request/trace id links them.
Why label a Prometheus histogram with /users/:id and not /users/42?
Every distinct label set is its own time series; unbounded labels (URL, user id) grow memory without bound. Label by route pattern and status.
