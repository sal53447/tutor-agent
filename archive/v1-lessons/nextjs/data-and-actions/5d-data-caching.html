Data Fetching & Caching

Most "Next.js is behaving strangely" bugs are one of four caches doing exactly what it was told. Next 15 made every one of them opt-in — a bare fetch no longer lands in the Data Cache — but a static route is still prerendered once at build, so "not cached" and "fresh per request" are different claims. This lesson is the model behind those claims; 5e (Server Actions) assumes you know what revalidateTag purges, and 5i (production architecture) assumes you can say which cache a stale page came from.

Next 14 vs Next 15 — breaking default

In Next 14, fetch() defaulted to cached indefinitely (force-cache), and GET route handlers were cached too. In Next 15 both flipped to uncached. Tutorials that say "fetch is cached by default" describe Next 14.

The four caches — what they actually are

  1. Request memoization — per-render, in-memory dedupe of identical fetch calls (same URL and options, GET) inside one React render pass. Two components fetching /api/user → one HTTP request. Gone when the render finishes. React, not Next, does this; for non-fetch work use React cache() (5d-17).
  2. Data Cache — cross-request, persistent on the server (filesystem, or a cache handler such as Redis). Shared across all users. Survives deploys on Vercel. Written only by fetch with force-cache / revalidate, by unstable_cache, and by "use cache". This is what revalidateTag purges.
  3. Full Route Cache — the rendered HTML + RSC payload of a static route, produced at build (or on first request with ISR). A route is static unless it uses a dynamic API (cookies(), headers(), searchParams, connection()), a cache: "no-store" fetch, or export const dynamic = "force-dynamic".
  4. Router Cache — client-side, in-memory store of RSC payloads for routes the user visited or that were prefetched. In Next 15 dynamic pages have a staleTimes.dynamic of 0 (was 30 s in 14); static pages and loading boundaries stay for 5 minutes. router.refresh() and a revalidatePath in a Server Action clear it.

Layered top to bottom, the question at each layer is what decides whether the request goes further down:

Mechanism

Every layer answers "no" by default in Next 15 except the top two, which are structural: a route with no dynamic API is prerendered whether or not its fetches are cached.

Python bridge

Django's cache.get_or_set("products", load, timeout=60) is the Data Cache with revalidate: 60 — one shared, cross-request store keyed by you. @cache_page(60) is the Full Route Cache: the whole response, keyed by URL. Request memoization is an lru_cache whose lifetime is one request — Django has no built-in for it; people reach for request-scoped attributes or django-cacheops. The Router Cache has no server-side analogue at all: it is the browser remembering RSC payloads, which is why a stale page can appear with the server never having been asked. One difference matters in review: Django's timeout expires the entry (next reader blocks on load); Next's revalidate is stale-while-revalidate (next reader gets the old value, refresh happens behind them).

fetch in Next 15: opt-in, per call

Next patches the global fetch on the server to read two extra options. Nothing is written to the Data Cache unless you say so:

// Default — not stored in the Data Cache. In a static route this still runs
// ONCE, at build; only in a dynamic route does it run per request.
const res = await fetch("https://api.example.com/products");

// Explicit no-store: per request, and the route becomes dynamic.
const res = await fetch(url, { cache: "no-store" });

// Data Cache, forever (the Next 14 default) — until revalidateTag/Path.
const res = await fetch(url, { cache: "force-cache" });

// Data Cache, time-based: after 60 s the next hit is served stale and
// triggers a background refresh (stale-while-revalidate).
const res = await fetch(url, { next: { revalidate: 60 } });

// Data Cache, tagged: purged on demand by revalidateTag("products").
// A tag on an uncached fetch labels nothing — pair it with force-cache or revalidate.
const res = await fetch(url, { cache: "force-cache", next: { tags: ["products"] } });

Route-level knobs exist too, exported from a page.tsx / layout.tsx / route.ts: export const revalidate = 60 (applies to every fetch in the segment that doesn't set its own, and to the Full Route Cache), export const dynamic = "force-dynamic" (render per request), export const fetchCache = "force-cache" (restore Next 14 behaviour for a segment). The lowest revalidate among a route's fetches is the route's revalidation period.

Gotcha — "uncached" is not "fresh"

fetch(url) with no options in a page that reads no cookies, headers or search params runs at next build and never again. The data is baked into the Full Route Cache until the next deploy or a revalidatePath. If you wanted per-request data, say cache: "no-store" (or read a dynamic API, or force-dynamic). Dev mode hides this — next dev renders every request.

Step through
Try it

The two server-side layers as 20 lines of plain JS — no Next here, only the rules. render is one React render pass with its own memo; dataCache outlives renders. Try: give /api/user a revalidate; set clock.now = 30 before render 3; delete the memo check and watch render 1 double.

let upstream = 0;
const dataCache = new Map();            // cross-request, shared by every render
const clock = { now: 0 };               // seconds

function fetchData(url, { revalidate } = {}) {
  if (revalidate === undefined) { upstream++; return "uncached"; }   // Next 15 default
  const hit = dataCache.get(url);
  if (hit && clock.now - hit.at < revalidate) return "HIT";
  upstream++;
  dataCache.set(url, { at: clock.now });
  return hit ? "STALE → refreshed" : "MISS";
}

function render(label, components) {
  const memo = new Map();               // request memoization: one per render pass
  for (const [url, opts] of components) {
    if (!memo.has(url)) memo.set(url, fetchData(url, opts));
  }
  console.log(label, [...memo.values()].join(", "), "| upstream:", upstream);
}

render("render 1:", [["/api/user"], ["/api/user"], ["/api/products", { revalidate: 60 }]]);
render("render 2:", [["/api/user"], ["/api/products", { revalidate: 60 }]]);
clock.now = 120;
render("render 3:", [["/api/products", { revalidate: 60 }]]);
render 1: uncached, MISS | upstream: 2 render 2: uncached, HIT | upstream: 3 render 3: STALE → refreshed | upstream: 4

Cache invalidation — revalidateTag and revalidatePath

Time-based revalidation bounds staleness; on-demand revalidation ends it. Both calls work from Server Actions and route handlers (never during render), and both mark entries so that the next request re-fetches — unlike the time-based path, that request blocks on the origin; nothing stale is served.

import { revalidateTag, revalidatePath } from "next/cache";

// Every Data Cache entry tagged "products" — across all routes that used it
revalidateTag("products");

// Every entry of one route: its Data Cache fetches, its Full Route Cache entry,
// and (when called from a Server Action) the caller's Router Cache
revalidatePath("/products");
revalidatePath("/products/[slug]", "page");   // every product page, on next visit
revalidatePath("/", "layout");                // everything under the root layout

Tags are a many-to-many index: one fetch can carry several tags, one tag can cover many fetches. revalidateTag("product-42") after editing product 42 touches exactly the entries that carried that tag — the catalog page, the detail page, the cart badge — and nothing else.

Rule of thumb

Tag at the resource level ("products", `product-${id}`) and invalidate by tag from the mutation. Reach for revalidatePath when the unit really is a page (a CMS "publish" button), and for revalidatePath("/", "layout") only as a deliberate full flush — it is a cache-wide sledgehammer that every tagged fetch on the site will pay for.

unstable_cache — the Data Cache for ORM calls and SDKs

fetch options only reach HTTP. For Prisma, Drizzle, or any SDK that doesn't go through fetch, wrap the function with unstable_cache: same Data Cache, same revalidate and tags, keyed by the function's id + the keyParts you pass + the serialized arguments.

import { unstable_cache } from "next/cache";
import { db } from "@/lib/db";

export const getProducts = unstable_cache(
  async (categoryId: string) => {
    return db.product.findMany({
      where: { categoryId },
      orderBy: { createdAt: "desc" },
    });
  },
  ["products-by-category"],      // keyParts — distinguishes this from other wrapped fns
  {
    tags: ["products"],          // revalidateTag("products") purges every category
    revalidate: 3600,            // and it goes stale after an hour anyway
  }
);

// app/c/[id]/page.tsx — Next 15: params is a Promise
export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const products = await getProducts(id);
  // …
}
Gotchas
  • Arguments must be serializable — they become part of the key. Pass userId, not session.
  • You cannot call cookies() or headers() inside the wrapped function: the cache is shared across users, so per-request input has to come in as an argument. Forgetting this is how user A sees user B's dashboard.
  • The name is honest about the API surface, not about reliability — it is the production-stable choice in Next 15. The successor is the "use cache" directive (5d-05).

Request memoization for non-fetch: React cache()

Memoization of fetch is automatic. A database call made from a layout and a page in the same render runs twice unless you wrap it in React's cache() — a per-render memo keyed by arguments, dropped when the render finishes. It is not the Data Cache: nothing persists, nothing is shared between requests, so it is safe for user-specific reads.

import { cache } from "react";
import { db } from "@/lib/db";

// One query per render pass, however many components call it
export const getCurrentUser = cache(async (sessionId: string) => {
  return db.user.findFirst({ where: { sessionId } });
});

// layout.tsx and page.tsx both call getCurrentUser(sid) → one query
Python bridge

cache() ≈ functools.lru_cache attached to the request object instead of the process — identical arguments return the same promise, and the table is thrown away with the render. unstable_cache ≈ django.core.cache.

Exercise

This cache implements revalidate the Django way: when the entry is older than the window, the reader blocks on the origin, and every concurrent stale reader blocks on its own origin call. Make it stale-while-revalidate, as Next does: a stale read returns the old value immediately and starts one background refresh per key; readers arriving while that refresh is in flight get the old value and start nothing. origin is instrumented; the tests count its calls and check which value each read got.

// --- fake origin + clock (leave as is)
const clock = { now: 0 };
let originCalls = 0;
function origin(key) {
  originCalls++;
  return new Promise(r => setTimeout(() => r(`${key}@${clock.now}`), 10));
}

// --- fix this
function createCache({ revalidate }) {
  const entries = new Map();   // key → { value, at }
  return {
    async get(key) {
      const e = entries.get(key);
      if (e && clock.now - e.at < revalidate) return e.value;   // fresh → hit
      const value = await origin(key);                           // stale or miss: block
      entries.set(key, { value, at: clock.now });
      return value;
    },
  };
}

Forward pointer: "use cache", cacheLife, cacheTag

The directive-based model replaces unstable_cache's wrapper with an annotation on the function, component or file. In Next 15 it is experimental (experimental.useCache or dynamicIO in next.config.ts); Next 16 ships it as Cache Components. The semantics carry over one-to-one — a tag is a tag, a lifetime is a revalidate — so what this lesson taught stays true.

// next.config.ts: experimental: { useCache: true }   (Next 15)
import { cacheLife, cacheTag } from "next/cache";

export async function getProducts(categoryId: string) {
  "use cache";
  cacheTag("products");          // same tags, same revalidateTag("products")
  cacheLife("hours");            // named profile: seconds | minutes | hours | days | weeks | max
  return db.product.findMany({ where: { categoryId } });
}

Pick unstable_cache for Next 15 production code; read "use cache" code without surprise.

Code review
  • Optionless fetch in a static page. Ask "when is this supposed to be fresh?". If the answer is "per request", it needs cache: "no-store" or the route needs force-dynamic; if "every N minutes", next: { revalidate }. As written it is a build-time snapshot that next dev will never show you.
  • User data in the Data Cache. An unstable_cache or force-cache fetch whose result depends on the session but whose key doesn't include the user id is a cross-user leak. Either the user id is an argument (part of the key) or the read is not cached and goes through React cache() only.
  • revalidatePath("/", "layout") after every mutation. Flushes the site. Tag the fetches, invalidate the tag. Reviewers also look for mutations that revalidate nothing — the page will show the old row until the window expires.
  • One no-store fetch in a layout. It makes every route under that layout dynamic, which silently drops the Full Route Cache for the whole subtree. Scope dynamic reads to the component that needs them, or stream them in a Suspense boundary.
  • revalidate values that don't agree. The lowest one across a route's fetches wins for the route. A revalidate: 10 on a widget sets the page to 10 s whatever the page exported.
  • Calling revalidateTag during render (in a component, a generateMetadata) throws in Next 15. It belongs in a Server Action or route handler, after the write.
  • "It's stale after navigating back." That is the Router Cache, not the server. Next 15 defaults dynamic pages to 0 s there; if you set experimental.staleTimes up for speed, mutations need revalidatePath in the action (which clears it) or router.refresh().

Recall
In Next 15, what does a bare fetch(url) in a server component do — and does the answer differ between a static and a dynamic route?
It is not stored in the Data Cache. In a dynamic route it runs per request; in a static route it runs once at next build and the result is baked into the Full Route Cache. Per-request freshness needs cache: "no-store".
Name the four caches, where each lives, and how long each lasts.
Request memoization (server, one render pass); Data Cache (server, cross-request, until revalidated); Full Route Cache (server, static routes, until revalidated or redeployed); Router Cache (browser memory, dynamic 0 s / static 5 min in Next 15).
What is the difference between time-based (revalidate: 60) and on-demand (revalidateTag) revalidation for the request that crosses the boundary?
Time-based is stale-while-revalidate: that request gets the old value and a refresh runs behind it. On-demand purges: that request blocks on the origin and gets fresh data.

You have a Drizzle query for the product catalog. How do you cache it with tag-based invalidation, and what must its arguments satisfy?
Wrap it in unstable_cache(fn, keyParts, { tags: ["products"], revalidate }). Arguments must be serializable (they form the key) and the function must not read cookies()/headers() — the cache is shared across users.
Two components in one render call db.user.find(id). How do you make that one query, and why isn't unstable_cache the answer?
Wrap it in React cache(): per-render memoization keyed by arguments, dropped after the render. unstable_cache would persist the user row across requests and users.
After editing product 42 in a Server Action, which call purges only the product-related cached data, and what does revalidatePath("/", "layout") do instead?
revalidateTag("product-42") (or "products") — only entries carrying that tag. revalidatePath("/", "layout") invalidates every route under the root layout: a site-wide flush.
A layout does one fetch(url, { cache: "no-store" }). What happens to the routes beneath it?
They all become dynamic — rendered per request, with no Full Route Cache entry. Scope the uncached read to the component that needs it or stream it in a Suspense boundary.
