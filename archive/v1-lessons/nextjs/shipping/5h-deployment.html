Deployment — Vercel vs Self-hosted

next build produces three different kinds of output — static files, server code, middleware — and a host is just a decision about where each one runs. Vercel splits them across a CDN, serverless functions and edge functions with a shared cache; a self-hosted container runs all three in one Node process. Every deployment surprise (a stale NEXT_PUBLIC_ value, a 404 on a JS chunk, a revalidatePath that only "worked" on one replica) is one of those outputs landing somewhere you didn't picture. 5i builds on this when it adds a CDN, cache and queue around the app.

Environment variables — two namespaces, two moments

  • NEXT_PUBLIC_* — inlined into the client bundle at build time as string literals. Visible to every user in the JS source. Changing the value on the host after the build changes nothing until you rebuild.
  • Everything else — server-only, read from process.env at runtime in server components, actions, route handlers, middleware. Never shipped to the browser.

The second moment has a catch: statically prerendered pages run at next build. A page that reads process.env.CMS_TOKEN and fetches at build needs that variable in the build environment (the Docker build stage, the CI job), not only in the running container.

Rule

If a variable name starts with NEXT_PUBLIC_, it is baked into the JS bundle and visible in the browser's source. A DB password or API secret there is public. Use non-prefixed vars for anything sensitive and read them only in server code — import "server-only" on the module that reads them makes the bundler enforce it (5i).

// lib/env.ts — parse once at boot, fail fast, export typed values
import "server-only";
import { z } from "zod";

const schema = z.object({
  DATABASE_URL: z.string().url(),
  PORT: z.coerce.number().int().default(3000),
  DEBUG: z.enum(["true", "false"]).default("false").transform(v => v === "true"),
});
export const env = schema.parse(process.env);      // throws with every missing key listed

A six-line model of what the bundler does with env vars. inline plays next build; the two new Function calls play the browser and the server. What does this print, one line per console.log?

const buildEnv   = { NEXT_PUBLIC_API: "https://api.v1", DB_URL: "postgres://build" };
const runtimeEnv = { NEXT_PUBLIC_API: "https://api.v2", DB_URL: "postgres://prod" };

// next build: every env.NEXT_PUBLIC_* in client code becomes a string literal
function inline(src, env) {
  return src.replace(/env\.(NEXT_PUBLIC_\w+)/g, (_, k) => JSON.stringify(env[k]));
}

const clientCode = 'console.log("client api:", env.NEXT_PUBLIC_API, "db:", env.DB_URL);';
const serverCode = 'console.log("server api:", env.NEXT_PUBLIC_API, "db:", env.DB_URL);';

const bundle = inline(clientCode, buildEnv);       // produced once, at build
console.log(bundle);
new Function("env", bundle)({});                   // browser: there is no server env
new Function("env", serverCode)(runtimeEnv);       // server: reads env per request

loadConfig runs once at boot and is the only place the app reads env. Env values are always strings (or missing), and this version forgets that: a PORT of "8080" comes out as a string, DEBUG="false" comes out truthy, and a missing DATABASE_URL is returned as undefined instead of failing at boot. Fix it: numbers parsed, booleans accept "true"/"1" as true and "false"/"0" as false, defaults applied only when the key is absent, and a missing required key throws an Error whose message names it.

function loadConfig(env) {
  return {
    port: env.PORT || 3000,
    debug: env.DEBUG || false,
    maxConnections: env.MAX_CONNECTIONS || 10,
    databaseUrl: env.DATABASE_URL,
  };
}

What next build produces

One command, three kinds of artifact. Where each one runs is what differs between hosts.

  • Static assets — .next/static/ (hashed JS/CSS chunks, immutable forever) and prerendered HTML + RSC payloads for every route that could be rendered at build. Serve from a CDN.
  • Server code — .next/server/: route handlers, server components, server actions, the ISR renderer. Needs Node (or, per route, the Edge runtime).
  • Middleware — a separate bundle meant to run before routing, as close to the user as possible.

Per route, the build also decides a rendering mode from the route's segment config and what it reads: static (prerendered once), ISR (prerendered, regenerated after revalidate seconds), dynamic (rendered per request), or edge (runtime = "edge"). next build prints this table; read it before every deploy.

Route (app)                     Size   First Load JS
┌ ○ /                           1.2 kB      90 kB     ○ static
├ ● /blog/[slug]                2.1 kB      92 kB     ● SSG / ISR  (revalidate: 60)
├ ƒ /dashboard                  4.0 kB      99 kB     ƒ dynamic  (uses cookies)
└ ƒ /api/health                 0 B          0 B
ƒ Middleware                    28 kB
Mechanism

Same build, two placements. Vercel fans the three outputs out to specialised runtimes with one shared cache; a standalone container (dashed) runs all three in one process with a cache on its own disk — which is why multi-replica self-hosting needs a cacheHandler.

Self-hosting with output: "standalone"

// next.config.ts
import type { NextConfig } from "next";
const config: NextConfig = { output: "standalone" };
export default config;

The build traces every file the server actually imports and writes a self-contained .next/standalone/: a server.js plus a pruned node_modules. Two things are deliberately not included and must be copied in: .next/static (the hashed client chunks) and public/. Forgetting either gives a page that renders and then 404s on every JS file.

# Dockerfile — two stages: build with everything, run with the trace
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
# Build-time env: NEXT_PUBLIC_* and anything a prerendered page reads
RUN npm run build

FROM node:22-alpine
WORKDIR /app
ENV NODE_ENV=production HOSTNAME=0.0.0.0 PORT=3000
COPY --from=build /app/.next/standalone ./
COPY --from=build /app/.next/static ./.next/static
COPY --from=build /app/public ./public
USER node
EXPOSE 3000
CMD ["node", "server.js"]

HOSTNAME=0.0.0.0 matters: the standalone server binds to localhost by default, which inside a container means unreachable. Runtime secrets (DATABASE_URL, AUTH_SECRET) go in at docker run / the orchestrator, not in the image.

What changes when you self-host

  • Image optimization — Next 15 bundles sharp, so next/image works in the container without extra installs. It costs CPU on your server per unique size; at volume, point images.loader at a CDN (Cloudinary, imgix, Cloudflare Images) and keep images.remotePatterns tight.
  • ISR and the data cache — default storage is the filesystem under .next/cache, per replica. With two containers behind a load balancer, revalidatePath() invalidates the one that ran it. Configure cacheHandler (Redis via @neshca/cache-handler, or your own) and set cacheMaxMemorySize: 0 so every replica reads the same cache.
  • Middleware — runs in your Node process, before routing. Same semantics, no edge latency benefit; put a CDN in front if you need geography.
  • Version skew — each replica must serve the same build: identical image tag, and generateBuildId pinned to the git SHA if you ever build per replica. Otherwise a client loaded from replica A asks replica B for a chunk hash it doesn't have.
  • Process model — one Node process per container, no built-in worker pool. Scale by replicas, not threads; put a health check on a route handler (/api/health) and let the orchestrator restart on failure.
// next.config.ts — shared cache for multi-replica ISR
const config: NextConfig = {
  output: "standalone",
  cacheHandler: require.resolve("./cache-handler.mjs"),
  cacheMaxMemorySize: 0,                 // disable the in-process LRU; Redis is the source of truth
  generateBuildId: async () => process.env.GIT_SHA ?? null,
};
Python bridge

The standalone container is gunicorn and collectstatic in one. node server.js is the app server (one process, async — think a single uvicorn worker, not gunicorn's --workers 4; you scale with replicas). COPY .next/static and public into the image is collectstatic, except nothing like whitenoise is needed — the Next server serves them, and a CDN in front caches the hashed _next/static/* paths forever. What has no Django equivalent is build-time inlining: settings.py reads os.environ when the process starts, full stop, whereas NEXT_PUBLIC_* is frozen into the artifact at docker build. And prerendering means some of your "views" run during the build — the equivalent of Django executing a template at collectstatic time and needing the database then.

Other targets — OpenNext, Cloudflare, Vercel

  • Vercel — zero config: CDN for static, a serverless function per route (or one edge function for runtime = "edge" routes and middleware), ISR and fetch cache shared globally, image optimization, preview deployments per branch. If you're small, just use it. What you give up: control over regions and runtimes, and the per-invocation bill when a page turns dynamic by accident (5h-13).
  • OpenNext — community adapters that split the build the way Vercel does, for other clouds: @opennextjs/aws (Lambda + CloudFront + S3, used by SST) and @opennextjs/cloudflare (Workers with Node compatibility — the successor to the deprecated @cloudflare/next-on-pages, which forced the Edge runtime on every route).
  • Container hosts — Fly.io, Railway, Render, ECS, Kubernetes: the standalone image from 5h-02 plus a shared cache handler if you run more than one replica.
npx opennextjs-cloudflare build      # adapts .next output for Workers
npx opennextjs-cloudflare deploy

Post-response work — after()

after() (stable in Next 15.1, next/server) schedules work to run once the response has been sent: analytics, audit logs, cache warming. The response isn't delayed by it, and it works in server components, actions, route handlers and middleware.

import { after } from "next/server";

export async function GET() {
  after(async () => {
    await analytics.track("page_view");   // runs after the response is flushed
  });
  return Response.json({ ok: true });
}

On serverless hosts the platform must keep the function alive for it (Vercel does, via waitUntil); in a container it just runs in the same process. Either way it's best-effort — a crash or a scale-down loses it. Anything that must happen goes in a queue (5i), not in after().

Startup and error hooks — instrumentation.ts

Stable in Next 15 (no flag). Two exports from the project root: register() runs once per server start — initialise OpenTelemetry, Sentry, a logger; onRequestError() is called for every uncaught error in server code, with the request and the route it came from.

// instrumentation.ts
import type { Instrumentation } from "next";

export async function register() {
  if (process.env.NEXT_RUNTIME === "nodejs") {        // also runs for the edge runtime; branch on it
    const { init } = await import("./sentry.server.config");
    init();
  }
}

export const onRequestError: Instrumentation.onRequestError = async (err, request, context) => {
  await reportError(err, { path: request.path, route: context.routePath, kind: context.routeType });
};

Dynamic import() inside register is deliberate: the file is loaded for both runtimes, and a Node-only SDK at the top level breaks the edge build. For Sentry specifically, withSentryConfig() around next.config.ts generates this file and uploads source maps.

Code review
  • Changed a NEXT_PUBLIC_ value in the host's dashboard and redeployed the same image. No effect — it's a literal in the bundle. Rebuild, or move the value to the server and pass it down as a prop.
  • Standalone image without .next/static and public. HTML renders, every chunk 404s, page never hydrates. The two COPY lines are not optional.
  • Two or more replicas and no cacheHandler. revalidatePath / revalidateTag only clear the replica that ran them; users see different data depending on which container the load balancer picked. Redis-backed handler, cacheMaxMemorySize: 0.
  • Prerendered page reads a secret that only exists at runtime. Build succeeds with undefined or fails in CI with a confusing stack. Either provide it to the build stage, or make the route dynamic on purpose.
  • Boolean env via ||. DEBUG=false enables debug. Parse env once through a schema (lib/env.ts) and import the parsed object everywhere.
  • Must-happen work in after(). Billing, emails, webhooks: best-effort is not enough. after() for telemetry; a queue with retries for anything with a consequence.
  • No health check, binding to localhost. The orchestrator can't tell a wedged process from a healthy one, and a missing HOSTNAME=0.0.0.0 makes the container "healthy" and unreachable.

Recall
What are the three kinds of output of next build, and where does Vercel run each?
Static assets + prerendered pages → CDN; server code (RSC, actions, route handlers) → serverless function per route; middleware → edge function. Plus a globally shared ISR / fetch cache.
When is NEXT_PUBLIC_API_URL read, and what happens if you change it on the host without rebuilding?
At build time — it's inlined as a string literal into the client bundle. Changing it later does nothing until the next next build. Non-prefixed vars are read from process.env at runtime.
What does this print? 
const env = { DEBUG: "false" };
console.log(env.DEBUG || false, env.DEBUG === "true");
false false — the first is the string "false" (truthy), printed as its value. Env values are strings; parse them, never || them.
Which two directories must be copied into a standalone Docker image by hand, and what breaks without them?
.next/static (hashed JS/CSS chunks) and public/. Without them the HTML renders but every chunk 404s and the page never hydrates.
Why does ISR invalidation misbehave with several self-hosted replicas, and what's the fix?
The cache is on each replica's own disk/memory; revalidatePath clears only the replica that ran it. Configure a shared cacheHandler (Redis) and cacheMaxMemorySize: 0.
A page calls cookies() with no other config. What rendering mode does next build assign, and how do you force it static?
Dynamic (rendered per request, a function invocation on serverless). export const dynamic = "force-static" makes it static — and cookies() then returns empty.
What is after() for, and what must not go in it?
Best-effort work after the response is sent (analytics, audit logs). Not for anything that must happen — a crash or scale-down loses it; use a queue with retries.
Which two functions can instrumentation.ts export?
register() — runs once at server start (init OpenTelemetry / Sentry; branch on NEXT_RUNTIME, dynamic-import Node-only SDKs); onRequestError(err, request, context) — called for every uncaught server error with the route it came from.
