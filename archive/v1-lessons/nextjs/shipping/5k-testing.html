Testing Next.js Apps

  • Unit / component — Vitest + React Testing Library. Same as Part 4. Client components are easy; server components that await fetch need care.
  • E2E — Playwright is the standard. Hits a real running server, clicks through real user flows. Catches the integration bugs other tests miss.
  • Server actions — test the underlying service function directly. Don't test the "wire" — test the logic.

Testing RSC — the practical pattern

RSC can't be rendered in jsdom (no server environment). The pattern: extract async data fetching into a service function, test the service directly, and test the rendered component output by mocking the service.

// server/services/posts.ts — testable in isolation
export async function getPost(slug: string) {
  return db.post.findUniqueOrThrow({ where: { slug } });
}

// __tests__/services/posts.test.ts
import { getPost } from "@/server/services/posts";
vi.mock("@/lib/db", () => ({ db: { post: { findUniqueOrThrow: vi.fn() } } }));

test("getPost returns post data", async () => {
  db.post.findUniqueOrThrow.mockResolvedValue({ slug: "hello", title: "Hello" });
  const post = await getPost("hello");
  expect(post.title).toBe("Hello");
});

// __tests__/components/post-page.test.tsx — test rendered output
import { render, screen } from "@testing-library/react";
vi.mock("@/server/services/posts", () => ({
  getPost: vi.fn().mockResolvedValue({ title: "Hello", body: "World" }),
}));

test("PostPage renders title", async () => {
  const { default: PostPage } = await import("@/app/blog/[slug]/page");
  render(await PostPage({ params: Promise.resolve({ slug: "hello" }) }));
  expect(screen.getByRole("heading", { name: "Hello" })).toBeInTheDocument();
});

Fetch mocking in Vitest — MSW

Mock Service Worker (MSW) intercepts fetch at the network level — works in both browser (via service worker) and Node/Vitest (via msw/node). Cleaner than monkey-patching global.fetch.

// __tests__/setup.ts
import { setupServer } from "msw/node";
import { http, HttpResponse } from "msw";

export const server = setupServer(
  http.get("https://api.example.com/posts", () => {
    return HttpResponse.json([{ id: 1, title: "MSW post" }]);
  })
);

beforeAll(() => server.listen());
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

E2E API interception — Playwright page.route()

In E2E tests, mock external APIs (payment gateways, third-party services) without hitting the real endpoints.

test("checkout shows success on payment API response", async ({ page }) => {
  // Intercept the external payment API before navigating
  await page.route("https://payments.example.com/charge", async (route) => {
    await route.fulfill({
      status: 200,
      contentType: "application/json",
      body: JSON.stringify({ status: "success", chargeId: "ch_test_123" }),
    });
  });

  await page.goto("/checkout");
  await page.getByRole("button", { name: "Pay" }).click();
  await expect(page.getByText("Payment successful")).toBeVisible();
});
// Playwright
import { test, expect } from "@playwright/test";

test("user can log in and see dashboard", async ({ page }) => {
  await page.goto("/login");
  await page.getByLabel("Email").fill("u@ex.com");
  await page.getByLabel("Password").fill("hunter22");
  await page.getByRole("button", { name: "Log in" }).click();
  await expect(page).toHaveURL(/dashboard/);
  await expect(page.getByRole("heading", { name: /welcome/i })).toBeVisible();
});
What I'd set up on day one
  • Playwright with 3-5 critical-path tests. Wire to CI. Don't chase coverage — chase user flows.
  • Vitest for services, utils, schemas, and pure components.
  • A small set of unit tests for server actions (call the exported function with fixtures).
  • A health-check E2E that hits /healthz and a smoke test of the homepage.
  • MSW for any component tests that involve fetch — keeps tests deterministic without disabling the network layer.
  • page.route() in Playwright for tests that would otherwise hit real payment or external APIs.
