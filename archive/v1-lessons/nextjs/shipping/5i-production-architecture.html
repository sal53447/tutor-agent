The "server-only" guard

import "server-only"; at the top of a file throws at build time if a client component tries to import it. Put it on DB clients, auth helpers, secrets. Catches the "I accidentally bundled my DB library into the browser" bug.

  • Separate client-only modules ("use client") from universal ones. Be deliberate.
  • Environment schema in src/lib/env.ts — Zod-parsed, throws on missing at boot.
  • Shared Zod schemas live in lib/schemas/; forms and server actions both import them.
  • Keep app/ thin. Heavy logic lives in server/services/ that both server components and server actions call.

The inverse guard — client-only

The client-only package is the mirror of server-only. Import it at the top of files that must never run on the server (e.g., files using window, browser-only APIs, or client-only state). Throws at build if a server component imports it.

// lib/browser-analytics.ts
import "client-only";    // guarantees this file never reaches the server
export function track(event: string) { window.dataLayer?.push({ event }); }

Service functions — shared by components and actions

The canonical pattern: business logic lives in a service function in server/services/, called from both server components (for reading) and server actions (for mutations). The action adds authorization; the component just fetches.

// server/services/posts.ts
import "server-only";
import { db } from "@/lib/db";

export async function getPostsByUser(userId: string) {
  return db.post.findMany({ where: { authorId: userId }, orderBy: { createdAt: "desc" } });
}

// app/dashboard/page.tsx (server component — reads)
import { getPostsByUser } from "@/server/services/posts";
const posts = await getPostsByUser(session.user.id);

// app/actions.ts (server action — mutates, re-authorizes first)
export async function deletePost(postId: string) {
  const session = await auth();
  if (!session) throw new Error("Unauthenticated");
  const post = await db.post.findUnique({ where: { id: postId } });
  if (post?.authorId !== session.user.id) throw new Error("Forbidden");
  await db.post.delete({ where: { id: postId } });
}

Connection pooling in serverless

Serverless functions spin up hundreds of instances under load. Each instance opening its own DB connection quickly exhausts Postgres's connection limit.

  • Prisma — use PgBouncer (set ?pgbouncer=true&connection_limit=1 in the URL) or Prisma Accelerate (managed pooling proxy from Prisma).
  • Drizzle — same problem; use pg with a pooled Neon / Supabase connection string, or a PgBouncer sidecar.
  • Long-running servers (Docker / Fly.io) don't have this problem — the single process holds a small pool.

Observability

  • Structured logging with pino — JSON logs, minimal overhead, works in Node and Edge.
  • Error tracking via Sentry — wrap next.config.ts with withSentryConfig(); add instrumentation.ts for server-side init (see 5h).
  • Traces via instrumentation.ts — initialize OpenTelemetry once at startup; works with Datadog, Grafana, Honeycomb.
Python bridge

The service layer pattern (server/services/) is identical to Django's service layer or a Flask services.py module. The view (server component) calls the service to get data; the form handler (server action) calls the service after authorization. Separating concerns this way makes everything individually testable — which is exactly why you'd do it in Django too.
