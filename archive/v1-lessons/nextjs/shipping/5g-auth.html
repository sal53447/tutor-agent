Auth in Next.js — Sessions, Cookies & Where the Check Runs

Auth in the App Router is three questions, not one: what proves identity (a cookie carrying a signed JWT or an opaque session id), where the check runs (middleware on the edge, a layout or page on the server, the server action that mutates), and what each location can know (the edge sees only the cookie; the server can hit the DB). Getting one of them wrong is the most common security bug in Next apps, and 5i's production architecture assumes you can place a check at the right layer without thinking.

Auth.js v5 — one config, four exports

The ecosystem default is Auth.js (NextAuth v5). One file exports everything: auth() reads the session anywhere on the server, handlers mount the OAuth / credentials endpoints, signIn / signOut are callable from server actions.

// auth.ts
import NextAuth from "next-auth";
import Google from "next-auth/providers/google";

export const { auth, handlers, signIn, signOut } = NextAuth({
  providers: [Google],
  session: { strategy: "jwt" },            // default; "database" needs an adapter
  callbacks: {
    jwt({ token, user }) { if (user) token.role = user.role; return token; },
    session({ session, token }) {
      session.user.id = token.sub!;
      session.user.role = token.role as string;
      return session;
    },
  },
});

// app/api/auth/[...nextauth]/route.ts
import { handlers } from "@/auth";
export const { GET, POST } = handlers;

// anywhere server-side: layout, page, server action, route handler
import { auth } from "@/auth";
const session = await auth();
if (!session) redirect("/login");

Config comes from env: AUTH_SECRET (signs and encrypts the session JWT), AUTH_GOOGLE_ID / AUTH_GOOGLE_SECRET (providers pick these up by name). AUTH_URL is only needed when the host can't be inferred; behind a proxy set AUTH_TRUST_HOST=true. The v4 names (NEXTAUTH_SECRET, NEXTAUTH_URL) are stale.

Middleware is Edge by default

middleware.ts runs on the Edge runtime unless you opt into Node (export const config = { runtime: "nodejs" }, Next 15.5+). A database adapter (Prisma, Drizzle) can't be imported there. Auth.js's answer is the split config: auth.config.ts holds providers and callbacks only and is what middleware imports; auth.ts spreads it and adds the adapter.

Python bridge

Django has the same three layers under different names. LoginRequiredMiddleware (Django 5.1) / a hand-written middleware is the middleware layer: it sees the cookie, resolves the session, and bounces anonymous users before any view runs. @login_required and @permission_required("app.change_post") on a view are the layout / page layer: they run per view with the full request.user loaded from the DB. The ownership check inside the view body — if post.author != request.user: raise PermissionDenied — is the server action layer: per operation, per object. What differs: Django's session is always DB-backed (an opaque id in sessionid), so revocation is instant by default; Auth.js defaults to a self-contained JWT and makes you choose.

Three-layer defense — each layer has a different job

  • Middleware — coarse, stateless, cookie-based. Blocks unauthenticated requests before they reach the app. Fast; no DB. Cannot check fine-grained roles beyond what's in the token, and only covers paths the matcher names.
  • Layout / page (server component) — fine-grained. Has the session; can query the DB for the user's actual role or plan. Redirect or render fallback UI here. Prefer the page or a data-access function over a layout: layouts don't re-render on client-side navigation between sibling routes, so a layout-only check can be skipped.
  • Server action / route handler — always re-authorize. A user can POST to an action directly with any arguments; the action must verify permission for that specific operation regardless of what the UI rendered.
// middleware.ts — layer 1: has the cookie, nothing else
import { auth } from "@/auth.config";       // providers + callbacks only, Edge-safe

export default auth((req) => {
  if (!req.auth) {
    const url = new URL("/login", req.nextUrl.origin);
    url.searchParams.set("callbackUrl", req.nextUrl.pathname);
    return Response.redirect(url);
  }
});
export const config = { matcher: ["/dashboard/:path*", "/settings/:path*"] };

// lib/dal.ts — layer 2: one place every page/action asks
import "server-only";
import { cache } from "react";

export const verifySession = cache(async () => {
  const session = await auth();
  if (!session?.user) redirect("/login");
  return session;                           // cached per request, not per call
});

// app/actions.ts — layer 3: re-check for this operation
"use server";
export async function deletePost(postId: string) {
  const { user } = await verifySession();
  const post = await db.post.findUnique({ where: { id: postId } });
  if (post?.authorId !== user.id) throw new Error("Forbidden");
  await db.post.delete({ where: { id: postId } });
  revalidatePath("/posts");
}
redirect() throws

redirect() and notFound() work by throwing a special error that Next catches. Call them inside your own try { … } catch {} and you'll swallow the redirect and keep rendering — a protected page that silently renders for a logged-out user. Keep the check outside the try, or rethrow after isRedirectError(err).

Mechanism

Each layer answers a cheaper question than the next: "is there a valid token?" → "may this user see this page?" → "may this user do this to this row?". Only the last one can be trusted for a mutation.

Two session strategies, one "log out everywhere". now is fixed. What does this print? One line per console.log, values separated by a space.

const now = 1000;
const dbSessions = new Map();                       // id → { userId }

function loginJwt(userId) { return { userId, exp: now + 3600 }; }    // the cookie IS the session
function loginDb(userId)  { dbSessions.set("s1", { userId }); return "s1"; }  // opaque id in cookie

function checkJwt(token) { return token.exp > now ? token.userId : null; }
function checkDb(id)     { return dbSessions.get(id)?.userId ?? null; }

const jwtCookie = loginJwt("u1");
const dbCookie  = loginDb("u1");
console.log(checkJwt(jwtCookie), checkDb(dbCookie));

dbSessions.clear();                                 // "log out everywhere"
console.log(checkJwt(jwtCookie), checkDb(dbCookie));

console.log(checkJwt({ ...jwtCookie, exp: now }));  // same token, an hour later

Session cookies — JWT vs DB session

  • strategy: "jwt" (Auth.js default) — the cookie holds an encrypted, signed token with the claims you put in it. No DB lookup per request; works in Edge middleware. Revocation is impossible without a blocklist or short expiry — a disabled user keeps a valid token until exp. Roles copied into the token at login go stale the same way.
  • strategy: "database" (Auth.js with an adapter, Better-Auth) — the cookie holds an opaque session id; the session row lives in the DB. Instant revocation and live roles; costs a DB read per request, and middleware can only check "a cookie exists" unless it can reach the store.

Rule of thumb: JWT when sessions are long-lived and revocation can wait minutes (set session.maxAge short and let Auth.js rotate); DB sessions when "log out everywhere", role changes, or admin bans must take effect on the next request.

Payload ≠ secret

A plain JWT (header.payload.signature) is base64url, not encryption — anyone holding it can read the claims. Auth.js wraps its session token in a JWE, so the cookie's contents are opaque; a token you mint yourself with jose's SignJWT is not. Never put anything in a signed-only token you wouldn't show the user.

The cookie itself — attributes that do the work

Whatever the strategy, the browser is the storage and the Set-Cookie attributes are the security model. Auth.js sets these for you; hand-rolled sessions (route handler + cookies().set()) must set them explicitly.

Set-Cookie: __Secure-authjs.session-token=eyJ…; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=2592000
  • HttpOnly — invisible to document.cookie. An XSS can still use the session (it's attached automatically) but can't exfiltrate it.
  • Secure — HTTPS only. The __Secure- / __Host- name prefixes make the browser refuse the cookie if it's missing.
  • SameSite=Lax — not sent on cross-site POSTs, which is the baseline CSRF defence; still sent on top-level GET navigations so links from elsewhere stay logged in. Strict breaks "click a link in an email, land logged in". None requires Secure and reopens CSRF — only for cross-site embedding.
  • Path=/, Max-Age — scope and lifetime. No Max-Age / Expires = session cookie, gone when the browser closes (not when the tab does).
// Hand-rolled: a route handler or server action setting its own session cookie
import { cookies } from "next/headers";

const jar = await cookies();                      // async in Next 15
jar.set("session", sessionId, {
  httpOnly: true, secure: process.env.NODE_ENV === "production",
  sameSite: "lax", path: "/", maxAge: 60 * 60 * 24 * 7,
});
Try it

A signed-only JWT, decoded with nothing but atob. Change exp to make it expired, add a claim to the payload, then try to change the role without the secret — the signature check (simulated with a fixed sig) catches the tampered payload.

const b64url = s => btoa(s).replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
const fromB64url = s => atob(s.replace(/-/g, "+").replace(/_/g, "/"));

const header  = { alg: "HS256", typ: "JWT" };
const payload = { sub: "42", role: "user", exp: 1700000000 };
const secret  = "dev-secret";
// a real HMAC would go here; a stand-in that still depends on every byte + the secret
const sign = (data) => [...data + secret].reduce((h, c) => (h * 31 + c.charCodeAt(0)) >>> 0, 7).toString(16);

const data = b64url(JSON.stringify(header)) + "." + b64url(JSON.stringify(payload));
const token = data + "." + sign(data);

// Anyone can read it:
console.log(JSON.parse(fromB64url(token.split(".")[1])));

// Only the secret holder can verify it:
const verify = t => { const [h, p, s] = t.split("."); return sign(h + "." + p) === s; };
console.log("valid:", verify(token));

// Tamper with the role → signature no longer matches
const forged = token.split(".")[0] + "." + b64url(JSON.stringify({ ...payload, role: "admin" })) + "." + token.split(".")[2];
console.log("forged valid:", verify(forged));
console.log("expired:", payload.exp < 1700000001);
{ sub: "42", role: "user", exp: 1700000000 } valid: true forged valid: false expired: true
Exercise

sessionCookie builds the Set-Cookie header for a hand-rolled session on an HTTPS site. It's missing two attributes a reviewer would block the PR for: the cookie is readable from JavaScript and is sent on cross-site POSTs. Add them. In local dev (secure: false, plain http) the cookie must still be protected from scripts and cross-site POSTs — only Secure is conditional. Tests parse the header with parseSetCookie.

// --- helper (leave as is)
function parseSetCookie(header) {
  const [pair, ...attrs] = header.split(";").map(s => s.trim());
  const [name, value] = pair.split("=");
  const out = { name, value, attrs: {} };
  for (const a of attrs) { const [k, v = true] = a.split("="); out.attrs[k.toLowerCase()] = v; }
  return out;
}

// --- fix this
function sessionCookie(token, { secure = true } = {}) {
  const parts = [`session=${token}`, "Path=/", `Max-Age=${60 * 60 * 24 * 7}`];
  if (secure) parts.push("Secure");
  return parts.join("; ");
}

CSRF and server actions

Server actions are POST-only and Next.js compares the request's Origin header with the Host (or X-Forwarded-Host) before running one; a mismatch is rejected. Combined with SameSite=Lax on the session cookie, the standard setup needs no CSRF token. Gaps to know:

  • Behind a reverse proxy or on a multi-domain setup the two headers can differ. Whitelist the public hosts: experimental: { serverActions: { allowedOrigins: ["app.example.com"] } } in next.config.ts.
  • Actions can't be called from a different origin (a native app, a partner site) — that's the point. Expose a route handler with explicit CORS and bearer auth instead.
  • Route handlers get none of this. A POST handler that mutates on the strength of a cookie alone needs its own origin check or a CSRF token.
  • The action's ID is a hash, but it's in the page's JS — it is not a secret and not an authorization check.

Auth.js vs the alternatives

  • Auth.js — OAuth / email / credentials, JWT or adapter-backed sessions, free, you own the user table. Weak on MFA and org management; you build those.
  • Better-Auth — the actively maintained lightweight alternative: DB sessions by default, plugins for 2FA, organizations, passkeys. Lucia (v2 and earlier) is sunset — don't start on it.
  • Clerk, WorkOS, Auth0 — managed. SSO, MFA, SCIM, audit logs without building them; the user table lives with the vendor and so does your per-MAU bill.

Whichever you pick, the three layers in 5g-02 don't change — only the function you call to get the session.

Code review
  • Auth only in middleware. The matcher is a list someone forgets to extend when a route is added. Every page and action must call verifySession() itself; middleware is an optimisation, not the guard.
  • Auth only in a layout. Layouts don't re-render on client-side navigation between their children, and a layout can't see the child's params. Put the check in the page or in the data-access function that loads the data.
  • Server action without re-authorization. "The button is only rendered for owners" is not a check. Any action exported from the bundle can be invoked with any arguments. The action loads the row and compares authorId to the session's user — every time.
  • redirect() inside try/catch. Swallows the NEXT_REDIRECT error and renders the protected page. Move the redirect outside, or rethrow when isRedirectError(err).
  • Role in the JWT, never refreshed. A promotion or ban doesn't apply until the token expires. Either keep session.maxAge short, re-read the role from the DB in the jwt callback on trigger === "update", or use DB sessions.
  • Hand-rolled cookie without HttpOnly / SameSite. cookies().set("session", id) with defaults is readable by any script and sent cross-site. Pass the options object every time; better, wrap it once in a setSessionCookie() helper.
  • DB adapter imported into middleware. Breaks the Edge build or, on Node, opens a DB connection per request at the edge. Split the config (auth.config.ts without adapter) or move the fine-grained check to the page.

Recall
Auth.js v5: what does auth.ts export, and where are the HTTP handlers mounted?
{ auth, handlers, signIn, signOut }. app/api/auth/[...nextauth]/route.ts does export const { GET, POST } = handlers; await auth() reads the session in any server code.
Name the three auth layers in a Next.js app and the one question each can answer.
Middleware (edge, cookie only): "is there a valid token for this path?". Page / data-access layer (server, has DB): "may this user see this?". Server action (has args): "may this user do this to this row?". Only the last is trustworthy for a mutation.
JWT session vs DB session — the trade-off in one sentence each.
JWT: no DB read per request, works at the edge, but can't be revoked before exp and claims go stale. DB: instant revocation and live roles, costs a lookup per request.
Which Set-Cookie attributes does a session cookie need, and what does each prevent?
HttpOnly (script can't read it — XSS can't exfiltrate), Secure (HTTPS only), SameSite=Lax (not sent on cross-site POSTs — CSRF floor), Path=/ + Max-Age (scope, lifetime).
What does this print? 
const now = 1000, db = new Map([["s1", "u1"]]);

u1 null. Clearing the store revokes the DB session instantly; the JWT stays valid until exp because nothing server-side remembers it.
How does Next.js protect server actions from CSRF, and what do you configure behind a proxy whose hostname differs?
Actions are POST-only and the Origin header must match Host / X-Forwarded-Host; plus SameSite=Lax on the cookie. Behind a proxy: experimental.serverActions.allowedOrigins in next.config.ts. Route handlers get none of this.
Why is a session check placed only in a layout not enough?
Layouts don't re-render on client-side navigation between sibling routes and can't read the child page's params. Check in the page or in a cache()-wrapped verifySession() that every page and action calls.
Why does middleware.ts import auth.config.ts instead of auth.ts?
Middleware runs on the Edge runtime by default; a DB adapter can't load there. The split config keeps providers + callbacks Edge-safe and adds the adapter only in auth.ts.
