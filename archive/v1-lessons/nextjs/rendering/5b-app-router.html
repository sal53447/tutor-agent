App Router Architecture

In the App Router the folder structure is the routing: a URL is matched segment by segment against directories under app/, and each directory contributes a fixed set of special files that nest around the page. Everything later in Part 5 — where data is fetched (5c, 5d), where actions run (5e), which middleware sees a request (5f) — is expressed as "which segment does this file sit in". Pages Router (pages/) still works in Next 15 but is legacy; nothing here applies to it.

Folder = segment; page.tsx = reachable URL

app/
  layout.tsx            # root shell — must render <html> and <body>
  page.tsx              # /
  loading.tsx           # Suspense fallback for this segment
  error.tsx             # error boundary for this segment ("use client")
  not-found.tsx         # rendered by notFound() and for unmatched URLs
  (marketing)/          # route group — not part of the URL
    layout.tsx          # applies to /about only
    about/page.tsx      # /about
  blog/
    layout.tsx
    new/page.tsx        # /blog/new     (static segment wins over [slug])
    [slug]/page.tsx     # /blog/:slug   → params: Promise<{ slug: string }>
  docs/
    [...path]/page.tsx  # /docs/a/b     → params.path = ["a", "b"]; needs ≥ 1 segment
    # [[...path]]/      # optional catch-all: also matches /docs
  api/
    users/route.ts      # /api/users — GET/POST handlers; cannot share a segment with page.tsx

Only a page.tsx (or route.ts) makes a URL exist; a folder with just a layout.tsx is a wrapper, not a route. Precedence when several files could match: static segment > [dynamic] > [...catchAll]. Route groups (name) are invisible to the URL but real to layouts — they are how two sections of a site get different shells under the same root.

Python bridge

Django's URLconf is explicit — path("blog/<slug:slug>/", views.post) — and include() nests one URLconf under a prefix. Next's file-system routing is the same tree with the names erased: a directory is an include(), [slug] is <slug:slug>, [...path] is <path:rest>. A layout.tsx is {% extends "base.html" %} with {children} as {% block content %} — except a Django base template is re-rendered on every request, whereas a Next layout is a live component that persists across client-side navigations and keeps its state. Route groups, parallel and intercepting routes have no Django equivalent: they exist because the "page" is a long-lived client tree, not a fresh response.

Layouts — persistent shells

A layout.tsx wraps every route in its segment and persists across navigation: when the URL changes, only the segments that changed re-render; the layout instance (and any client state inside it) stays mounted. Layouts receive children and params, never searchParams — a persistent component cannot depend on something that changes with every navigation.

// app/layout.tsx — the root layout is required and owns the document
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <Header />
        <main>{children}</main>
      </body>
    </html>
  );
}

// app/blog/[slug]/layout.tsx — nested layouts get params too (Next 15: a Promise)
export default async function PostLayout(
  { children, params }: { children: React.ReactNode; params: Promise<{ slug: string }> }
) {
  const { slug } = await params;
  return <section data-slug={slug}>{children}</section>;
}

Special files

  • loading.tsx — a Suspense boundary around the segment's page. Shows during the initial stream and during navigation while the page's data is pending.
  • error.tsx — an error boundary around the segment. Must be "use client" (boundaries need client lifecycle). It receives error and reset(). It catches errors from the page and everything below — not from the layout of its own segment; that needs the parent's error.tsx, or global-error.tsx for the root layout.
  • template.tsx — like layout.tsx but re-mounts on every navigation. Use for effects that must re-run per route (page-view analytics, enter animations) or state that must reset.
  • not-found.tsx — rendered when notFound() is thrown in the segment; the root one also serves unmatched URLs.
  • default.tsx — fallback for a parallel-route slot on hard navigation (below).
  • route.ts — HTTP handlers: export async function GET(req: Request) {…}, returning a Response. Cannot share a segment with page.tsx.
// app/blog/[slug]/error.tsx
"use client";
export default function PostError({ error, reset }: { error: Error & { digest?: string }; reset: () => void }) {
  return (
    <div role="alert">
      <p>Could not load this post. ({error.digest})</p>
      <button onClick={reset}>Try again</button>   {/* re-renders the segment */}
    </div>
  );
}
Gotcha

Forgetting "use client" on error.tsx is a build error, not a silent one. The silent failure is the other direction: an error thrown in app/blog/layout.tsx is not caught by app/blog/error.tsx — the boundary is inside the layout. It propagates to app/error.tsx.

const files = [
  "app/page.tsx",
  "app/(marketing)/about/page.tsx",

// "app/(g)/blog/[slug]/page.tsx" → ["blog", "[slug]"]: route groups vanish, page.tsx is implied
const segmentsOf = (file) =>
  file.replace(/^app\//, "").replace(/\/?page\.tsx$/, "").split("/").filter((s) => s && !/^\(.*\)$/.test(s));

function matchOne(file, pathname) {
  const segs = segmentsOf(file), parts = pathname.split("/").filter(Boolean), params = {};
  for (let i = 0; i < segs.length; i++) {
    const s = segs[i], p = parts[i];
    const optional = /^\[\[\.\.\.(\w+)\]\]$/.exec(s), rest = /^\[\.\.\.(\w+)\]$/.exec(s), dyn = /^\[(\w+)\]$/.exec(s);
    if (optional) { params[optional[1]] = parts.slice(i); return params; }
    if (rest) { if (p === undefined) return null; params[rest[1]] = parts.slice(i); return params; }
    if (p === undefined) return null;
    if (dyn) params[dyn[1]] = p;
    else if (s !== p) return null;
  }
  return parts.length === segs.length ? params : null;
}

// static < dynamic < catch-all: fewer brackets wins
const specificity = (file) => (file.match(/\[\.\.\./g) || []).length * 10 + (file.match(/\[/g) || []).length;

function matchRoute(files, pathname) {
  const hits = files.map((file) => ({ file, params: matchOne(file, pathname) })).filter((h) => h.params);
  hits.sort((a, b) => specificity(a.file) - specificity(b.file));
  return hits[0] ?? null;
}

for (const url of ["/", "/about", "/blog/new", "/blog/hello", "/docs", "/docs/guide/install"]) {
  const hit = matchRoute(files, url);
  console.log(url, "→", hit ? `${hit.file} ${JSON.stringify(hit.params)}` : "404");
}

Parallel routes

Render several independent pages in the same layout at once. Each slot is a folder prefixed with @; the layout receives each slot as a prop alongside children (which is the implicit @children slot).

app/dashboard/
  layout.tsx          # receives { children, team, analytics }
  page.tsx
  @team/
    page.tsx
    default.tsx       # what to render for this slot when the URL doesn't match it
  @analytics/
    page.tsx
    default.tsx
    settings/page.tsx # /dashboard/settings fills @analytics; @team falls back to default.tsx
// app/dashboard/layout.tsx
export default function DashboardLayout(
  { children, team, analytics }: { children: React.ReactNode; team: React.ReactNode; analytics: React.ReactNode }
) {
  return (
    <div>
      {children}
      <aside>{team}</aside>
      <aside>{analytics}</aside>
    </div>
  );
}

Each slot has its own loading.tsx / error.tsx and streams independently — a dashboard whose widgets fail or load separately. On a soft navigation an unmatched slot keeps showing what it had; on a hard navigation (reload, direct URL) Next has no previous state and renders the slot's default.tsx — with none, the whole page 404s.

Intercepting routes

Override what a URL renders within the current layout context, without leaving the page. Prefix the segment with (.) (same level), (..) (one segment up), (..)(..) (two up), or (...) (from app/ root). The levels count route segments, not folders — route groups and @slots don't count.

app/feed/
  layout.tsx            # renders {children} and {modal}
  page.tsx
  @modal/
    default.tsx         # null — no modal unless intercepted
    (.)photo/[id]/
      page.tsx          # intercepts /photo/[id] when navigated to from /feed
app/photo/
  [id]/page.tsx         # direct URL, refresh, or shared link → the full page

The modal-with-shareable-URL pattern: clicking a photo in the feed opens an overlay and the URL becomes /photo/42; reloading that URL shows the standalone photo page. Interception only happens on client-side navigation — which is why it is always paired with a parallel slot that has a default.tsx returning null.

Static params for dynamic segments

generateStaticParams lists the dynamic values to prerender at build time — SSG for [slug] routes. Values not in the list are rendered on first request and cached (dynamicParams = true, the default); set export const dynamicParams = false to 404 them instead.

// app/blog/[slug]/page.tsx
export async function generateStaticParams() {
  const posts = await db.posts.findMany({ select: { slug: true } });
  return posts.map((p) => ({ slug: p.slug }));   // → /blog/hello-world, /blog/getting-started, … at build
}

export default async function Post({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;                  // same Promise shape whether prerendered or on-demand
  const post = await db.posts.findBySlug(slug);
  if (!post) notFound();                          // → nearest not-found.tsx, 404 status
  return <article>{post.body}</article>;
}

Metadata API

Export metadata (static) or generateMetadata (per request, runs on the server) from any page.tsx or layout.tsx; nested exports merge, leaf wins. Next renders the <head> from it — never hand-write <title> in a layout.

// Static — same for every visitor
import type { Metadata } from "next";
export const metadata: Metadata = {
  title: { template: "%s · My Blog", default: "My Blog" },   // children fill %s
  description: "Thoughts on software.",
};

// Dynamic — per request; params is a Promise here too
export async function generateMetadata(
  { params }: { params: Promise<{ slug: string }> }
): Promise<Metadata> {
  const { slug } = await params;
  const post = await db.posts.findBySlug(slug);    // deduped with the page's own fetch via React cache()
  return {
    title: post.title,
    openGraph: { images: [post.ogImage] },
  };
}
Code review
  • Per-page logic in a layout. Page-view analytics, scroll reset, "enter" animation in layout.tsx run once and never again, because layouts persist across navigation. Use template.tsx, or key an effect on usePathname().
  • error.tsx expected to catch its own layout. The boundary sits inside the layout; a throw in app/x/layout.tsx reaches app/error.tsx. Root-layout errors need global-error.tsx, which must render its own <html>.
  • Parallel route without default.tsx. Works in development clicks, 404s on reload and on every shared link. Every @slot gets a default.tsx, even if it returns null.
  • params / searchParams used synchronously. Next 15 made them Promises; params.slug logs a deprecation warning today and breaks in the next major. await params — and run npx @next/codemod@canary next-async-request-api on old code.
  • useSearchParams() in a client component with no <Suspense> above it. On a statically rendered route this forces the whole page up to the nearest boundary to render on the client (a "bail out"); the build warns. Wrap the component in <Suspense>, or read searchParams in the page on the server.
  • generateStaticParams returning the whole table. 50 000 product pages at build time. Return the hot set; let dynamicParams render the long tail on demand.
  • route.ts next to page.tsx in the same directory is a build error — move handlers under api/ or a sibling segment.

Recall
Which file makes a URL publicly reachable in the App Router, and what can it not share a directory with?
page.tsx (or route.ts for handlers). A directory with only layout.tsx is a wrapper, not a route. page.tsx and route.ts in the same segment is a build error.
In what order do a segment's special files nest around the page?
layout → template → error (boundary) → loading (Suspense) → not-found → page. Ancestor directories nest outside, root first.
layout.tsx vs template.tsx — the one-line difference?
A layout persists across navigations (state kept, effects don't re-run); a template re-mounts on every navigation. Same position in the tree.
Why must error.tsx be "use client", and which error does it not catch?
Error boundaries need client lifecycle. It wraps the page, not its own segment's layout — a throw in that layout goes to the parent's error.tsx; root-layout errors need global-error.tsx.
Both app/blog/new/page.tsx and app/blog/[slug]/page.tsx exist. Which one serves /blog/new?
The static segment: new/page.tsx. Precedence is static > [dynamic] > [...catchAll], independent of any file order.
What does (marketing)/about/page.tsx serve, and what is the group for?
/about — the group is invisible in the URL. It exists so (marketing)/layout.tsx can wrap some routes with a different shell under the same root layout.
[...path] vs [[...path]] for /docs?
[...path] needs at least one segment, so /docs is 404; [[...path]] is optional and matches /docs with path: [].
A parallel-route slot has no default.tsx. What happens on reload of a URL the slot does not match?
404 for the whole route. Soft navigation keeps the slot's previous content; a hard navigation has none, so Next needs default.tsx (often returning null).
How are params and searchParams typed in a Next 15 page, and who receives searchParams?
Both are Promises — const { slug } = await params. Only pages get searchParams; layouts get params only, because a persistent layout cannot depend on per-navigation query strings.
