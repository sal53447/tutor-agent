The Rendering Spectrum

A plain React app renders in the browser (CSR): blank HTML, then a JS bundle, then a data fetch, then pixels. Next.js exists to move that work to the server — per request (SSR), at build time (SSG), on a schedule (ISR), or progressively over one HTTP response (streaming). The App Router decides this per route, and 5b–5d assume you can read a route and say where and when its HTML is produced.

The spectrum

ModeHTML generatedWhen to use
CSR (client-side)Browser runs JS, React builds DOMApp-like UIs behind login. Poor SEO, slow first paint, three round-trips before content.
SSR (server-side)Server renders HTML per request, client hydratesDynamic, personalized pages. Good SEO and first paint; server-bound.
SSG (static)HTML built once at build timeMarketing, blogs, docs. Served from CDN; cannot be per-user.
ISR (incremental static)SSG, regenerated in the background after revalidate secondsMostly-static content that drifts: product pages, listings.
StreamingHTML flushed in chunks as <Suspense> boundaries resolveDefault for dynamic routes. Shell paints immediately; slow data arrives later on the same response.

These are not framework "modes" you pick in a config. In the App Router every route is static unless something in it reads the request, and a dynamic route streams whenever a <Suspense> boundary (or loading.tsx) sits above slow data. A marketing page and a per-user dashboard live in the same app with different answers.

Python bridge

A Django view returning render(request, "page.html", ctx) is SSR, full stop: one HTML response, no JavaScript involved, every request re-renders. Next's SSR is that plus a second phase — the component JS is shipped and React hydrates the server HTML so the same components become interactive. SSG is what you get from caching a Django template render at deploy time (django-distill, a static export); ISR is that cache with a TTL and background refresh. Streaming is StreamingHttpResponse, except you never write the generator: React flushes the template at each <Suspense> boundary. Jinja template partials ({% include %}) map onto Server Components — rendered once on the server, output only — while anything that needs onclick is a Client Component, the piece Jinja never had.

Streaming — chunked HTML around <Suspense>

Classic SSR sends nothing until the whole tree has rendered, so one slow await holds the entire page. Streaming uses chunked transfer encoding: React flushes the shell — everything outside suspended boundaries, with fallbacks in the holes — immediately, then sends one more HTML chunk per boundary as its data resolves. Same connection, no extra round-trip, no client JS needed for the initial paint; each chunk carries a tiny inline script that swaps the fallback for the content.

// app/dashboard/page.tsx
import { Suspense } from "react";
import { RecentOrders } from "./recent-orders"; // async Server Component — awaits the DB

export default function Dashboard() {
  return (
    <main>
      <h1>Dashboard</h1>
      <Suspense fallback={<p>Loading orders…</p>}>
        <RecentOrders />   {/* streams in when its await resolves */}
      </Suspense>
    </main>
  );
}

A loading.tsx file (5b) is the same mechanism at segment level: Next wraps that segment's page in <Suspense fallback={<Loading />}> for you. Boundaries are independent: two slow siblings each in their own <Suspense> arrive in resolve order, not tree order.

Gotcha

An await that is not under a boundary blocks the shell. The usual offender is a layout that awaits the session: every page below it waits, and streaming buys nothing. Either wrap the slow subtree in <Suspense> or push the await down into the component that needs the data.

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function render(tree) {
  const streaming = [];
  for (const child of tree.children) {
    if (child.suspense) streaming.push(sleep(child.delay).then(() => console.log("flush chunk:", child.name)));
    else if (child.delay) await sleep(child.delay);     // no boundary → blocks the shell
  }
  console.log("flush shell (fallbacks in the holes)");
  await Promise.all(streaming);
  console.log("response closed");
}

Exercise

This renderer behaves like classic SSR: it waits for every child, then sends everything. Make it stream. Contract: render(tree, out) pushes "shell" into out as soon as every non-suspended child is ready; each suspended child pushes "chunk: <name>" when its own delay resolves; the returned promise settles when the last chunk is out. Tests check that the shell is first, that chunks arrive in resolve order, and that a suspended child never delays the shell (a non-suspended one still does).

// --- helper (leave as is)

// --- fix this
async function render(tree, out) {
  const chunks = [];
  for (const child of tree.children) {
    if (child.delay) await sleep(child.delay);
    if (child.suspense) chunks.push(`chunk: ${child.name}`);
  }
  out.push("shell", ...chunks);
  return out;
}

Static or dynamic — how Next decides per route

There is no "SSG mode" switch. At build time Next renders every route it can; a route becomes dynamic (rendered per request) only if rendering it reads the request: cookies(), headers(), connection(), the searchParams prop, or a fetch with cache: "no-store". Everything else is static — built once, served from the CDN. A static route with export const revalidate = N is ISR: served stale, regenerated in the background at most every N seconds.

// app/blog/[slug]/page.tsx — static: nothing here reads the request
export default async function Post({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;         // Next 15: params is a Promise. Awaiting it does NOT make the route dynamic.
  const post = await getPost(slug);      // slugs from generateStaticParams are built; others render on first request, then cached
  return <article>{post.body}</article>;
}
export const revalidate = 300;           // ISR: regenerate at most every 5 min

// app/account/page.tsx — dynamic: cookies() reads the request
import { cookies } from "next/headers";
export default async function Account({ searchParams }: { searchParams: Promise<{ tab?: string }> }) {
  const session = (await cookies()).get("session")?.value;   // Next 15: cookies() is async
  const { tab = "profile" } = await searchParams;            // reading searchParams also opts into dynamic
  return <Profile session={session} tab={tab} />;
}

// explicit overrides on any page or layout
export const dynamic = "force-dynamic";  // always per request, even if nothing reads the request
export const dynamic = "force-static";   // build it; cookies()/headers() return empty values
Gotcha

Dynamic-ness is inherited downward. cookies() in app/layout.tsx makes every route in the app dynamic, including the marketing pages that could have been static. Read request data in the leaf that needs it.

Mechanism

Reading the request (cookies(), headers(), searchParams, connection(), force-dynamic) is the only thing that makes a route dynamic; revalidate only matters once it is not. Streaming is orthogonal — it is how a dynamic render is delivered.

Partial Prerendering (PPR)

PPR collapses the static/dynamic choice to the boundary level: the parts of a route outside <Suspense> are prerendered into a static shell at build time; the holes stream at request time. One route gets CDN-speed first byte and per-request content. In Next 15 it is experimental and canary-only; the opt-in is per route.

// next.config.ts
export default {
  experimental: { ppr: "incremental" },   // or true for every route
};

// app/product/[slug]/page.tsx
export const experimental_ppr = true;     // opt this route in

import { Suspense } from "react";
import { StaticProductInfo } from "./static-info";      // rendered at build
import { DynamicStockLevel } from "./dynamic-stock";    // reads cookies() → streamed at request

export default function ProductPage() {
  return (
    <>
      <StaticProductInfo />
      <Suspense fallback={<span>Checking stock…</span>}>
        <DynamicStockLevel />
      </Suspense>
    </>
  );
}
Rule of thumb

Wrap each independently dynamic piece in its own <Suspense>. Without PPR, one cookies() call makes the whole route dynamic; with PPR, only that hole is. The same boundaries you add for streaming are the ones PPR prerenders around — write them now, PPR is a config flag later.

Code review
  • One <Suspense> around the whole page. The shell is now an empty fallback; you have reinvented CSR's spinner with extra server cost. One boundary per independently slow subtree.
  • await in a layout. const session = await getSession() in app/(app)/layout.tsx puts every page under it behind that await. Move the read into the components that need it, or wrap them.
  • cookies() / headers() in the root layout (theme, locale). Every route in the app turns dynamic; the marketing pages stop being CDN hits. Read in the leaf, or do it in middleware and pass a header (5f).
  • export const dynamic = "force-dynamic" as the fix for stale data. It throws away static serving for the route; the real fix is targeted revalidation (5d).
  • Slow generateMetadata. <head> must be complete before the shell can flush, so a slow metadata query delays first byte for the whole page (Next 15.2+ streams metadata for non-bot user agents, which softens but does not remove this).
  • Hydration mismatch. Rendering Date.now(), window.innerWidth, or a locale-formatted number produces different HTML on server and client; React 19 reports a recoverable error and re-renders the subtree on the client — a visible flash and wasted work. Client-only values go in useEffect/useSyncExternalStore, or the component gets suppressHydrationWarning for a timestamp.

Recall
Mechanically, what is the difference between SSR and streaming SSR?
SSR buffers the full HTML and sends one response. Streaming sends the shell (with Suspense fallbacks in the holes) as soon as it is ready, then appends one HTML chunk per boundary over the same chunked response as each resolves.
What makes an App Router route dynamic instead of static?
Reading the request during render: cookies(), headers(), connection(), the searchParams prop, a fetch with cache: "no-store" — or export const dynamic = "force-dynamic". Awaiting params alone does not.
What does export const revalidate = 60 do on a static route?
Makes it ISR: the built HTML is served (even if stale) and regenerated in the background at most once every 60 seconds. It has no effect on a dynamic route.
What is hydration, and what does the user see before it finishes?
React runs the Client Components in the browser and attaches event handlers to the server-rendered DOM instead of creating it. Before it finishes the page is painted but inert — clicks on JS-driven controls do nothing.
PPR serves a page in two stages — what are they and where does each run?
A static shell prerendered at build and served from the CDN; then the <Suspense> holes rendered at request time on the origin and streamed into it. Next 15: experimental, canary only, experimental_ppr = true per route.

A product page: hero image and name are the same for everyone; the "in stock" badge hits a live inventory API. Which strategy?
Static (or ISR) page with the badge in its own <Suspense> boundary — PPR when available: static shell from the CDN, stock streamed per request.
Why is const session = await getSession() in a layout a streaming problem?
Nothing in the layout is under a Suspense boundary, so the await sits on the shell's critical path: every page beneath waits for the session before the first byte is sent.
