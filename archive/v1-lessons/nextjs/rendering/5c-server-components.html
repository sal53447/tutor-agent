React Server Components — the new mental model

RSC is the biggest React shift in a decade. Components are server by default. They render on the server, can be async, talk to your DB directly, and ship zero JS to the client (just their rendered output).

// app/users/[id]/page.tsx — a server component (default)
// params is a Promise in Next 15 — must be awaited
import { db } from "@/lib/db";

export default async function UserPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;                       // Next 15: await params
  const user = await db.users.findById(id);          // direct DB access!
  return <h1>{user.name}</h1>;
}

The client / server boundary

Interactivity (useState, useEffect, onClick) requires a Client Component. Mark it with "use client" at the top of the file. Client components can be imported into server components, but not vice versa — the boundary is one-way.

// app/like-button.tsx
"use client";
import { useState } from "react";

export function LikeButton() {
  const [liked, setLiked] = useState(false);
  return <button onClick={() => setLiked(v => !v)}>{liked ? "♥" : "♡"}</button>;
}
The key pattern

Keep the server shell as server components (fetch, render, no JS cost). Drop client components as "islands" where interactivity is needed. Pass server-fetched data to them via props. This is the opposite of a traditional SPA: by default, no JS ships.

The "use client" waterfall problem

"use client" is a file-level boundary. Every module that a client component imports also becomes part of the client bundle — recursively. One misplaced directive pulls everything below it into the browser.

Rule

Never put "use client" on a file that imports DB clients, ORMs, secret env vars, or any heavy server-side library. If that file is ever imported by a client component, those libraries ship to the browser and your secrets leak into the bundle.

// BAD — "use client" placed too high, pulls db into the browser bundle
"use client";
import { db } from "@/lib/db";         // DB client now in the browser!
import { useState } from "react";

export function UserCard({ id }) {
  const [open, setOpen] = useState(false);
  // db import was pointless here anyway — can't call it in the browser
}
// GOOD — keep the boundary as narrow as possible
// app/user-card.tsx (server component — no directive)
import { db } from "@/lib/db";
import { ExpandButton } from "./expand-button"; // only this is "use client"

export async function UserCard({ id }) {
  const user = await db.users.findById(id);
  return (
    <div>
      <h2>{user.name}</h2>
      <ExpandButton label="Details" />  {/* client island */}
    </div>
  );
}

Server component as children — the escape hatch

A client component cannot directly import a server component (the import would pull it into the client bundle). But it can receive one as children or a prop — because the server component was already rendered by a server component parent before it reaches the client.

// BAD — client component importing a server component directly
"use client";
import { UserData } from "./user-data";  // server component — BREAKS

export function Shell() {
  return <div><UserData /></div>;       // Next throws a build error
}
// GOOD — server component passes SC as children to the client component
// app/page.tsx  (server component)
import { Shell } from "./shell";           // client component
import { UserData } from "./user-data";   // server component

export default function Page() {
  return (
    <Shell>
      <UserData />  {/* rendered server-side, passed as an opaque prop */}
    </Shell>
  );
}

// app/shell.tsx
"use client";
export function Shell({ children }) {
  // children is already server-rendered RSC output — no client bundle cost
  return <div className="shell">{children}</div>;
}

Server action interop hooks

Two React 19 hooks bridge client components and server actions (covered in depth in 4e/4i):

  • useFormStatus() — reads the pending state of the nearest parent <form> action. Use inside a submit button to show a spinner without lifting state.
  • useOptimistic(state, updateFn) — applies a local optimistic update immediately, then settles once the server action resolves or rejects.
// Spinner button — reads form's pending state from server action
"use client";
import { useFormStatus } from "react-dom";

export function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? "Saving…" : "Save"}</button>;
}

Serialization rules

  • Props crossing from server → client must be serializable (JSON-like). No functions, classes, Symbols. Dates work via Next's serializer.
  • children is special — you can pass JSX from a server component into a client component. The server-rendered tree is embedded in the client's render.
Python bridge

In Django, a view function is always "server-side" — there's no concept of the same function running in the browser. RSC makes this explicit for the React world: most components should stay server-side, touching the DB and shipping zero JS. Only reach for "use client" when you genuinely need browser APIs or local state — just as you'd only add Django's JS-heavy frontend tooling when the template engine isn't enough.

Self-check
  1. You add "use client" to a component that imports your Prisma client. What breaks?
  2. You have a Modal client component that needs to display server-fetched content. How do you pass that content without breaking the server/client boundary?
  3. What is useFormStatus for, and why must it live in a client component?

Expected answers: (1) Prisma ships into the browser bundle — build may fail or secrets/DB credentials leak. (2) Render the server component in a server parent and pass it as children to the Modal. (3) It reads the pending state of the enclosing form's server action; it requires "use client" because it uses React's client-side hook system.
