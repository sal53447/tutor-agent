What TypeScript Actually Is

TypeScript is a static type checker that compiles to plain JavaScript. Every later lesson — generics (2c), type-level tools (2d), typed React props (2g), typed Express handlers (2h) — rests on one fact from this one: types exist only before the build. Get the erasure model right and the rest of the topic is vocabulary.

Types are erased at build time

// TS source:
function add(a: number, b: number): number { return a + b; }

// After compilation — types gone:
function add(a, b) { return a + b; }

Two consequences. First, types are a design tool, not a runtime guarantee. JSON.parse, req.body, localStorage, a database row — anything that enters from outside has whatever shape it has, and an annotation on the receiving variable changes nothing. Validate external data at runtime (3d covers zod). Second, adoption is incremental. Rename a .js to .ts, fix errors, move on; the emitted JS is the same program.

Not everything erases

enum, namespace, constructor parameter properties (constructor(private x: number)) and import x = require() emit runtime code. TS 5.8's --erasableSyntaxOnly rejects them, and recent Node (23.6+ / 22.18+) runs .ts files directly by stripping types — it refuses the same constructs. Treat "annotations only" as the modern baseline.

Step through

Run your first compile

npm install -D typescript
npx tsc --init          # generates tsconfig.json
echo 'const x: number = "oops";' > hello.ts
npx tsc hello.ts

The compiler prints:

hello.ts:1:7 - error TS2322: Type 'string' is not assignable to type 'number'.

1 const x: number = "oops";
        ~

Fix it (const x: number = 42;), run npx tsc hello.ts again — it emits hello.js with types stripped. That .js file is what Node (or the browser) actually runs.

Workflow

In real projects you rarely invoke tsc for output — Vite, Next.js, tsx, or Node's own type stripping run the code. Those tools don't type-check. The check is a separate command, tsc --noEmit, and it belongs in CI and in the editor (the TS language server is what powers the red squiggles).

Python bridge

Think of Python's type hints + mypy, but enforced and with much deeper inference. Python hints are often aspirational; TS is where teams actually rely on the types. The cultural adoption is more like Rust than like Python annotations. The erasure story is the same, though: def f(x: int) accepts a str at runtime just as function f(x: number) does.

Structural typing — the mental model

TS is structural: a value is assignable to a type if its shape has every required member with a compatible type, regardless of what the value was declared as. Python classes, Java and C# are nominal — the name (or the inheritance chain) decides.

type Named = { name: string };
function greet(x: Named) { return "hi " + x.name; }

const user = { name: "P", age: 30 };
greet(user);                     // OK — has name: string; extra age is fine
greet({ name: "P" });            // OK
greet({ age: 30 });              // Error TS2345 — name is missing
Excess property checks

greet({ name: "P", age: 30 }) — the same object as user, but as a fresh object literal in a typed position — is an error (TS2353 "Object literal may only specify known properties"). That is a typo lint for literals, not a nominal check: assign to a variable first and it passes. Expect it when building options bags inline.

Mechanism

Assignability asks one question per required member of the target: is it present with a compatible type? Extra members never matter — except on a fresh literal, where they're flagged as probable typos.

Python bridge

Python classes are nominal: isinstance(x, Named) needs inheritance. typing.Protocol opts one type into structural matching — TS has no opt-in, every object type behaves like a Protocol. What mypy calls "compatible with protocol Named" is what TS calls "assignable to Named", and both ignore extra attributes. The flip side: Python's NewType("UserId", str) is a one-liner for a nominal wrapper; TS needs a branded type (2f) to stop userId and orderId — both string — from being interchangeable.

Code review
  • JSON.parse(x) as T / (await res.json()) as T. A cast is erased; the data is unchecked. Validate at every boundary — HTTP body, env vars, storage, DB rows — with a schema (zod, 3d) and derive the type from it with z.infer.
  • any leaking in. JSON.parse, req.body, untyped libraries. Turn on strict (which includes noImplicitAny and useUnknownInCatchVariables) and the @typescript-eslint/no-unsafe-* rules so any can't spread silently.
  • Green bundler build ≠ type-checked. esbuild, SWC, Vite, Next's compiler and Node's type stripping only erase. CI must run tsc --noEmit (or the framework's typecheck step) or type errors ship.
  • // @ts-ignore. Prefer // @ts-expect-error with a reason: it fails the build once the error goes away, so suppressions don't outlive their cause.
  • Non-erasable syntax. enum, namespace, parameter properties emit code and break under type stripping; --erasableSyntaxOnly (TS 5.8) makes the compiler say so.
  • Structural confusion of ids. userId: string and orderId: string are interchangeable to the checker. Brand them (2f) when a mix-up would be a production incident, not a typo.

Recall
What does const u: User = JSON.parse('{"id":"42"}') do at runtime, and why does it compile?
It assigns { id: "42" } unchanged — the annotation is erased. It compiles because JSON.parse returns any, which is assignable to everything.
What does this print? 
const u: { id: number } = JSON.parse('{"id":"42"}');
console.log(typeof u.id, u.id === 42);
string false. Types are deleted before the code runs; u.id is whatever the JSON held.
Which TS constructs are not erasable, and which compiler flag rejects them?
enum, namespace (with values), constructor parameter properties, import x = require(). --erasableSyntaxOnly (TS 5.8) — matching what Node's type stripping can run.
Does a green Vite / Next / esbuild build mean the code type-checks?
No. Those tools only strip types. Type-checking is tsc --noEmit (or the editor's language server) and must run separately, typically in CI.
Structural typing in one sentence — and the one case where an extra property is an error.
A value is assignable to a type if it has every required member with a compatible type; extras are ignored. Exception: a fresh object literal in a typed position gets an excess-property check (TS2353).
Python equivalent of TS's default assignability rule?
typing.Protocol — structural matching — except TS applies it to every object type without opting in. NewType has no direct TS equivalent; use branded types.
What is a type guard, and what part of it survives compilation?
A function returning boolean annotated x is T. The boolean logic survives and runs; the x is T annotation is erased and only tells the checker to narrow after a true result.
