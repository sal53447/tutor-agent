Generics in Practice

Generics parametrize types. Like Python's TypeVar, but the inference is much stronger.

Why not any[]?

// With any[]: TS can't help you — return type is any
function firstBad(arr: any[]): any { return arr[0]; }
const x = firstBad([1, 2, 3]);
x.toUpperCase();   // no error at compile time — will blow up at runtime

// With generics: return type tracks the input type
function first<T>(arr: T[]): T | undefined { return arr[0]; }
const y = first([1, 2, 3]);   // y: number | undefined
y?.toUpperCase();              // Error: toUpperCase doesn't exist on number

The generic version is not harder to write — it just makes the compiler track the type through the function rather than throw it away.

function first<T>(arr: T[]): T | undefined { return arr[0]; }
first([1,2,3]);          // T = number, return: number | undefined
first(["a", "b"]);       // T = string

// Multiple type parameters — TS infers both from usage
function zip<A, B>(as: A[], bs: B[]): [A, B][] {
  return as.map((a, i) => [a, bs[i]] as [A, B]);
}
zip([1, 2], ["a", "b"]);   // [number, string][]
zip(["x"], [true]);         // [string, boolean][]

// Constraints
// keyof T is the union of all keys of T — covered in 2d.
function pluck<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
pluck({ name: "P", age: 30 }, "age");  // number
// pluck({ name: "P" }, "missing");    // Error — "missing" not a key

// Defaults
type Result<T, E = Error> = { ok: true; value: T } | { ok: false; err: E };

// Generic components (React)
function List<T>(props: { items: T[]; render: (x: T) => React.ReactNode }) {
  return <ul>{props.items.map((x, i) => <li key={i}>{props.render(x)}</li>)}</ul>;
}
When NOT to use generics
// Bad — T isn't constrained or linked to anything; unknown does the job
function wrap<T>(x: T): { value: T } { return { value: x }; }

// Fine for single-caller code, but if nothing calls wrap() with a
// specific type the generic buys you nothing. For a one-shot wrapper:
function wrap(x: unknown): { value: unknown } { return { value: x }; }

// Good — T is load-bearing: return type is tied to input type
function identity<T>(x: T): T { return x; }
const n = identity(42);   // n: 42 (literal), not unknown

Generics add complexity. Only reach for them when the caller's type must flow through — not just to "avoid any".

When to reach for generics
  • You're writing a library-style function (reusable utility, container) and the caller's type should flow through.
  • You're linking two things (a key and its value type, a request and its response type).
  • Don't use generics for "any object"; use unknown or Record<string, unknown>.
