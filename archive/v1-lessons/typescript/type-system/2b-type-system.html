The Type System

TS types are sets of values, and the compiler's job is to track which set a variable is in at every line. Unions widen the set, checks narrow it, unknown and never are the top and bottom. Everything from here on — generics (2c), mapped and conditional types (2d), exhaustive matching (2f), typed req.body (2h) — is built on narrowing a union down to the one case you can act on.

The building blocks

// Primitives
let s: string; let n: number; let b: boolean;
let u: undefined; let nl: null; let big: bigint; let sym: symbol;

// Literal types — a single value is a type
type Direction = "up" | "down" | "left" | "right";
type HTTPMethod = "GET" | "POST" | "PUT" | "DELETE";

// Unions — either
type ID = string | number;

// Intersections — both
type Named = { name: string };
type Aged  = { age: number };
type Person = Named & Aged;    // { name: string; age: number }

// Tuples — fixed-length, positionally typed arrays
type Point = [number, number];
type Pair<T, U> = [T, U];

Literal unions do the work enum does in other languages, with no runtime cost (2b-08). const x = "GET" infers the literal type "GET"; let x = "GET" widens to string.

Discriminated unions — the workhorse

A union of object types that share one literal-typed field (the discriminant, conventionally kind or type). Checking that field tells the compiler exactly which member you hold.

type Shape =
  | { kind: "circle"; r: number }
  | { kind: "square"; side: number };

function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.r ** 2;   // s: { kind: "circle"; r: number }
    case "square": return s.side ** 2;          // s: { kind: "square"; side: number }
    default: return assertNever(s);              // s: never — every case handled
  }
}
function assertNever(x: never): never {
  throw new Error("unhandled variant: " + JSON.stringify(x));
}

Add a third member to Shape and the default stops compiling: s is no longer never there. That is the whole value of the pattern — the compiler finds every switch you forgot to update. 2f goes deeper on exhaustiveness.

Narrowing — how TS tracks type flow

TypeScript performs control flow analysis: every check you write narrows the type of the checked variable inside that branch. No casts; you check, and the compiler knows.

// typeof narrowing
function format(x: string | number) {
  if (typeof x === "string") return x.toUpperCase();  // x: string here
  return x.toFixed(2);                                // x: number here
}

// instanceof narrowing
function handle(err: Date | Error) {
  if (err instanceof Error) return err.message;       // err: Error
  return err.toISOString();                           // err: Date
}

// in narrowing — property presence
type Circle = { kind: "circle"; r: number };
type Rect   = { kind: "rect"; w: number; h: number };
function area2(s: Circle | Rect) {
  if ("r" in s) return Math.PI * s.r ** 2;           // s: Circle
  return s.w * s.h;                                   // s: Rect
}

// Truthiness narrowing
function greet(name: string | null) {
  if (!name) return "Hello, stranger";
  return `Hello, ${name}`;                            // name: string (null excluded)
}

// Equality narrowing + early return: the rest of the function is narrowed
function len(x: string | null) {
  if (x === null) return 0;
  return x.length;                                    // x: string
}
Truthiness narrows too much

if (!name) excludes null — and also "". if (!count) excludes 0. When the empty value is legitimate, narrow on === null / == null instead.

Since TS 5.5, a function whose body is a narrowing check gets an inferred type predicate — no x is string annotation needed:

const isString = (x: unknown) => typeof x === "string";   // inferred: (x: unknown) => x is string
const strs = ["a", 1, "b", null].filter(isString);          // string[]
const nonNull = [1, null, 2].filter(x => x !== null);       // number[] (also 5.5+)
Mechanism

Each check splits the union into the members that pass and the members that don't; the false branch is narrowed just as much as the true one. After an early return, the rest of the function lives on the false edge.

Python bridge

mypy narrows on isinstance(x, str), x is None, and match with class patterns; TS narrows on typeof, instanceof, in, === and a switch on a discriminant. The mapping of shapes: Union[A, B] / A | B is the same idea; a Literal["GET", "POST"] is a TS literal union; a discriminated union is a match over TypedDicts with a Literal tag field. The difference is habit, not capability: Python code reaches for class hierarchies where TS code reaches for a tagged union plus a switch — and assertNever is typing.assert_never, which Python added in 3.11 for exactly this reason.

any, unknown, and never

// any — disables type checking. Poisons anything it touches. Avoid.
function bad(x: any) { return x.whatever(); }   // no error — TS gave up

// unknown — safe top type. Every value is assignable TO it;
// it is assignable to nothing until you narrow.
function parse(raw: unknown) {
  if (typeof raw === "string") return raw.toUpperCase();  // ok after check
  throw new Error("not a string");
}

// never — the empty type. Assignable to everything; nothing is assignable to it.
// A value of type never means "this code path is unreachable" —
// the default branch of an exhaustive switch (2b-07), a function that always throws.
function fail(msg: string): never { throw new Error(msg); }
Rule

When a function can receive "anything", reach for unknown, not any. unknown forces you to narrow once, at the boundary; any silently bypasses every check downstream — and every value derived from an any is any too.

Mechanism

Arrows mean "is assignable to". Narrowing walks down this lattice; widening walks up. never is what's left when every member of a union has been eliminated; any short-circuits the whole picture in both directions.

Function types and type aliases

// Function type alias
type Handler = (req: Request, res: Response) => void;
type Predicate<T> = (item: T) => boolean;
type Transform<A, B> = (input: A) => B;

// Inline function type
function run(fn: (x: number) => string) { return fn(42); }

// Type aliases are compile-time only — erased at runtime.
// typeof SomeTypeAlias does NOT exist in JS output.
type UserId = string;   // gone at runtime — purely a TS construct

Parameters are checked bivariantly for methods and contravariantly for function-typed properties under strictFunctionTypes: a callback that accepts less than the declared parameter type is rejected, one that accepts more is fine. Return types are covariant. In practice: declare callbacks with the property syntax (on: (e: Event) => void) rather than method syntax to get the strict check.

Interfaces vs type aliases

  • Type aliases (type) — any shape: unions, tuples, mapped and conditional types, primitives. Preferred default.
  • Interfaces — object shapes only. Open to declaration merging, which is how you augment library types (declare module "express" { interface Request { user?: User } }). Marginally faster to check in very large codebases because they're cached by name.

Rule of thumb: interface for public API contracts and anything consumers may need to augment; type for everything else. Pick one per codebase and lint it (@typescript-eslint/consistent-type-definitions).

enum vs as const

Avoid

enum. It is one of the few TS constructs that emits runtime code (2a): an object with reverse mappings for numeric members, built by an IIFE that bundlers can't tree-shake. It is also rejected by Node's type stripping and by --erasableSyntaxOnly (TS 5.8). Use literal unions, or an as const object when you need the values at runtime.

// Instead of enum:
const Role = { Admin: "admin", User: "user" } as const;
type Role = typeof Role[keyof typeof Role];  // "admin" | "user"

// Both namespaces at once: Role the value (runtime object), Role the type (literal union).
function can(role: Role) { return role === Role.Admin; }

Code review
  • as to reach a union member. A cast to access s.r means the union has no usable discriminant, or the author skipped narrowing. Add a kind field and switch on it; casts are where NaN and undefined is not a function come from.
  • Non-exhaustive switch without assertNever. The next variant added to the union silently falls through. default: assertNever(x) plus @typescript-eslint/switch-exhaustiveness-check.
  • any at a boundary. function handle(payload: any) turns off checking for every line that touches payload. Take unknown, narrow once (or parse with a schema), and the rest of the function is typed. @typescript-eslint/no-explicit-any.
  • Truthiness narrowing on strings and numbers. if (!value) treats "" and 0 as missing. Use == null when those are real values.
  • Literal unions without a runtime list. A type like "GET" | "POST" can't validate input. Keep one as const array and derive the type from it (2b-15), so the guard and the type can't drift.
  • enum in new code. Emits code, breaks type stripping, numeric enums accept any number. Literal union or as const object.

Recall
What is a discriminated union, and what does default: assertNever(s) buy you?
A union of object types sharing a literal-typed field (kind). Switching on it narrows each branch. assertNever(x: never) fails to compile when a variant is unhandled and throws at runtime for unexpected data.
Name five narrowing forms TS understands.
typeof, instanceof, in, equality (=== null), truthiness, a switch on a discriminant — plus user-defined type guards (x is T, inferred since TS 5.5).
What does this print? 
function greet(name: string | null) {
  if (!name) return "stranger";
  return name.toUpperCase();
}
console.log(greet(""), greet("ada"));
stranger ADA. Truthiness narrowing excludes null and also ""; use === null when the empty string is a real value.
unknown vs any — the one-sentence difference.
Both accept every value; unknown can't be used until narrowed, any can be used as anything and turns off checking for everything derived from it.
Where does never sit in the assignability lattice, and when does a value have that type?
At the bottom: assignable to everything, nothing assignable to it. A variable is never when every union member has been narrowed away (exhausted switch) or a function can't return (always throws).
How do you give a literal union like "GET" | "POST" a runtime check?
One as const array (METHODS), the type as typeof METHODS[number], and a guard typeof x === "string" && (METHODS as readonly string[]).includes(x).
Why avoid enum, and what replaces it?
It emits runtime code (an IIFE with reverse mappings), isn't tree-shakeable, and breaks under type stripping / --erasableSyntaxOnly. Use a literal union, or an as const object with typeof Role[keyof typeof Role].
When must you use interface instead of type?
When the shape needs declaration merging — augmenting a library's types (declare module "express" { interface Request { … } }). Otherwise it's a consistency choice.
