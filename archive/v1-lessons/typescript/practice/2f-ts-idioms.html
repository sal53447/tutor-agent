TS Idioms

The type system of 2b–2d is static; the program it describes runs on untyped data. Every idiom here is about the boundary between the two: how a value of unknown shape becomes a typed one (narrowing), when that step is a real check (typeof, in, type guards, assertion functions) versus a promise you make to the compiler (as), and how to make the compiler prove you handled every case (never). 2g applies these to props and reducers; 2h puts a schema parser at the boundary so you rarely write the guards by hand.

any vs unknown

  • any — opts out of type checking. Anything is assignable to it and it is assignable to anything, so it spreads through inferred types silently. Avoid.
  • unknown — the safe top type. Anything is assignable to it, but it is assignable to nothing else: you must narrow before use. Prefer this for JSON.parse results, catch (e), event payloads, anything from outside the program.
function parse(raw: unknown) {
  if (typeof raw === "string") return raw.toUpperCase();  // narrowed: string
  if (raw instanceof Error) return raw.message;           // narrowed: Error
  throw new Error("unexpected");
}

Narrowing is control-flow analysis: inside the if, and after an early return/throw, TS tracks a smaller type for the same variable. It works on typeof, instanceof, in, equality against literals, truthiness, and the two user-defined forms below.

Mechanism

Five of the six paths out of unknown run code at runtime and narrow only where that code proved something. as is the dashed one: it compiles to nothing, so it narrows without evidence.

Python bridge

unknown ≈ object, any ≈ typing.Any — same contagion. A type guard x is Cat ≈ TypeGuard[Cat] (3.10) or the stricter TypeIs[Cat] (3.13), which also narrows the else branch like TS does. as ≈ typing.cast: zero runtime effect, pure assertion to the checker. never ≈ Never and the exhaustiveness idiom is assert_never(x) (3.11). Branded types ≈ NewType("UserId", str). No Python equivalent exists for asserts x is T — mypy narrows an inline assert isinstance(x, str), but a function that asserts does not narrow at its call site.

Type guards — custom predicates

A function returning x is Cat is a boolean function the checker trusts: in the true branch x is Cat, in the false branch the Cat member is removed from the union. The body is ordinary runtime code — and the checker does not verify that the body actually proves the predicate.

type Cat = { kind: "cat"; meows: boolean };
type Dog = { kind: "dog"; barks: boolean };

function isCat(x: Cat | Dog): x is Cat {
  return x.kind === "cat";
}

function speak(pet: Cat | Dog) {
  if (isCat(pet)) return pet.meows ? "meow" : "…";   // pet: Cat
  return pet.barks ? "woof" : "…";                     // pet: Dog
}

// Guards from unknown are where they earn their keep:
function isUser(x: unknown): x is { id: string; email: string } {
  return typeof x === "object" && x !== null
    && typeof (x as { id?: unknown }).id === "string"
    && typeof (x as { email?: unknown }).email === "string";
}
A guard can lie

function isUser(x: unknown): x is User { return typeof x === "object"; } compiles. Every object now passes as a User, and the TypeError shows up three modules away. The predicate return type is a contract you wrote; the body has to honour it.

in narrowing — discriminated unions without a kind field

When a union lacks a shared discriminant field, "key" in x narrows to the members that declare that key (required or optional). At runtime in checks key presence, including on the prototype chain — a key holding undefined or null still counts as present.

type ApiSuccess = { data: unknown };
type ApiError   = { error: string; code: number };
type ApiResult  = ApiSuccess | ApiError;

function handle(result: ApiResult) {
  if ("error" in result) {
    console.error(result.code, result.error);   // result: ApiError
  } else {
    render(result.data);                        // result: ApiSuccess
  }
}

// Also works when one branch has a field the other doesn't
type WithId    = { id: string; name: string };
type WithoutId = { name: string };
function label(x: WithId | WithoutId) {
  return "id" in x ? `#${x.id}` : x.name;        // x: WithId in the true branch
}

Assertion functions

An assertion function narrows for all code after the call. The signature asserts x is T tells the checker: if this returns normally, x is T. If it throws, the rest of the scope is unreachable for the bad case.

function assertIsString(x: unknown): asserts x is string {
  if (typeof x !== "string") throw new Error(`Expected string, got ${typeof x}`);
}

function assertDefined<T>(x: T | null | undefined, what = "value"): asserts x is T {
  if (x == null) throw new Error(`Expected ${what} to be defined`);
}

const raw: unknown = JSON.parse(input);
assertIsString(raw);
raw.toUpperCase();          // OK — raw: string from here on

const user = users.find(u => u.id === id);   // User | undefined
assertDefined(user, "user");
user.email;                 // OK — user: User
Assertion vs type guard

A type guard (x is T) is for if branches — both outcomes continue. An assertion function (asserts x is T) is for invariants — the wrong case is a bug and should throw. Reach for guards at boundaries where both shapes are legitimate, assertions where the other shape means the program is already broken.

Explicit annotation required

An assertion function must have an explicit return-type annotation; const assertDefined = (x) => { … } without : asserts x is T is an ordinary void function and narrows nothing. The same applies when you call it through a variable whose type was inferred: TS 3.7+ requires every name in the call chain to be explicitly typed.

as is a cast, not a conversion

as does not transform the value — it is erased on emit and only silences the checker. If the runtime value doesn't match, you get silent corruption later, not an error now. TS refuses a cast between types that don't overlap at all ("x" as number), which is what the as unknown as T double cast defeats. When you reach for as, ask: can I use a type guard, an assertion function, or a schema parse instead?

Exhaustiveness with never

In a switch over a discriminant, each case removes a member from the union. After every member is handled, the remaining type is never — and never is the only type assignable to a never parameter. Adding a union member later makes the default branch a compile error at the exact spot that needs a new case.

type Shape =
  | { kind: "circle"; r: number }
  | { kind: "square"; side: number }
  | { kind: "tri"; b: number; h: number };

function assertNever(x: never): never {
  throw new Error("Unhandled case: " + JSON.stringify(x));
}

function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.r ** 2;
    case "square": return s.side ** 2;
    case "tri":    return (s.b * s.h) / 2;
    default:       return assertNever(s);   // s: never here; error if a kind is missing
  }
}

The runtime throw is not redundant: data from outside (a stale client, a hand-edited row) can carry a kind the type never allowed. assertNever is both a compile-time proof and a runtime guard.

noUncheckedIndexedAccess in practice

When this flag is on (recommended — see 2e), indexing an array or a Record<string, T> returns T | undefined. This forces the empty-array and missing-key cases into the code that reads them.

const items = ["a", "b", "c"];

const first = items[0];           // string | undefined (flag on)
first.toUpperCase();              // Error: 'first' is possibly 'undefined'

// Handle it where you read it:
const first2 = items[0];
if (first2 !== undefined) first2.toUpperCase();   // OK

// Or reach for APIs that were always honest about absence:
const first3 = items.at(0);       // string | undefined regardless of the flag
const hit = items.find(s => s === "b");           // string | undefined

// Iteration is unaffected — elements of a for…of / map are never undefined:
for (const s of items) s.toUpperCase();           // OK
Not a substitute for a length check

if (items.length > 0) items[0].toUpperCase() is still an error: TS doesn't correlate length with index types. Either read into a variable and test it, or destructure: const [head] = items; gives string | undefined once and you narrow that.

satisfies — validate shape without widening

See 2d for the mechanics. The payoff: a compile-time shape check and TS keeps the literal / narrower inferred type for use after the declaration. An annotation (: Theme) replaces the inferred type with the declared one; satisfies only checks against it.

type Theme = { colors: Record<string, string> };

const theme = {
  colors: {
    primary: "#0070f3",
    danger: "#ff0000",
  },
} satisfies Theme;

theme.colors.primary.startsWith("#");   // OK — primary: string, key known to exist
theme.colors.warning;                   // Error — no such key (inference kept the exact keys)

const theme2: Theme = { colors: { primary: "#0070f3" } };
theme2.colors.primary;                  // string | undefined with noUncheckedIndexedAccess —
                                        // the annotation widened colors to Record<string, string>

Branded types — nominal typing on demand

TS is structural: two strings are interchangeable even if one is a user id and the other an order id. A brand intersects the primitive with a phantom property that only exists at the type level, so the two aliases stop being assignable to each other. Nothing changes at runtime; the brand is applied once, at the place that validated the value.

declare const brand: unique symbol;
type Brand<T, Name extends string> = T & { readonly [brand]: Name };

type UserId  = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;

function parseUserId(s: string): UserId {
  if (!/^u_[a-z0-9]{8}$/.test(s)) throw new Error(`bad user id: ${s}`);
  return s as UserId;                 // the one sanctioned cast: right after the check
}

function loadUser(id: UserId) { /* … */ }

loadUser(parseUserId("u_1a2b3c4d"));  // OK
loadUser("u_1a2b3c4d");               // Error: string is not UserId
loadUser(orderId);                    // Error: OrderId is not UserId

unique symbol keeps the brand out of autocomplete and out of Object.keys expectations; the older { __brand: "UserId" } spelling works the same way but shows up as a real-looking property.

Code review
  • as on data from outside the process. JSON.parse(body) as Order, req.body as CreateUser, await res.json() as User[]. The cast is erased; the first wrong field is a TypeError in a different module. Parse with a schema (2h) or a real guard. ESLint: @typescript-eslint/consistent-type-assertions can forbid object-literal casts.
  • Guards that under-check. x is User with a body that only tests typeof x === "object". Reviewers read guard bodies against the predicate type field by field.
  • any in a signature. One any parameter poisons every inferred type downstream. unknown plus narrowing, or a generic. ESLint: @typescript-eslint/no-explicit-any, no-unsafe-*.
  • Non-null assertions (!) to silence noUncheckedIndexedAccess. items[0]! is the empty-array bug the flag exists to catch. Narrow the value or use at() / find() and handle undefined. ESLint: @typescript-eslint/no-non-null-assertion.
  • switch over a union with no default: assertNever. Adding a member compiles and silently returns undefined. ESLint: @typescript-eslint/switch-exhaustiveness-check.
  • @ts-ignore. Suppresses forever, including errors that appear later on that line. @ts-expect-error fails the build once the error is gone, so the suppression can't outlive its reason. ESLint: @typescript-eslint/ban-ts-comment.
  • catch (e: any). useUnknownInCatchVariables (part of strict) makes e unknown on purpose: anything can be thrown. Narrow with e instanceof Error before reading .message.

Recall
What is the one-line difference between any and unknown?
Both accept any value; any is also assignable to everything (checks off, spreads through inference), unknown is assignable to nothing until you narrow it.
Which narrowing forms run code at runtime, and which one doesn't?
typeof, instanceof, in, literal equality, type guards (x is T) and assertion functions (asserts x is T) all execute a check. as is erased on emit and narrows with no check.
Type guard vs assertion function — when do you use which?
Guard (x is T) for if branches where both outcomes are legitimate; assertion (asserts x is T) for invariants — it throws on the bad case and narrows for the rest of the scope. Both need explicit return-type annotations.
What does this print? 
function label(x: { id: string; name: string } | { name: string }) {
  return "id" in x ? `#${x.id}` : x.name;
}
console.log(label(JSON.parse('{"id":null,"name":"c"}')));
console.log("id" in { id: undefined });
#null then true. in tests key presence (including undefined/null values and the prototype chain), and the type annotation never checked the parsed data.
Why does a type guard whose body only checks typeof x === "object" compile, and what goes wrong?
The checker verifies callers against the predicate type, never the body against it. Every object passes as T; the TypeError appears wherever a missing field is first read.
How does default: return assertNever(s) catch a forgotten case?
Each handled case subtracts a member; after all are handled s is never, the only type assignable to a never parameter. A new member leaves s as that member → compile error at the switch. The throw inside also catches stale runtime data.
Under noUncheckedIndexedAccess, what is the type of items[0] for items: string[], and does if (items.length > 0) help?
string | undefined. The length check doesn't narrow the index type; read into a variable (or destructure const [head] = items) and test that for undefined.
: Theme vs satisfies Theme — what's kept and what's lost?
The annotation replaces the inferred type with Theme (keys widen to Record, values may become | undefined). satisfies checks against Theme but keeps the inferred literal keys and types.
What does a branded type change at runtime, and where is the as allowed?
Nothing — the brand is a phantom property (unique symbol) that exists only in the type. The single cast lives in the function that validated the value (parseUserId); everything else receives UserId already branded.
