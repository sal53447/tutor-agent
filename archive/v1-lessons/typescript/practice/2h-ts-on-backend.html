TS on the Backend

@types/* — type definitions for plain JS libraries

Most npm packages that predate TS (or ship without types) have community-maintained type definitions in the @types namespace. These are dev-only packages that provide the .d.ts files TS needs to understand the library.

npm install express
npm install -D @types/node @types/express

Once installed, import express from "express" gives you full type inference. Packages that ship their own types (e.g., zod, prisma) don't need a separate @types/* install.

Express request typing

Express's Request type accepts four generic parameters: Request<Params, ResBody, ReqBody, Query>. In practice you'll type Params and ReqBody most often.

import { Request, Response, RequestHandler, ErrorRequestHandler } from "express";

// Typed route params and response body
type GetUserParams = { id: string };
type UserResponse  = { id: string; name: string };

app.get("/users/:id", (req: Request<GetUserParams>, res: Response<UserResponse>) => {
  const { id } = req.params;   // id: string
  res.json({ id, name: "Alice" });
});

// req.body is any by default — type it after Zod validation
app.post("/users", (req, res) => {
  const result = CreateUserSchema.safeParse(req.body);
  if (!result.success) return res.status(400).json(result.error);
  const body = result.data;  // CreateUser — validated and typed
});

Middleware types: RequestHandler and ErrorRequestHandler

// A middleware that doesn't change params/body
const logRequest: RequestHandler = (req, res, next) => {
  console.log(req.method, req.path);
  next();
};

// Auth middleware — typed with generic params
const requireAuth: RequestHandler<{}, any, any, { token?: string }> = (req, res, next) => {
  if (!req.query.token) return res.status(401).json({ error: "Unauthorized" });
  next();
};

// Error middleware — must have exactly 4 params; Express detects by arity
const errorHandler: ErrorRequestHandler = (err, req, res, next) => {
  console.error(err);
  res.status(500).json({ error: "Internal server error" });
};

Declaration merging: augmenting Express.Request

When auth middleware attaches a user to req, TS doesn't know about it. Use declaration merging to extend the Express namespace.

// src/types/express.d.ts  (or any .d.ts file included in your tsconfig)
import { User } from "../models/user";

declare global {
  namespace Express {
    interface Request {
      user?: User;
    }
  }
}

// Now req.user is typed everywhere — no casts needed
app.get("/profile", requireAuth, (req, res) => {
  res.json(req.user);   // req.user: User | undefined
});

Zod — runtime validation that generates types

import { z } from "zod";

const UserSchema = z.object({
  id: z.string().uuid(),
  email: z.string().email(),
  age: z.number().int().positive().optional(),
});
type User = z.infer<typeof UserSchema>;   // { id: string; email: string; age?: number }

// In an Express handler:
app.post("/users", (req, res) => {
  const result = UserSchema.safeParse(req.body);
  if (!result.success) return res.status(400).json(result.error);
  const user: User = result.data;   // validated AND typed
});
The pattern to internalize

Define the schema once, derive the TS type with z.infer. Your validation and your types can never drift. This pattern — schema as source of truth — is everywhere in modern TS backends.

tRPC — end-to-end type safety

tRPC lets a Next.js or React client call server functions and get full type inference across the network, no manual types or OpenAPI. When you own both ends, this is the gold standard. When you don't (public API, mobile clients), stick with REST + OpenAPI/Zod.

// server/router.ts
import { initTRPC } from "@trpc/server";
import { z } from "zod";

const t = initTRPC.create();

export const appRouter = t.router({
  getUser: t.procedure
    .input(z.object({ id: z.string() }))
    .query(async ({ input }) => {
      return db.user.findUnique({ where: { id: input.id } });
      // return type is inferred from the query — no manual typing
    }),

  createUser: t.procedure
    .input(z.object({ name: z.string(), email: z.string().email() }))
    .mutation(async ({ input }) => {
      return db.user.create({ data: input });
    }),
});

export type AppRouter = typeof appRouter;   // export for client use
// client/api.ts
import { createTRPCReact } from "@trpc/react-query";
import type { AppRouter } from "../server/router";

export const trpc = createTRPCReact<AppRouter>();

// In a component:
const { data: user } = trpc.getUser.useQuery({ id: "123" });
// user is fully typed — matches server return type, no cast needed

Env vars, validated at boot

import { z } from "zod";

const Env = z.object({
  DATABASE_URL: z.string().url(),
  PORT: z.coerce.number().int().default(3000),
  // z.coerce.number() is required because process.env values are always strings.
  // "3000" coerces to 3000; without coerce, z.number() would reject it.
  NODE_ENV: z.enum(["development", "test", "production"]),
});

export const env = Env.parse(process.env);
// If DATABASE_URL is missing, the app crashes on start — fail fast.

Typed ORM results

Modern ORMs generate types you get for free without any manual annotation:

  • Prisma — generates a .prisma/client with a TypeScript type for every model and query result. db.user.findMany() returns User[] automatically. Running prisma generate after schema changes keeps types in sync.
  • Drizzle — infers types from your schema definitions at the JS level. db.select().from(users) returns the inferred row type. No codegen step — the types live alongside the schema definition.
// Prisma — type comes from generated client
import { type User } from "@prisma/client";
const users: User[] = await db.user.findMany({ where: { active: true } });

// Drizzle — type inferred from schema
import { users } from "./schema";
const rows = await db.select().from(users);
// rows: { id: number; name: string; email: string }[]  — inferred
