tsconfig Deep Dive

tsconfig.json decides what counts as an error, how an import specifier turns into a file, and what tsc writes to disk. Most "TypeScript is weird" moments in a new codebase are a config choice, not a language rule: arr[0] being T | undefined (2f), the .js extension on imports of .ts files (2h), @/ aliases that type-check and then crash under node. Two configs below cover 90% of projects; the rest of the lesson is the flags that make them differ.

Four groups of options

Every compilerOptions key belongs to one of four groups, and each group changes a different stage of the compiler:

  • Strictness — strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes, noImplicitOverride, noFallthroughCasesInSwitch. Change only which errors are reported. Zero effect on output.
  • Modules — module, moduleResolution, paths, esModuleInterop, verbatimModuleSyntax. How a specifier string maps to a file, and what import/export syntax survives emit.
  • Emit — target, lib, jsx, outDir, declaration, noEmit, sourceMap. What tsc writes, and in which dialect of JS.
  • Program — include, exclude, files, rootDir, types, skipLibCheck. Which files form one compilation, and which .d.ts get checked.

Bundler-based projects (Vite, Next.js, esbuild) use only the first, second and fourth groups: the bundler emits, tsc --noEmit type-checks. Only a tsc-built Node service cares about the Emit group.

Mechanism

Strictness flags never change the emitted JavaScript; module flags change both what type-checks and what the emitted import lines say. That is why a strictness flag is safe to flip in an existing project and a module flag is not.

Python bridge

The Strictness group is [tool.mypy]: strict = true ≈ "strict": true, disallow_untyped_defs ≈ noImplicitAny, no_implicit_optional ≈ strictNullChecks, warn_unreachable ≈ allowUnreachableCode: false. files / mypy_path ≈ include / paths. The difference: mypy only reports; it never rewrites your code or decides how import x is found at runtime. tsconfig does both, and the Modules and Emit groups have no Python counterpart — the closest is the interpreter's own sys.path and version, which you configure outside the type checker.

Frontend / Vite config

The bundler emits; tsc only checks (noEmit). moduleResolution: "bundler" accepts extensionless relative imports and package.json exports; jsx: "react-jsx" uses the automatic runtime (no import React in every file). Next.js sets jsx: "preserve" instead because its own compiler handles JSX.

{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "moduleResolution": "bundler",
    "jsx": "react-jsx",
    "noEmit": true,
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "exactOptionalPropertyTypes": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true,
    "resolveJsonModule": true,
    "paths": {
      "@/*": ["./src/*"]
    }
  },
  "include": ["src"]
}

Node / Express backend config

Node's native ESM resolver is stricter than a bundler's. Use module: "NodeNext"; since TS 5.2 that implies moduleResolution: "NodeNext" and esModuleInterop, and tsc errors if you set a different resolution. Whether a .ts file is ESM or CommonJS is decided the way Node decides it: the nearest package.json "type" field, or a .mts / .cts extension.

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true,
    "resolveJsonModule": true,
    "sourceMap": true,
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": ["src"]
}
Import paths need the .js extension

Under NodeNext, import { x } from "./util" is error TS2835 and import { x } from "./util.js" is correct — even though the file on disk is util.ts. tsc never rewrites specifiers; Node resolves the emitted dist/util.js, so the source has to name it. TS 5.7 added rewriteRelativeImportExtensions, which lets you write ./util.ts and rewrites it to .js on emit — the one exception to "specifiers are never rewritten". Bundler resolution needs neither.

Start here

For new projects, turn on strict: true, noUncheckedIndexedAccess: true, and verbatimModuleSyntax: true. These three catch the overwhelming majority of bugs strict alone misses. @total-typescript/tsconfig is a popular preset built on the same idea.

Mechanism

Top lane: with NodeNext the string you write is the string Node will see, so it must already be the output filename. Bottom lane: a bundler consumes the specifier itself, so .ts, extensionless and directory imports all work — and nothing is left for the runtime to resolve.

Key flags explained

  • strict — turns on all strict-mode flags (strictNullChecks, noImplicitAny, strictFunctionTypes, useUnknownInCatchVariables, …). Non-negotiable.
  • outDir / rootDir — where tsc writes and where source lives. Without them, .js files land next to .ts files.
  • noUncheckedIndexedAccess — arr[0] and record[key] are typed T | undefined. Catches "forgot the empty array" bugs. See 2f for what this means in practice.
  • exactOptionalPropertyTypes — distinguishes { x?: string } (key may be absent) from { x: string | undefined } (key present, value may be undefined). Without it, { x: undefined } satisfies { x?: string }. Next block shows why that is a runtime difference.
  • verbatimModuleSyntax — an import without type is kept in the output exactly as written; type-only imports must say import type. Removes the guessing that single-file transpilers (esbuild, SWC, sucrase) can't do.
  • isolatedModules — errors on constructs that can't be transpiled one file at a time (const enum across files, re-exporting a type without export type). Required for Vite, SWC, esbuild.
  • moduleResolution: "bundler" — the modern default for anything a bundler builds; "NodeNext" for anything node runs directly.
  • skipLibCheck — don't type-check node_modules/**/*.d.ts. Faster, and avoids errors in two libraries' conflicting globals that you can't fix anyway.

paths aliases are compile-time only

paths tells the checker how to resolve @/*. It does not teach Node, and tsc does not rewrite the specifier on emit — dist/index.js still says import "@/db.js", which Node treats as a package named @.

$ node dist/index.js
Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@/db.js' imported from dist/index.js

Bundlers (Vite, webpack, Next.js) read paths and resolve it themselves. For a plain Node service use the platform feature instead: package.json "imports" (subpath imports, #-prefixed), which both NodeNext resolution and Node itself understand.

{
  "name": "api",
  "type": "module",
  "imports": {
    "#db": "./dist/db.js",
    "#lib/*": "./dist/lib/*.js"
  }
}
import { db } from "#db";          // resolves in tsc and in node — no bundler, no tsconfig-paths

What exactOptionalPropertyTypes protects at runtime

A missing key and a key holding undefined are different objects to in, Object.keys, JSON.stringify, and — the one that bites — object spread. { ...defaults, ...overrides } copies an explicit undefined over the default. Without the flag, TS lets { retries: undefined } flow into a { retries?: number } parameter, so the merge silently loses the default.

type Options = { retries?: number };
const defaults = { retries: 3 };

function run(opts: Options) {
  const cfg = { ...defaults, ...opts };     // cfg.retries: number — says TS
  return cfg.retries;
}

run({ retries: undefined });
// exactOptionalPropertyTypes off:  compiles, returns undefined at runtime
// exactOptionalPropertyTypes on:   error TS2375 — 'undefined' is not assignable to 'number'
Try it

Plain JS — this is the behaviour the flag is guarding. Try: replace the spread with Object.assign({}, defaults, explicit) (same result); then filter explicit with Object.fromEntries(Object.entries(o).filter(([, v]) => v !== undefined)) before spreading; then swap the spread order.

const absent   = {};
const explicit = { retries: undefined };

for (const o of [absent, explicit]) {
  console.log("in:", "retries" in o, "| keys:", Object.keys(o).length, "| json:", JSON.stringify(o));
}

const defaults = { retries: 3 };
console.log({ ...defaults, ...absent }.retries);
console.log({ ...defaults, ...explicit }.retries);
in: false | keys: 0 | json: {} in: true | keys: 1 | json: {} 3 undefined

Exercise

mergeConfig lets an explicit undefined in overrides clobber a default — the bug exactOptionalPropertyTypes exists to flag. Fix it so undefined is treated as "absent": it neither overrides a default nor appears as a key in the result. Defined falsy values (0, "", false) must still override. Tests check all three cases.

// --- fix this
function mergeConfig(defaults, overrides) {
  return { ...defaults, ...overrides };
}

console.log(mergeConfig({ retries: 3, timeout: 1000 }, { retries: undefined, timeout: 50 }));

Implement resolveImport(importer, specifier, mode) — a model of the two resolution modes from the diagram above. files is the set of source files on disk; join and dirname are provided. Contract:

// --- helpers (leave as is)

function dirname(p) { return p.slice(0, p.lastIndexOf("/")); }
function join(dir, spec) {           // join("src/components", "../lib/api") → "src/lib/api"
  const parts = dir.split("/");
  for (const seg of spec.split("/")) {
    if (seg === "." || seg === "") continue;
    if (seg === "..") parts.pop(); else parts.push(seg);
  }
  return parts.join("/");
}

Code review
  • strict: false or individual strict flags switched off in a new project. Every later migration to strict is a multi-week PR; start strict and add noUncheckedIndexedAccess on day one.
  • paths in a tsc-built Node service. Type-checks, crashes at node dist/index.js with ERR_MODULE_NOT_FOUND. Use package.json "imports" (#db) or a bundler; tsconfig-paths is a workaround, not a fix.
  • moduleResolution: "node" (node10) in 2026. It ignores package.json exports, so you get stale or wrong types from dual-published packages. Pick bundler or NodeNext; nothing else.
  • Mismatched module / moduleResolution (e.g. module: "CommonJS" with bundler). TS 5.x reports it as an error; older configs copied from blog posts still carry it.
  • No verbatimModuleSyntax with an esbuild/SWC/Vite pipeline. A type-only import without import type survives as a runtime import of a file that exports nothing → SyntaxError: does not provide an export named. The flag turns that into a compile error.
  • target below what the runtime supports. target: "ES5" for Node 20 downlevels async/await into generator state machines and class into functions — slower, bigger, and stack traces stop matching the source. Match the oldest runtime you actually ship to (ES2022 for Node 20+ and evergreen browsers).
  • CI runs the bundler but never tsc --noEmit. Vite and esbuild strip types without checking them; a project can ship with hundreds of type errors. The type check is a separate CI step.

Recall
Which group of tsconfig options never changes the emitted JavaScript, and which group changes both checking and emit?
Strictness (strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes, …) is check-only. Module options (module, moduleResolution, verbatimModuleSyntax) affect both what resolves and what import lines are emitted.
Under module: "NodeNext", what must a relative import of src/util.ts look like, and why?
import { x } from "./util.js" — tsc never rewrites specifiers, and Node will resolve the emitted dist/util.js. Extensionless imports are error TS2835. (TS 5.7's rewriteRelativeImportExtensions allows ./util.ts and rewrites it.)
Why does paths: { "@/*": ["./src/*"] } type-check and then crash a tsc-built Node service at runtime? What's the fix?
paths is checker-only; dist/index.js still imports "@/db.js" and Node reports ERR_MODULE_NOT_FOUND. Use package.json "imports" (#db subpath imports) or a bundler.
What distinction does exactOptionalPropertyTypes enforce, and which runtime operation makes it matter?
{ x?: T } (key may be absent) vs { x: T | undefined } (key present). Object spread copies an explicit undefined over a default, so { ...defaults, ...{ x: undefined } }.x is undefined.
What does this print? 
const merged = { ...{ retries: 3 }, ...{ retries: undefined } };
console.log(merged.retries, "retries" in merged, JSON.stringify(merged));
undefined true {} — the key exists with value undefined; JSON.stringify omits it.
What do verbatimModuleSyntax and isolatedModules protect against, and which toolchains need them?
Single-file transpilers (esbuild, SWC, Vite, sucrase) can't see other files, so they can't tell whether an import is type-only. verbatimModuleSyntax forces import type; isolatedModules rejects cross-file const enum and un-annotated type re-exports.
Which moduleResolution values are acceptable in a TS 5.x project, and what's wrong with "node"?
"bundler" (bundler-built) or "NodeNext" (run by Node directly). "node" (node10) ignores package.json exports, so dual-published packages resolve to the wrong or missing types.
Why does a Vite project need tsc --noEmit as a separate CI step?
Vite/esbuild strip types without checking them; the build succeeds with any number of type errors. Only tsc (or vue-tsc) reports them.
