React Mental Model

React is a declarative UI library: a component returns a description of the UI for the current state, and React works out which DOM nodes to create, update or remove. Every later lesson — hooks (4c–4f), forms (4i), performance (4k), Server Components (Part 5) — assumes three things from this one: a component is a plain function that React calls; a state change schedules a re-render rather than mutating anything; and rendering is cheap while committing to the DOM is what costs.

The one-sentence model: UI = f(state)

UI = f(state). A component is a function from props + state to a tree of element objects — plain JS data (4b). React calls the function, compares the new tree with the one it rendered last time (reconciliation), and applies the minimal set of DOM operations (commit). You never write "when X changes, update element Y"; you write what the UI is for any X.

Concrete form

import { useState } from "react";
import { createRoot } from "react-dom/client";

function Counter() {
  const [count, setCount] = useState(0);
  // Every time count changes, React calls Counter again and gets a new description.
  // Turning that description into DOM operations is React's job, not yours.
  return <button onClick={() => setCount(c => c + 1)}>Clicked {count}×</button>;
}

createRoot(document.getElementById("root")).render(<Counter />);

createRoot(...).render(...) does not render synchronously: it schedules the first render. Same for every setState — nothing happens on that line except an update being queued.

A state change: render → reconcile → commit → effects

setCount(1) enqueues an update and schedules work. React then runs four phases:

  1. Render phase. React calls the component function — and, by default, every component below it — to get a new element tree. Must be pure; may be interrupted or thrown away.
  2. Reconcile. The new tree is diffed against the current one, by position and key. Same element type → keep the DOM node, patch changed props. Different type → unmount the old subtree, mount the new.
  3. Commit. All collected DOM mutations are applied in one synchronous pass. useLayoutEffect runs, then the browser paints.
  4. Effects. useEffect callbacks run after paint (4d).

Two consequences you will hit in week one. Batching: every setState call inside one event handler (and, since React 18, inside one timer or promise callback) is collected into a single render. Stale reads: the state variable is a const local to this call of the function; reading it after setState gives the old value, because the new value only exists in the next call.

function Counter() {
  const [n, setN] = useState(0);
  function onClick() {
    setN(n + 1);
    setN(n + 1);        // same n — the committed value will be 1, not 2
    console.log(n);     // 0: this call's n; the next render gets a fresh const
  }
  return <button onClick={onClick}>{n}</button>;
}
// To chain updates, pass a function: setN(c => c + 1); setN(c => c + 1);  → 2

Unidirectional data flow

State lives in one component. It flows down as props; events flow up as callbacks passed as props. No two-way binding: a child that wants to change something it was given calls the function it was given. When two components need the same state, it moves to their closest common ancestor (lifting state up).

function App() {
  const [query, setQuery] = useState("");
  return (
    <>
      <Header />
      <SearchBox value={query} onChange={setQuery} />   {/* data down, events up */}
      <Results query={query} />
    </>
  );
}

function SearchBox({ value, onChange }) {
  return <input value={value} onChange={e => onChange(e.target.value)} />;
}

Think spreadsheet: state is the input cells, components are the formulas. You change an input; every dependent formula recomputes. You never tell a cell to update itself.

Python bridge

A component is called like SearchBox(value="re", onChange=set_query) — props are one keyword-argument dict, children included. There is no self: no instance survives between calls, so every render is a fresh invocation with fresh locals, and the handlers it creates close over that call's values (4c).

Step through

Rendering ≠ DOM update

"Rendering" in React means calling your component function. It does not mean touching the DOM. A component renders when its own state changes or when its parent renders — props are not compared first. The DOM is written only for the nodes whose output actually changed. So a component can render 100 times and produce zero DOM operations, and that is usually fine: function calls are cheap, layout and paint are not. Optimisation discussions go wrong when the two are conflated — measure the commit, not the render count (4k).

Opting a child out of parent-triggered renders is explicit: wrap it in memo so React compares props first, or let the React Compiler (React 19) insert that memoisation for you. Both only work if the component is pure — see below.

State is compared by identity — mutation is invisible

setState(next) compares next with the current value using Object.is. Equal → React bails out and nothing renders. Mutating an array or object keeps the same reference, so items.push(x); setItems(items) is a no-op as far as React can tell — and it has also silently changed the "previous" value that memo, effect dependencies and the DevTools diff rely on. State is treated as immutable: every change produces a new value.

Don't
items.push(newItem);     setItems(items);    // same reference → no render
user.name = "Ada";       setUser(user);      // same reference → no render
items.sort();            setItems(items);    // mutates in place, too
Do
setItems([...items, newItem]);
setUser({ ...user, name: "Ada" });
setItems(items.toSorted());                  // ES2023: toSorted / toReversed / toSpliced / with return copies
setItems(items.filter(i => i.id !== id));
setItems(items.map(i => i.id === id ? { ...i, done: true } : i));

Copies are shallow: { ...user } shares user.address with the original. That is a feature (unchanged branches keep their identity, so memoised children skip) as long as you never mutate the shared branch. Nested updates spread each level you change, or use Immer (useImmer) when the nesting gets deep.

Try it

const state = { items: [1, 2], user: { name: "Ada" } };

Python bridge

Python code mutates by default — xs.append(x), d["k"] = v, obj.name = … — and nothing cares. React state is the opposite discipline: treat every value like a tuple or a frozen=True dataclass and build the next one. The mappings are mechanical: [...xs, x] ≈ xs + [x]; { ...d, k: v } ≈ {**d, "k": v}; { ...obj, name } ≈ dataclasses.replace(obj, name=name); xs.toSorted() ≈ sorted(xs) (copy) while xs.sort() ≈ xs.sort() (in place, don't). The reason is the same as hashing a dict key: React identifies "changed" by identity, not by content.

Concurrent rendering and the purity rule

Since React 18 the scheduler can pause a render, work on something more urgent (a keypress), and resume or restart the paused one. That is what useTransition, useDeferredValue and Suspense streaming are built on. Three things follow for your code:

  • A component function may be called and its result thrown away. No side effects during render: no mutation of outer variables, no fetch, no writes to localStorage. Side effects belong in event handlers or effects (4d).
  • <StrictMode> deliberately calls every component (and effect) twice in development to make impurity visible. If double-invocation changes the output, the component was already wrong.
  • The React Compiler (React 19) auto-memoises components and hooks by assuming the Rules of React. An impure component does not error under the compiler — it renders stale output, which is harder to debug than a crash.
Forward pointer — where does this code run?

In a browser-only React app, components always run in the browser. In Next.js (Part 5), Server Components run on the server, render once, and ship no JS. UI = f(state) still holds, but "state" there is request data (params, cookies, a database read), not useState. Details in 4g and Part 5.

Code review
  • Side effect in the render body. analytics.track(), fetch, ref.current = … or a mutated module variable at the top of a component. Fires twice under StrictMode, fires for discarded concurrent renders, breaks under the Compiler. Move it to an event handler or useEffect. ESLint: eslint-plugin-react-hooks (react-compiler rule set) flags most of these.
  • Mutating state then setting the same reference. list.push(x); setList(list). Sometimes it appears to work because something else re-rendered; then it stops. Always build a new value.
  • Reading state right after setting it. setOpen(true); if (open) … — open is this render's const. Use the value you just computed, or derive in the next render.
  • setX(x + 1) where the next update may land before the render. Rapid clicks, keyboard repeat, async callbacks. Functional updates (setX(c => c + 1)) compose; value updates overwrite.
  • Storing derived data in state. const [total, setTotal] = useState(0) kept in sync with items by an effect. It is a second source of truth that lags by one render; compute it during render (const total = sum(items)) and memoise only if measured.
  • State held too high. A typing field whose state lives in the page root re-renders the whole page on every keystroke. Keep state in the lowest component that needs it; lift only when siblings must share.

Recall
What are the four phases React runs after setState, and which one touches the DOM?
Render (call the component functions) → reconcile (diff new tree vs current, by position and key) → commit (apply DOM mutations synchronously, run useLayoutEffect, paint) → effects (useEffect, after paint). Only commit writes to the DOM.
Inside a click handler: setN(n + 1); setN(n + 1); console.log(n) with n === 0. What is logged, and what does the button show after the render?
Logs 0 (this call's const); the button shows 1 — both updates computed 0 + 1 and were batched into one render. setN(c => c + 1) twice would give 2.
What does this print, in order? 
createRoot(root).render(<App />);   // App logs "App render"
console.log("render() returned");
render() returned, then App render. createRoot().render schedules the render; nothing runs synchronously.
When does a component re-render, and does React compare its props first?
When its own state changes, or when its parent re-renders. Props are not compared by default; memo (or the React Compiler) opts a component into that comparison.
Why does items.push(x); setItems(items) not update the screen?
setItems compares with Object.is; the mutated array is the same reference as the current state, so React bails out. Build a new array: setItems([...items, x]).
What does this print? 
const s = { a: [1], b: { x: 1 } };
const n = { ...s, a: [...s.a, 2] };
console.log(Object.is(s.a, n.a), Object.is(s.b, n.b));
false true. Spread is shallow: the rebuilt branch gets a new identity, the untouched branch is shared.
Why must a component function be pure, and what two React features exploit that?
Concurrent rendering may call it and discard the result (or call it again after an interruption), and the React Compiler memoises on the assumption that same inputs give the same output. StrictMode double-invokes in dev to catch violations.
Where does the state go when two sibling components need the same value?
Into their closest common ancestor ("lifting state up"); it flows down as props and changes flow up through callback props. No two-way binding.
