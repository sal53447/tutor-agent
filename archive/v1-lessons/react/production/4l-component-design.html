Component Design Patterns

Compound components

A parent and children that share implicit state via context. User composes them freely.

<Tabs defaultValue="a">
  <Tabs.List>
    <Tabs.Trigger value="a">A</Tabs.Trigger>
    <Tabs.Trigger value="b">B</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Content value="a">A content</Tabs.Content>
  <Tabs.Content value="b">B content</Tabs.Content>
</Tabs>

Headless UI (behavior, no styles)

Radix UI, React Aria, Headless UI, shadcn/ui. They give you accessible primitives (dropdowns, dialogs, menus) without imposing a visual design. You style them yourself, usually with Tailwind. This is the dominant modern pattern — don't roll your own dialog unless you want to fight focus traps, keyboard nav, and ARIA forever.

Polymorphic components — prefer asChild over as prop

The as prop is hard to type correctly in TypeScript (the component needs to accept all props of the target element). The modern dominant pattern from Radix UI is asChild: the component merges its behavior/styles onto its single child element rather than rendering its own root element.

// asChild pattern (Radix Slot)
import { Slot } from "@radix-ui/react-slot";

function Button({ asChild = false, className, children, ...props }) {
  const Comp = asChild ? Slot : "button";
  return <Comp className={cn("btn", className)} {...props}>{children}</Comp>;
}

// Usage — Button renders as a Next.js Link, keeping Button's styles + Link's routing
<Button asChild>
  <Link href="/dashboard">Go to dashboard</Link>
</Button>

Slot merges event handlers, refs, and className from the parent onto the child. No TypeScript gymnastics needed — the child's own type describes valid props.

Suspense and ErrorBoundary as composition primitives

These aren't just error-handling tools — they're the standard way to declare loading and error states at the component tree level, decoupled from the async data logic inside.

import { Suspense } from "react";
import { ErrorBoundary } from "react-error-boundary";  // npm package

function UserSection({ id }) {
  return (
    <ErrorBoundary fallback={<p>Failed to load user.</p>}>
      <Suspense fallback={<Skeleton />}>
        <UserCard id={id} />  {/* suspends while fetching; throws on error */}
      </Suspense>
    </ErrorBoundary>
  );
}
Next.js file-based versions

In Next.js App Router, loading.tsx is a file-based <Suspense> boundary for a route segment. error.tsx is a file-based <ErrorBoundary>. They're the same primitive — Next.js just wires them up automatically from the filesystem. Understanding Suspense + ErrorBoundary directly makes the Next.js conventions obvious.

  1. Why does defining a component inside another component cause state loss on every re-render of the parent?
  2. What problem does asChild solve that the as prop doesn't?
  3. What's the difference between a Suspense boundary and an ErrorBoundary? Can they be nested?

1. Every render creates a new component type (new function reference) — React sees a different component at that position, unmounts the old one (clearing state), and mounts the fresh one. 2. asChild avoids TypeScript typing complexity — the child's own type system handles prop validation, and Slot handles merging. The as prop requires the wrapper to re-export the full prop union of every possible target element. 3. Suspense catches pending async operations (shows fallback); ErrorBoundary catches thrown errors (shows error fallback). Yes, nest them — ErrorBoundary outside, Suspense inside, so errors don't just show an empty loading state forever.
