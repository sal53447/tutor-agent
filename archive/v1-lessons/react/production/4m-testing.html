Testing — React Testing Library Philosophy

The RTL mantra: test your components the way a user uses them. Query by accessible role / text, not by class names or test IDs (last resort). If your test resembles how a user interacts, it survives refactors.

Tests in this curriculum use Vitest — a Vite-native test runner. Its API mirrors Jest exactly (describe, it, expect), but vi.fn() replaces jest.fn(). If you see vi.fn() in an example, that's Vitest's mock factory.

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("login form submits", async () => {
  const onSubmit = vi.fn();
  render(<LoginForm onSubmit={onSubmit} />);

  await userEvent.type(screen.getByLabelText(/email/i), "a@b.c");
  await userEvent.type(screen.getByLabelText(/password/i), "hunter22");
  await userEvent.click(screen.getByRole("button", { name: /log in/i }));

  expect(onSubmit).toHaveBeenCalledWith({ email: "a@b.c", password: "hunter22" });
});

customRender — wrapping providers once

Components that use useQuery / useMutation need a QueryClientProvider above them. Set it up once in a test utility rather than in every test file.

import { render, RenderOptions } from "@testing-library/react";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";

function makeQueryClient() {
  return new QueryClient({ defaultOptions: { queries: { retry: false } } });
}

function AllProviders({ children }: { children: React.ReactNode }) {
  const qc = makeQueryClient();   // fresh client per test — no cache bleed
  return <QueryClientProvider client={qc}>{children}</QueryClientProvider>;
}

export function customRender(ui: React.ReactElement, options?: RenderOptions) {
  return render(ui, { wrapper: AllProviders, ...options });
}

// Usage: replace render() with customRender() in any test that touches useQuery
customRender(<UserCard id={1} />);

Mocking API calls with MSW

Mock Service Worker (MSW) intercepts network requests at the service worker level — your code calls fetch normally, MSW intercepts before the request leaves the browser (or Node in tests). This is the standard for mocking APIs in React tests because it tests your actual fetch logic, not a mock of it.

import { http, HttpResponse } from "msw";
import { setupServer } from "msw/node";

const server = setupServer(
  http.get("/api/users/:id", ({ params }) => {
    return HttpResponse.json({ id: params.id, name: "Test User" });
  })
);

beforeAll(() => server.listen());
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

test("displays user name", async () => {
  customRender(<UserCard id="1" />);
  expect(await screen.findByText("Test User")).toBeInTheDocument();
});

Testing React Server Components

RSC testing tooling is still maturing as of 2026. The pragmatic approach: test RSC output via integration/E2E tests (Playwright), or test the data-fetching logic separately from the rendering. RTL + jsdom cannot execute RSC — they're server-only. Avoid investing heavily in unit-testing RSC internals; the ecosystem will stabilize over 2026.

Anti-patterns
  • Querying by class name or data-testid when an accessible role or label exists.
  • Asserting on internal state (was useState called with X?). Test outputs.
  • Rendering a provider wrapper in every test inline — extract a customRender.
  • Mocking your own components. If you need to mock Button, the test is too coupled.
  • Sharing a QueryClient instance across tests — cache state bleeds between tests, causing order-dependent failures.
Python bridge

RTL's philosophy matches pytest's: test behavior, not implementation. customRender with providers is analogous to a pytest fixture that sets up a test database session — scaffolding that every test needs, defined once. MSW intercepting at the network level is similar to responses or httpretty in Python — you mock the boundary, not the internal function calls.
