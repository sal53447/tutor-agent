Styling — Tailwind, CSS Modules, CSS-in-JS

Styling in React is a question of when a class name becomes a CSS rule: at build time (Tailwind, CSS Modules, zero-runtime CSS-in-JS) or at render time (styled-components, Emotion). That one distinction decides what works in Server Components (5c), what ships as JavaScript, and why a dynamically built class name renders unstyled in production. The rest is conventions: cn(), variant maps, design tokens.

The landscape

ApproachResolvedStatus
Tailwind CSS v4buildDominant. Utility classes generated from the strings found in your source. Config lives in CSS (@theme). Ecosystem: shadcn/ui, Radix. Default for new projects.
CSS ModulesbuildPlain CSS, class names rewritten to btn_x7f2a per file. Works everywhere, including Server Components. Zero runtime.
Vanilla CSS + cascade layers—Viable again: native nesting, @layer, :has(), container queries ship in every browser. Small projects need no preprocessor.
styled-components / EmotionruntimeGenerate CSS during render on the client. Need "use client" and an SSR style registry; impossible inside a Server Component. Avoid in new App Router apps.
Vanilla Extract, Panda, StyleXbuildTyped, zero-runtime CSS-in-JS: the styles are extracted into static CSS at build. Good TS ergonomics; smaller ecosystems.
// Tailwind: className is just a string; every class in it must exist in the generated stylesheet
function Button({ variant = "primary", children }) {
  const base = "rounded-md px-3 py-1.5 text-sm font-medium transition";
  const styles = {
    primary:   "bg-indigo-600 text-white hover:bg-indigo-700",
    secondary: "bg-zinc-100 text-zinc-900 hover:bg-zinc-200",
  };
  return <button className={`${base} ${styles[variant]}`}>{children}</button>;
}

Where a class name becomes CSS: build time vs runtime

Tailwind runs a scanner at build: it reads every source file as plain text, collects every token that looks like a utility (px-3, hover:bg-indigo-700, md:grid-cols-2) and emits one rule per token into a static .css file. At runtime nothing happens — React sets a string on class, the browser matches it against a stylesheet that was finished before deploy.

CSS Modules are also build-time: the bundler rewrites .btn to .btn_x7f2a, emits the rewritten CSS, and gives the component styles.btn === "btn_x7f2a". Local by construction — two files can both define .btn.

Runtime CSS-in-JS (styled-components, Emotion) serialises the template literal during render, hashes it, and injects a <style> tag. That needs a client-side runtime and React context — which is why it needs "use client", a registry (useServerInsertedHTML) to get styles into server-rendered HTML, and cannot run in a Server Component at all. Vanilla Extract, Panda and StyleX keep the authoring model but move serialisation to build time.

// Scanner sees the token "bg-red-500" → the stylesheet gets .bg-red-500 { … }
<div className="bg-red-500" />

// Scanner sees "bg-", "-500" and a template — it emits nothing. Unstyled in production,
// and it "works" in dev only if some other file happens to contain the full class.
<div className={`bg-${color}-500`} />

// Full strings in a lookup: every value appears verbatim in the source
const tone = { red: "bg-red-500", blue: "bg-blue-500" }[color];
<div className={tone} />
Gotcha

The scanner does not evaluate JavaScript. String concatenation, replace(), props spliced into a class — all invisible. The rule: a utility must appear as one unbroken string somewhere in the scanned files.

Mechanism

Two of the three paths finish before deploy and produce a plain stylesheet; the third runs on every render in the browser, which is what makes it incompatible with Server Components.

Python bridge

Tailwind's scanner is Django's makemessages: it greps source text for literal strings and emits an entry for each one it can see. _("Hello") gets a catalogue entry; _(f"Hello {name}") runs fine and ships untranslated. className={`bg-${color}-500`} is the f-string case — valid code, no matching rule. CSS Modules map to module namespaces: styles.btn can't collide with another file's .btn for the same reason a.helper and b.helper don't.

Conditional classes — clsx + tailwind-merge

Template literals get unwieldy fast. clsx flattens its arguments, drops falsy values and joins what's left — nothing more. tailwind-merge (twMerge) knows Tailwind's utility groups and resolves conflicts: twMerge("p-2", "p-4") is "p-4", because in a plain concatenation both classes apply and the stylesheet order decides, not the order in your string. cn() composes the two; it is the convention in shadcn/ui and most Tailwind codebases.

import clsx from "clsx";
import { twMerge } from "tailwind-merge";

function cn(...inputs) { return twMerge(clsx(...inputs)); }

function Button({ variant = "primary", disabled, className, children, ...props }) {
  return (
    <button
      disabled={disabled}
      className={cn(
        "rounded-md px-3 py-1.5 text-sm font-medium transition",
        variant === "primary" && "bg-indigo-600 text-white hover:bg-indigo-700",
        variant === "ghost"   && "bg-transparent text-zinc-700 hover:bg-zinc-100",
        disabled              && "opacity-50 cursor-not-allowed",
        className              // caller overrides win — twMerge resolves px-3 vs px-6
      )}
      {...props}
    >
      {children}
    </button>
  );
}
Don't
<button className="btn btn-primary" {...props} />   // props.className replaces both classes
Do
<button className={cn("btn btn-primary", className)} {...props} />

Dynamic values: CSS variables through style, not class strings

Utilities cover a finite set of design decisions. A value computed at runtime — a hue from a colour picker, a progress percentage, a column count from data — is not a class, and no scanner can pre-generate it. Set it as a custom property on style and let one static rule read it:

// React sets custom properties with style.setProperty("--pct", …)
<div className="progress" style={{ "--pct": `${pct}%` }} />

/* one static rule, any value */
.progress { width: var(--pct); }
/* Tailwind v4 equivalent: className="w-(--pct)"  (v3: "w-[var(--pct)]") */
Gotcha

style is fine for a value or two, not as a styling strategy: no pseudo-classes, no media queries, no cascade, and it bypasses design tokens. The pattern is one variable in style, everything else in classes.

Tailwind v4 — CSS-first configuration

Tailwind v4 replaces tailwind.config.js with an @theme block in your CSS. Tokens are CSS variables, which means they're readable from any rule, any component, and from style.

/* globals.css */
@import "tailwindcss";

@theme {
  --color-primary: oklch(55% 0.2 260);
  --color-surface: oklch(98% 0 0);
  --font-sans: "Inter", sans-serif;
}

/* Utilities are generated from the tokens: bg-primary, text-surface, font-sans.
   Each is also a plain variable: var(--color-primary) */

Existing v3 projects can keep tailwind.config.js via @config. New projects: CSS-first.

Design tokens

Don't spread raw colours through JSX (text-[#1d4ed8], bg-zinc-100 on fifty files). Name decisions in @theme and reference the names: bg-primary, text-body. Rebranding and dark mode become one-file changes.

Code review
  • Dynamic class construction. `bg-${color}-500`, "text-" + size, classes assembled from props. Invisible to the scanner; passes in dev because another file contains the string, breaks in production. Replace with a lookup map of full strings (or cva).
  • Component swallows className. className="…" {...props} or no className prop at all. Consumers fork the component instead of extending it. Destructure and merge with cn().
  • Runtime CSS-in-JS in the App Router. styled.div in a file without "use client" fails at render; with it, every styled component is client JS and needs a useServerInsertedHTML registry for SSR. New code: Tailwind, CSS Modules, or a zero-runtime library.
  • Raw values instead of tokens. Arbitrary values (w-[137px], text-[#1d4ed8]) and hex colours in style. Unrebrandable, breaks dark mode. Put the value in @theme or question whether the design needs it.
  • Global CSS imported from a component. Next.js only accepts global stylesheets in the root layout; everything else must be a CSS Module or Tailwind. A global .card { … } from a leaf component leaks into every route.
  • !important to beat a conflict. Two utilities for the same property both applied — the fix is merging (twMerge) or removing the conflict, not !px-4.
  • A full stylesheet in style={{…}}. No hover, no breakpoints, no tokens. One custom property for a runtime value is the limit.

Recall
When does Tailwind turn px-3 into a CSS rule, and what does that imply for `bg-${color}-500`?
At build time: a scanner reads source files as text and emits a rule per utility string it finds verbatim. An interpolated class is never found, so no rule is generated — unstyled in production. Use a map of full strings.
What does this print? 
const cx = (...xs) => xs.flat().filter(Boolean).join(" ");
console.log(cx("btn", false && "x", "lg" === "lg" && "btn-lg", 0, null, ["a", undefined]));
console.log(cx("p-2", "p-4"));
btn btn-lg a, then p-2 p-4. clsx flattens, drops falsy values and joins; it never resolves conflicting utilities — the stylesheet order decides which of p-2/p-4 applies.
What does clsx do, what does tailwind-merge do, and what is cn()?
clsx: conditional joining of class strings. twMerge: resolves conflicting Tailwind utilities so the last one wins ("p-2 p-4" → "p-4"). cn = (...a) => twMerge(clsx(...a)), the shadcn/ui convention.
Why can't styled-components or Emotion be used inside a React Server Component?
They generate CSS during render on the client and need React context plus a style registry for SSR. Server Components have no client runtime, so those libraries require "use client"; zero-runtime alternatives (CSS Modules, Vanilla Extract, Panda, StyleX, Tailwind) resolve at build and work anywhere.
How do you feed a runtime value (a hue from state, a percentage) into CSS without generating class names?
Set a custom property on style — style={{ "--pct": `${pct}%` }} — and read it from one static rule: width: var(--pct) (Tailwind v4: w-(--pct)).
What's the bug in <button className="btn" {...props}>, and the fix?
If props.className exists, the spread overwrites "btn" (last key wins). Destructure className and merge: className={cn("btn", className)} {...props}.
Where does Tailwind v4 configuration live?
In CSS: @import "tailwindcss"; plus an @theme { --color-primary: …; } block. Each token becomes both a utility (bg-primary) and a CSS variable (var(--color-primary)). tailwind.config.js is only for v3 projects via @config.
