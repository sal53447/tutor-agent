State Primitives — useState, useReducer

useState and useReducer are the only two ways a component owns state; forms (4i), server state (4g) and stores (4h) are built on them or deliberately move state out of them. The model to carry forward: state is a snapshot per render, a setter schedules the next render rather than changing anything now, and React decides whether to re-render by reference equality. Every stale-closure and "it doesn't update" bug in React is one of those three rules being ignored.

useState — a slot, a setter, a scheduled render

const [count, setCount] = useState(0);

// The setter takes a value OR an updater function. The updater reads the
// latest *queued* state — use it whenever next depends on previous.
setCount(count + 1);
setCount(c => c + 1);

// Lazy init — the function runs once, on mount. Use for expensive defaults.
const [items, setItems] = useState(() => loadFromStorage());

Calling a setter does not change count in the running function — count is a const captured by this render. The setter enqueues an update and schedules a re-render; the next call of the component function reads the new value. All setter calls inside one event handler (and, since React 18, inside timers, promises and native listeners too) are batched into a single re-render.

function plus3Stale() {
  setCount(count + 1);   // queue: "replace with 1"
  setCount(count + 1);   // queue: "replace with 1" — same snapshot of count
  setCount(count + 1);   // → count becomes 1, one re-render
}
function plus3() {
  setCount(c => c + 1);  // queue: "apply fn"
  setCount(c => c + 1);
  setCount(c => c + 1);  // → 3, one re-render
}
Bail-out

The setter is Object.is-gated. setCount(0) while count is already 0 is dropped — no render of this component or its children (React may occasionally call the component once more and discard the result; it never re-renders the subtree). The same gate is what makes in-place mutation invisible, next block.

This is how React resolves the queue of updates for one state slot at the next render: a value replaces, an updater applies to the result so far. n is the snapshot the handler captured. What does this print? One value per line.

function applyQueue(initial, queue) {
  return queue.reduce((s, u) => (typeof u === "function" ? u(s) : u), initial);
}

Immutability invariant

React detects changes by reference equality (Object.is). If you mutate state in place, the setter receives the same reference it already holds — the update is dropped before any render. Always produce a new object / array.

// BAD
user.name = "new";
setUser(user);                // same ref → bail-out, no re-render

// GOOD
setUser({ ...user, name: "new" });

// Arrays:
setItems([...items, newItem]);                               // append
setItems(items.filter(x => x.id !== removedId));            // remove
setItems(items.map(x => x.id === id ? { ...x, ...p } : x));  // update one
setItems(items.toSorted(byName));                            // sort (ES2023; .sort() mutates)
The intermittent version

items.push(x); setItems([...items]) re-renders, so it looks fixed — but the previous render's snapshot was mutated too. Anything still holding it (a memoized child, a pending startTransition, StrictMode's second render) now sees data from the future. Mutation bugs surface as "works until it doesn't".

Mechanism

React never looks inside the object. A mutated object is Object.is-identical to the one in the slot, so the update dies at the gate.

When useReducer beats useState

When state has multiple related fields that update together ("complex transitions"), or when the next state depends on previous + an event. A reducer makes transitions explicit, keeps them in one place, and is testable without React — it's a pure function (state, action) → state.

const [state, dispatch] = useReducer(reducer, initialState);

function reducer(state, action) {
  switch (action.type) {
    case "add":   return { ...state, items: [...state.items, action.item] };
    case "clear": return { ...state, items: [] };
    default:      throw new Error("unknown action: " + action.type);
  }
}

<button onClick={() => dispatch({ type: "add", item })}>add</button>

dispatch does not call the reducer synchronously in your handler — it enqueues the action. React runs the reducer while preparing the next render (it may run it eagerly once to check for a bail-out, and twice in StrictMode), so the reducer must be pure: no fetch, no Date.now(), no mutation. import { useReducer } from "react";
import { createRoot } from "react-dom/client";

function reducer(state, action) {
  console.log("reducer:", action.type, "→ items so far:", state.items.length);
  switch (action.type) {
    case "add":   return { ...state, items: [...state.items, action.item] };
    case "clear": return { ...state, items: [] };
    default:      throw new Error("unknown action: " + action.type);
  }
}

function Cart() {
  const [state, dispatch] = useReducer(reducer, { items: [] });
  console.log("render, items =", state.items.length);
  const add = () => dispatch({ type: "add", item: "item " + (state.items.length + 1) });
  return (
    <>
      <button onClick={add}>add</button>{" "}
      <button onClick={() => { add(); add(); }}>add ×2</button>{" "}
      <button onClick={() => dispatch({ type: "clear" })}>clear</button>
      <ul>{state.items.map((it, i) => <li key={i}>{it}</li>)}</ul>
    </>
  );
}

useReducer — lazy initializer (third argument)

Like useState's function form, you can pass an init function as the third argument. React calls init(initialArg) once on mount. Use this when the initial state is expensive to compute or comes from a transformation of some argument — and to keep the reducer testable with a plain initial value.

function init(count) {
  return { items: [], count };   // runs once, not on every render
}

const [state, dispatch] = useReducer(reducer, 0, init);
// state → { items: [], count: 0 }

// To re-initialise when a prop changes, don't reach for an effect — remount with key:
<Cart key={userId} />

useRef as a non-rendering instance variable

When you need to track something across renders without triggering a re-render (interval IDs, previous values, abort controllers), reach for useRef. Covered in detail in 4e, but worth knowing it exists before you instinctively put interval IDs into state — every setIntervalId is a wasted render.

Forward pointers

State that must escape one component → 4h — Client state management (Zustand, Context). Lift it only when two siblings genuinely need the same piece. Submission state of a form (pending, last error) → useActionState in 4i, not a hand-rolled isSubmitting. Derived values (total from items) → compute during render; they are not state.

Python bridge

{ ...state, items: [...] } is {**state, "items": [...]}, and the discipline is the one you'd keep with @dataclass(frozen=True) + dataclasses.replace(): never mutate, always derive. A reducer is literally functools.reduce(reducer, actions, initial) — a pure fold over events, which is why 4c-14 tests it with no React at all. The part with no Python counterpart is the snapshot: inside a handler, count is a captured local, not self.count. There is no self.count += 1; you post an update and the next call of the function sees it.

Code review
  • Mutate-then-set. arr.push(x); setArr(arr) is dropped at the Object.is gate; setArr([...arr]) after a push "works" but corrupts the previous snapshot. The React Compiler's ESLint rule flags mutation of hook-returned values; until it's on, grep for .push(, .sort(, .splice( and = on state in handlers.
  • setX(x + 1) in anything asynchronous or repeated — intervals, promise callbacks, two calls in one handler. The closure holds a stale snapshot. Updater form: setX(c => c + 1).
  • Derived state in state. const [total, setTotal] kept in sync by an effect is one render behind and a second source of truth. Compute it during render; useMemo only if it's measurably expensive.
  • useState(expensive()). The argument is evaluated on every render and discarded after the first. Pass the function: useState(expensive) / useReducer(r, arg, init).
  • Impure reducers. A fetch, Date.now() or Math.random() inside a reducer runs at an unpredictable time and possibly twice (StrictMode, eager bail-out check). Do the effect in the handler, dispatch the result.
  • Eight useState calls that change together. Impossible transitions become representable (isLoading && error). One useReducer with explicit actions, or one object with a discriminated status field.
  • State for things that never render — interval ids, the previous value, a WebSocket. That's a ref (4e); each setter call is a pointless render.

Recall
Why does user.name = "new"; setUser(user) not trigger a re-render?
The setter receives the same object reference it already holds; React's Object.is check passes, so the update is dropped before any render.
A form with 8 fields that submit together — useState or useReducer?
useReducer: transitions between field states are explicit, impossible combinations can't be represented by accident, and the reducer is unit-testable with reduce.
What's the difference between useState(heavyFn()) and useState(heavyFn)?
The first calls heavyFn on every render and discards the result after the first; the second is lazy init — called once, on mount.
Inside one click handler with n === 0: setN(n + 1); setN(n + 1); setN(n + 1); — what is n after the re-render? And with setN(c => c + 1) three times?
1 — each call queues the literal value 1 computed from the same snapshot. With updaters, 3: each applies to the latest queued result. Either way, one re-render (batching).
What does this print? 
const apply = (s0, q) => q.reduce((s, u) => typeof u === "function" ? u(s) : u, s0);
const n = 0;
console.log(apply(n, [n + 5, c => c + 1, 42, c => c * 2]));
84: a value replaces (5, then 42), an updater applies to the running result (6, then 84). This is how React resolves one state slot's update queue at the next render.
When does useReducer's reducer run — inside dispatch, or later?
Later, while React prepares the next render (possibly eagerly once to check for a bail-out, and twice in StrictMode). dispatch only enqueues the action, so the reducer must be pure.
What single check decides whether a setter call re-renders the component?
Object.is(prev, next) on the state value. Equal → bail out, no render of the component or its children.
In useReducer(reducer, arg, init), when does init run and with what?
Once, on mount, as init(arg); its return value is the initial state. To re-initialise on a prop change, remount with key, not an effect.
