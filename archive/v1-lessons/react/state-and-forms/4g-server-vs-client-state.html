Server State vs Client State

Most "state management" pain in React apps is one category error: treating data that a server owns as if the component owned it. Split state by who owns it and the tooling picks itself — a cache for server data, useState (4h) for UI data, form actions (4i) for the handoff between them. Next.js (Part 5) assumes you have this split: Server Components fetch, Client Components hold toggles, and the cache sits in between.

Two kinds of state, one question: who owns it?

Server state is data whose source of truth is a remote system — a row in Postgres, a Stripe customer, a GitHub issue. The browser only ever holds a copy, which can be stale the moment it arrives, can be changed by other users, and must be refetched to be trusted. Client state is data the UI owns outright — an open modal, a draft in a text box, the selected tab. Nobody else can change it; it needs no refetch, no retry, no cache.

The classic anti-pattern is useState + useEffect for server data. It works in the demo and then you re-implement, one bug report at a time: deduplication (two components, two requests), the race when the id changes mid-flight, retries, background refetch, invalidation after a write, loading flicker. A query cache is those features, done once.

Don't

  const [user, setUser] = useState(null);

Mechanism

Server state flows left to right through a cache that holds a copy; client state never leaves the component. Writes go around the cache and come back as an invalidation.

Python bridge

A query cache is cachetools.TTLCache (or Django's cache.get_or_set) wired to a re-render. queryKey is the cache key — like functools.lru_cache, it is built from every argument, so ["user", id] not ["user"]. staleTime is the TTL: inside it, reads are served from memory with no I/O. The difference is what happens after the TTL: TTLCache evicts and the next read blocks on a miss; a query cache keeps the stale copy, returns it immediately, and refetches in the background (stale-while-revalidate). invalidateQueries(key) ≈ cache.delete(key) followed by an eager re-read for anyone currently looking at it. gcTime is the eviction of entries nobody is subscribed to — the part lru_cache does by size instead of time.

Where does this code run?

In Next.js App Router (Part 5), every component is a Server Component by default. A Server Component can fetch server state directly — it is on the server — so the initial copy of the data needs no client cache at all. The boundary is the most important mental-model shift coming from plain React.

Rule of thumb

Default to Server Component. Add "use client" only when you need interactivity (hooks, events, browser APIs). Push the boundary as far down the tree as possible — the smaller the client island, the less JS shipped.

TanStack Query v5 — the cache in front of the server

TanStack Query (née React Query) is a cache keyed by queryKey, with a subscription per component. useQuery returns the cached copy plus its status; useMutation runs a write and, on success, invalidates the keys the write affected so every subscriber refetches. v5 names: isPending (no data yet), isFetching (a request is in flight, possibly in the background), gcTime (was cacheTime).

import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";

function User({ id }) {
  const { data, isPending, error } = useQuery({
    queryKey: ["user", id],                       // every input to queryFn goes in the key
    queryFn: () => fetch(`/api/users/${id}`).then(r => r.json()),
    staleTime: 60_000,                            // serve from cache, no request, for 60 s
  });

  if (isPending) return <Spinner />;
  if (error) return <ErrorView error={error} />;
  return <h1>{data.name}</h1>;
}

function RenameButton({ id }) {
  const qc = useQueryClient();
  const rename = useMutation({
    mutationFn: (input) => fetch(`/api/users/${id}`, { method: "PATCH", body: JSON.stringify(input) }),
    onSuccess: () => qc.invalidateQueries({ queryKey: ["user", id] }),   // mark stale → subscribers refetch
  });
  return <button onClick={() => rename.mutate({ name: "new" })} disabled={rename.isPending}>Rename</button>;
}
Defaults that earn their keep
  • staleTime set per query (or globally in QueryClient). The library default is 0: every mount and every window focus refetches. That is correct for a stock ticker and wasteful for a settings page.
  • retry: 3 with exponential backoff is the default — turn it off for mutations and for 4xx responses, where retrying is wrong.
  • queryKey is hashed structurally: ["todos", { status: "done", page: 2 }] is one key, order of object fields irrelevant. Omit a parameter from the key and two different queries share one cache slot.
Not available in the sandbox

The playgrounds below can't import @tanstack/react-query. They hand-roll a ~15-line useQuery with a Map — the same mechanism, none of the edge cases. Treat it as the model, not the library.

Try it

A minimal useQuery: a module-level Map keyed by string, an in-flight promise shared by everyone who asks for the same key, and a staleTime. Three components mount, two of them with the same key — count the requests. Then: set staleTime to 0 and click unmount / remount; add a fourth <Name id={1} />; give the two id=1 components different keys by mistake ("user" + id vs "user:" + id) and watch the dedupe disappear.

// hand-rolled stand-in for TanStack Query's useQuery (no gc, no retry, no error state)
import { useState, useEffect } from "react";
import { createRoot } from "react-dom/client";

const cache = new Map();                         // key → { data, updatedAt, promise }
function fetchUser(id) {
  console.log("fetch user", id);
  return new Promise(r => setTimeout(() => r({ id, name: "user-" + id }), 30));
}

function useQuery(key, queryFn, { staleTime = 0 } = {}) {
  const entry = cache.get(key);
  const fresh = !!entry && !!entry.data && Date.now() - entry.updatedAt < staleTime;
  const [, rerender] = useState(0);
  useEffect(() => {
    if (fresh) return;                           // inside staleTime: serve the copy, no request
    const e = cache.get(key) || {};
    if (!e.promise) {                            // first asker starts the request; others share it
      e.promise = queryFn().then(data => { Object.assign(e, { data, updatedAt: Date.now(), promise: null }); });
      cache.set(key, e);
    }
    e.promise.then(() => rerender(n => n + 1));
  }, [key, fresh]);
  return { data: entry && entry.data, isPending: !(entry && entry.data) };
}

function Name({ id }) {
  const { data, isPending } = useQuery("user:" + id, () => fetchUser(id), { staleTime: 5000 });
  return <li>{isPending ? "loading…" : data.name}</li>;
}
function App() {
  const [show, setShow] = useState(true);
  return (
    <div>
      <button onClick={() => setShow(s => !s)}>{show ? "unmount" : "remount"}</button>
      {show && <ul><Name id={1} /><Name id={1} /><Name id={2} /></ul>}
    </div>
  );
}
createRoot(document.getElementById("root")).render(<App />);

The cache lifecycle: fresh → stale → refetch → gone

Every entry in the cache is in one of a few states, and two timers drive the transitions. staleTime says how long after a fetch the copy counts as fresh — fresh data is returned with no request. After that it is stale: still returned instantly, but the next trigger (a component mounts with the key, the window regains focus, the network reconnects, a refetchInterval ticks, or someone calls invalidateQueries) starts a background refetch. The UI keeps showing the stale copy until the new one lands; isFetching is true meanwhile, isPending is not. When the last subscriber unmounts the entry is inactive; after gcTime (default 5 min) with no subscribers it is garbage-collected, and the next mount starts from isPending again.

useQuery({
  queryKey: ["orders", { status }],
  queryFn: fetchOrders,
  staleTime: 30_000,          // fresh for 30 s: mounts and focus events don't refetch
  gcTime: 5 * 60_000,         // keep an unused entry 5 min so navigating back is instant
  refetchOnWindowFocus: true, // (default) stale entries refetch when the tab regains focus
  refetchInterval: false,     // polling, if you need it
});
staleTime ≠ gcTime

Raising gcTime does not stop refetches — it only keeps unused entries around longer. Raising staleTime stops refetches. Almost every "why does this refetch on every mount" question is staleTime: 0, the default.

Mechanism

Only the first fetch shows a spinner. Everything after is stale-while-revalidate: the stale copy stays on screen while the refetch runs, and gcTime only matters once nobody is subscribed.

TanStack Query's role in a Next.js app

Server Components handle initial data fetching — no Query needed there, and no isPending state: the page arrives rendered. Query's role shifts to:

  • Client-side data that changes after page load (polling, WebSocket-driven refetches, infinite scroll)
  • Mutation management: optimistic updates, cache invalidation after writes, isPending for buttons
  • Data that is genuinely per-session and client-only (a preferences endpoint, a draft autosave)

The classic useQuery fetch-on-mount pattern is largely replaced by RSC initial loads, or by Server Actions + revalidatePath for the write half (5e). Query stays relevant when the client needs its own long-lived cache with fine-grained invalidation; the hydration recipe (HydrationBoundary + dehydrate) lets a Server Component prefetch into that cache so the first client render has data.

Suspense mode

TanStack Query v5 ships useSuspenseQuery. It integrates with React <Suspense> — while data is loading the component suspends, the nearest Suspense boundary shows its fallback, and the component renders only once data is available. data is typed non-nullable; no isPending guard. Errors go to the nearest error boundary instead of an error field.

// No isPending check — the component only renders when data is ready
function UserCard({ id }) {
  const { data } = useSuspenseQuery({
    queryKey: ["user", id],
    queryFn: () => fetch(`/api/users/${id}`).then(r => r.json()),
  });
  return <h2>{data.name}</h2>;
}

// Wrap in Suspense at the call site
<Suspense fallback={<Skeleton />}>
  <UserCard id={42} />
</Suspense>
Waterfalls

Two useSuspenseQuery calls in one component run sequentially: the first suspends the render before the second is reached. Use useSuspenseQueries for parallel fetches, or split into sibling components under one boundary.

SWR — the lightweight alternative

SWR (from Vercel) is a simpler alternative to TanStack Query. Same stale-while-revalidate semantics, smaller API surface: a key, a fetcher, and mutate for invalidation. Good pick for projects that only need basic caching and don't need the full Query feature set (infinite queries, mutation lifecycle, devtools, per-query retry policy).

import useSWR from "swr";
const { data, error, isLoading } = useSWR("/api/user", url => fetch(url).then(r => r.json()));
Code review
  • Server data in useState + useEffect. No dedupe, no cancel on id change (the race in 4g-15), no retry, no invalidation after writes — each one arrives later as a bug ticket. Reach for the query cache or a Server Component.
  • Parameter missing from queryKey. queryKey: ["orders"] with queryFn: () => fetchOrders(status) means every status shares one slot: switching filters shows the previous filter's rows. Every input to queryFn goes in the key; @tanstack/eslint-plugin-query's exhaustive-deps flags it.
  • Default staleTime: 0 left in place on a read-heavy page. Every mount and tab focus refetches. Set a global default in QueryClient (e.g. 30 s) and lower it per query where freshness matters.
  • Mutation without invalidation. A useMutation whose onSuccess doesn't invalidate (or setQueryData) the affected keys leaves every other subscriber showing stale rows until a focus event happens to refetch.
  • Over-broad invalidation. invalidateQueries() with no key after every write refetches the whole screen. Invalidate the prefix that changed: ["orders"] matches ["orders", { page: 2 }].
  • Retrying a 4xx or a mutation. The default retry (3×, backoff) is for flaky reads. A 400/401/404 won't get better, and retrying a POST can duplicate the write — set retry: false there, or a retry function that checks the status.
  • Query in a Client Component that a Server Component could have rendered. If the data is needed on first paint and doesn't change client-side, fetch it in the Server Component and pass it down; keep Query for data that moves after load.

Recall
What distinguishes server state from client state, and why does each need a different tool?
Server state is a copy of data owned elsewhere (DB/API): it goes stale, needs dedupe, retry, refetch and invalidation — a cache (TanStack Query / SWR / RSC). Client state is owned by the UI (modal open, draft, selected tab): no staleness, just placement in the tree — useState, context, a store.
staleTime vs gcTime in TanStack Query v5?
staleTime: how long after a fetch the copy is fresh — fresh entries are served with no request (default 0). gcTime: how long an entry with no subscribers is kept before deletion (default 5 min). Only staleTime affects whether a mount or focus refetches.
Which events trigger a refetch of a stale query?
A component mounting with that key, the window regaining focus, the network reconnecting, a refetchInterval tick, and invalidateQueries. Fresh entries ignore all but the interval and explicit invalidation.
What does this print? 
let now = 0; const cache = new Map();
async function query(key, fn, { staleTime }) {
  const hit = cache.get(key);
  if (hit && now - hit.at < staleTime) { console.log("fresh"); return hit.data; }
  console.log(hit ? "stale" : "miss");
  const data = await fn(); cache.set(key, { data, at: now }); return data;

await query("u", async () => 1, { staleTime: 60 });
now = 59; await query("u", async () => 1, { staleTime: 60 });
now = 60; await query("u", async () => 1, { staleTime: 60 });
miss, fresh, stale. At 59 the age is under 60 → fresh; at exactly 60 the < check fails → stale, refetch.
What happens in the cache when a mutation's onSuccess calls invalidateQueries({ queryKey: ["user", 1] })?
Matching entries are marked stale (not deleted). Entries with active subscribers refetch immediately in the background; the old copy stays rendered (isFetching true, isPending false) until the new data swaps in.
Why must every argument of queryFn appear in queryKey?
The key is the cache slot. ["orders"] with fetchOrders(status) gives all statuses one slot, so changing the filter shows the previous filter's data until a refetch. Keys are hashed structurally, so ["orders", { status }] is correct and object field order doesn't matter.
What is the race condition in useEffect(() => { fetchUser(id).then(setUser); }, [id]) and the minimal fix?
If id changes before the first response lands, the slower (older) response can arrive last and overwrite the newer one. Fix: an ignore flag flipped in the effect cleanup (or an AbortController aborted in cleanup), so a stale response is dropped.
In a Next.js App Router app, what is TanStack Query still for?
Not initial loads — Server Components do those. It handles data that changes after load (polling, infinite scroll, sockets), mutation lifecycle with invalidation/optimistic updates, and client-only session data. HydrationBoundary lets a Server Component prefetch into the client cache.
