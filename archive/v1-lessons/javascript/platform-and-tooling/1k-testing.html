Testing — Philosophy and Tools

Tools

  • Vitest — modern, fast, Vite-native. Default choice for new projects.
  • Jest — the incumbent. Still everywhere. Slower, more config.
  • Node's built-in test runner (node --test) — decent for small libraries, no ecosystem yet.
  • Playwright — the E2E standard.
  • React Testing Library — component testing for React (we cover in 4m).
import { describe, it, expect, vi } from "vitest";
import { add } from "./math";

describe("add", () => {
  it("sums two numbers", () => {
    expect(add(1, 2)).toBe(3);
  });

  it("calls a callback", () => {
    const cb = vi.fn();
    doWork(cb);
    expect(cb).toHaveBeenCalledWith("done");
  });
});

Async tests

Make the test function async and await the result. Missing the await is a common trap — the test body resolves before the assertion runs, the promise is never checked, and the test passes green even when the code is broken.

import { describe, it, expect } from "vitest";
import { fetchUser } from "./api";

describe("fetchUser", () => {
  it("returns a user object", async () => {
    const user = await fetchUser(1);   // MUST await
    expect(user.id).toBe(1);
  });

  // Trap — missing await silently passes:
  it("(broken) always passes", () => {
    fetchUser(999);                    // no await — test exits before promise settles
    // expect below is never reached; Vitest sees no assertion failure
    expect(false).toBe(true);         // unreachable!
  });

  // Testing that a promise rejects:
  it("rejects on invalid id", async () => {
    await expect(fetchUser(-1)).rejects.toThrow("Invalid id");
  });
});
Missing await trap

Enable Vitest's expect.assertions(n) or ESLint's @typescript-eslint/no-floating-promises rule in test files to catch un-awaited promises. Otherwise async test bugs are invisible.

Setup and teardown — beforeEach / afterEach

import { beforeEach, afterEach, describe, it, expect, vi } from "vitest";

describe("UserService", () => {
  let db;

  beforeEach(async () => {
    db = await createTestDb();     // fresh DB before each test
  });

  afterEach(async () => {
    await db.close();              // clean up after each test
    vi.restoreAllMocks();          // reset any spies/stubs
  });

  it("saves a user", async () => {
    await db.users.create({ name: "Alice" });
    expect(await db.users.count()).toBe(1);
  });
});

beforeAll / afterAll run once per describe block — use for expensive setup (starting a test server). beforeEach / afterEach run per test — use for state that must be isolated.

vi.fn() vs vi.spyOn()

// vi.fn() — create a standalone mock function from scratch
const mockFetch = vi.fn().mockResolvedValue({ ok: true });
doWork(mockFetch);
expect(mockFetch).toHaveBeenCalledOnce();

// vi.spyOn() — wrap an existing method on an object, preserving the original
const spy = vi.spyOn(console, "error").mockImplementation(() => {});
triggerError();
expect(spy).toHaveBeenCalledWith(expect.stringContaining("oops"));
spy.mockRestore(); // restores original console.error

Rule of thumb: vi.fn() when you're injecting a dependency; vi.spyOn() when you need to observe or suppress a real method on an existing object without replacing the whole thing.

The philosophy — in one sentence

Test behavior, not implementation. A test that checks "when the user clicks submit, the onSubmit prop is called with the form values" survives refactors. A test that checks "the component has a handleClick method" breaks every time you rename something.

Python bridge

Vitest ≈ pytest. describe/it/expect ≈ class Test: def test_* + assert. vi.fn() ≈ unittest.mock.MagicMock. The philosophy is also the same — favor integration-ish tests for user-observable behavior.

Code review — anti-patterns
  • Tests that re-implement the code they test. If both would have the same bug, the test is useless.
  • Mocking your own code. Usually a sign the boundary is in the wrong place.
  • Snapshot tests on everything. Great for highly structured output (AST dumps, generated code). Abused as "lazy assertions" elsewhere.
  • Flaky tests ignored or retried. Fix them or delete them — a flaky test is worse than no test.
1. This test always passes. Why? How do you fix it?
it("rejects on bad input", () => {
  expect(validateAsync("bad")).rejects.toThrow();
});

The test function is synchronous — it returns before the promise settles. Vitest sees no thrown error and marks it passed. Fix: make the test async and add await: await expect(validateAsync("bad")).rejects.toThrow();

2. When should you use vi.spyOn rather than vi.fn()?

Use vi.spyOn when the thing you want to observe already exists as a method on an object (e.g., console.warn, Date.now, a class method). It wraps the real implementation so you can assert on calls and optionally restore it. Use vi.fn() when you're providing a fresh mock to inject as a dependency.

3. You have a beforeEach that seeds a database and an afterEach that clears it. A test fails mid-run. Does afterEach still run?

Yes. Vitest (and Jest) always run afterEach regardless of whether the test passed or failed — that's the whole point of teardown. Same semantics as finally.
