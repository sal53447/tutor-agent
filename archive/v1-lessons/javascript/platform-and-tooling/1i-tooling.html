Tooling Ecosystem

Three mechanisms explain almost every "works on my machine" in a JS repo: how a version range in package.json becomes an exact version in the lockfile, how import "zod" becomes a file path at runtime, and which tool turns source into what actually ships. Express (Part 3), React (Part 4) and Next.js (Part 5) all assume you can read a package.json, trust a lockfile, and know why two copies of a package end up in node_modules.

Package managers: npm, pnpm, yarn

  • npm — ships with Node, ubiquitous. Fine.
  • pnpm — one content-addressable store on disk, hard-linked into each project; strict by default (you can only import what you declared). Faster, smaller, catches phantom dependencies. Recommended.
  • yarn — yarn 1 is legacy; yarn Berry (4.x) exists with niche adoption. Its ideas (lockfile, workspaces) are in npm and pnpm now.

One-off tool execution without a global install:

npx create-next-app@latest my-app      # npm: uses the local binary if present, else a temp install
pnpm dlx create-next-app@latest my-app # pnpm: always an isolated temp install, never touches node_modules
corepack enable                        # pins the package manager itself via "packageManager" in package.json
Phantom dependencies

npm and yarn hoist: every transitive package lands flat in node_modules/, so import "lodash" works even though only one of your dependencies declared it. It breaks the day that dependency drops lodash. pnpm's layout (node_modules/.pnpm/ + symlinks) makes undeclared imports fail immediately — which is the point.

Python bridge

package.json ≈ pyproject.toml; pnpm-lock.yaml ≈ uv.lock; npm ci / pnpm install --frozen-lockfile ≈ uv sync --frozen; npx / pnpm dlx ≈ uvx / pipx run. The structural difference: a venv holds one version of each package, so pip must solve a single global constraint set and fails on conflicts. node_modules is a tree — package A can depend on zod@3 while B depends on zod@4, each gets its own nested copy, and resolution walks up directories from the importing file. That is why installs rarely conflict, why bundles get fat, why instanceof across two copies of a class fails (1g), and why peerDependencies exist at all: "I need your React, not a second one".

  },
  "dependencies": { "express": "^5.1.0", "zod": "^3.24.0" },
  "devDependencies": { "vite": "^6.0.0", "vitest": "^3.0.0", "typescript": "^5.7.0" }
}
  • "type": "module" — .js files are ES modules (1e). Without it they are CommonJS.
  • dependencies vs devDependencies — what the deployed artifact imports at runtime vs what builds and tests it. npm ci --omit=dev in a Docker image installs only the former.
  • scripts — npm run x runs with node_modules/.bin on PATH, so "lint": "eslint ." finds the local binary.
  • engines + engine-strict=true in .npmrc — fail the install on the wrong Node instead of failing in production.

A published package adds the entry-point fields the resolver reads: exports (with conditions) replaces the older main.

{
  "name": "my-lib",
  "exports": {
    ".":        { "types": "./dist/index.d.ts", "import": "./dist/index.js", "require": "./dist/index.cjs" },
    "./server": { "import": "./dist/server.js" }
  },
  "files": ["dist"]
}

peerDependencies — "use the host's copy"

A package lists a peer dependency when it needs the host project to provide that package rather than installing its own copy. A React component library lists react as a peer: it needs React, but a second copy would break hooks and context (two React objects, two dispatchers).

{
  "peerDependencies": { "react": ">=18" },
  "devDependencies":  { "react": "^19.0.0" }
}

Publishing a library: framework deps go in peerDependencies (and in devDependencies so your own tests run). Consuming one: npm ≥ 7 auto-installs missing peers; pnpm warns — either way, declare the peer in your own dependencies so the version is yours to control.

Semver ranges and lockfiles

  • ^1.2.3 — >=1.2.3 <2.0.0. The default npm install writes. The first non-zero component is fixed, so ^0.2.3 means >=0.2.3 <0.3.0 — 0.x libraries treat minor as breaking.
  • ~1.2.3 — >=1.2.3 <1.3.0. Patch updates only.
  • 1.2.3 — exact. Rare in apps; the lockfile already pins.

The range is a policy; the lockfile (package-lock.json, pnpm-lock.yaml) is the decision: the exact version of every package in the tree plus its integrity hash. Commit it. Then two commands with different contracts:

npm install        # resolve ranges; reuse the lock where it still satisfies, otherwise update it
npm ci             # delete node_modules, install exactly the lock; FAIL if lock and package.json disagree
pnpm install --frozen-lockfile   # pnpm's npm ci (the default in CI environments)
Mechanism

npm install is allowed to change the lockfile; npm ci only reads it. Reproducible builds depend on CI never taking the top path.

function parse(v) { return v.split(".").map(Number); }
function below(got, want) {
  for (let i = 0; i < 3; i++) { if (got[i] < want[i]) return true; if (got[i] > want[i]) return false; }
  return false;
}
function satisfies(range, version) {
  const op = range[0] === "^" || range[0] === "~" ? range[0] : "";
  const want = parse(range.slice(op.length));
  const got = parse(version);
  if (below(got, want)) return false;                                   // never below the floor
  if (op === "") return got.every((n, i) => n === want[i]);              // exact
  if (op === "~") return got[0] === want[0] && got[1] === want[1];       // patch may move
  const lock = want[0] !== 0 ? 0 : want[1] !== 0 ? 1 : 2;              // caret: first non-zero part is fixed
  return got.slice(0, lock + 1).every((n, i) => n === want[i]);
}

Module resolution — how import "zod" finds a file

A specifier is one of three things. Relative (./x.js) and absolute (/x.js, file:, node:fs) resolve directly. A bare specifier ("zod", "@scope/pkg/sub") triggers the node_modules walk: starting from the importing file's directory, look for node_modules/zod/package.json, and if it is not there, try the parent directory, up to /. The first hit wins — which is why a nested copy shadows the root one.

Inside the package, exports decides the file. Its conditions are matched in order: "import" or "require" depending on how you loaded it, "types" for TypeScript, custom ones like "browser", "workerd", "react-server" for bundlers and runtimes, then "default". No exports → fall back to main → index.js. Subpaths not listed in exports are unreachable (ERR_PACKAGE_PATH_NOT_EXPORTED) — deep imports into dist/ are gone on purpose.

import { z } from "zod";                 // bare → node_modules walk → exports["."]["import"]
import { z } from "zod/v4";              // subpath → exports["./v4"]
import { readFile } from "node:fs";      // built-in, never node_modules
import { db } from "./db.js";            // relative; the extension is mandatory in ESM
Gotcha

Bundlers (Vite, Turbopack) and TypeScript (moduleResolution: "bundler") run their own resolver that mostly agrees with Node, except where it does not: extension-less relative imports, the "browser" condition, and path aliases (@/components) exist only in the bundler. Code that works in Vite and throws ERR_MODULE_NOT_FOUND under plain node is usually one of those.

Bundlers and transpilers

Node runs source files; browsers need a bundle (one request instead of hundreds of module loads, tree-shaken, minified) and both need TypeScript and JSX turned into JS. Two separate jobs, often in one tool:

  • Vite — default for new front-end projects. Dev server serves native ESM and transpiles on demand with esbuild (instant start); production build bundles with Rollup (Rolldown, its Rust successor, is taking over). The runtime for Vitest too.
  • esbuild — Go, very fast transpile + bundle, few plugins. Embedded in Vite, tsx, and most tools.
  • Turbopack — Next.js's Rust bundler: default for next dev since 15, production builds in newer releases. Replaces webpack inside Next.
  • webpack — legacy, widely deployed, slow, infinitely configurable.
  • SWC / Babel — transpilers only (TS/JSX → JS, syntax down-levelling). SWC is Rust and what Next and Vitest use; Babel is the plugin ecosystem (React Compiler ships as a Babel plugin).
  • tsc — type-checks; emitting JS with it is now the exception. Typical pipeline: tsc --noEmit for types, esbuild/SWC for output, Node's type stripping for scripts.
Gotcha

Transpilers process one file at a time and never see types. const enum, namespace merging and export type re-exports without type (isolatedModules) break under esbuild/SWC/type stripping. TypeScript's verbatimModuleSyntax: true makes tsc reject the same code, so the problem surfaces in type-check instead of at runtime.

Code review
  • CI runs npm install. It may rewrite the lock and silently resolve newer versions. npm ci / pnpm install --frozen-lockfile, and fail the pipeline if the lock changes.
  • Runtime dependency in devDependencies. Works locally, crashes in the --omit=dev Docker image with ERR_MODULE_NOT_FOUND. Conversely, a linter or @types/* in dependencies bloats every install.
  • Undeclared (phantom) import. import "lodash" with no lodash in package.json — works through hoisting until a transitive dep changes. pnpm or eslint-plugin-import's no-extraneous-dependencies catches it.
  • Unpinned engines and package manager. No engines, no packageManager, no .nvmrc: lockfile format drift between npm versions, Node API drift between laptops and CI. Pin all three; corepack enable.
  • Deep imports into a package's dist/. import "pkg/dist/internal.js" bypasses exports and breaks on the next patch release. Use the public subpath or ask for one.
  • Two copies of a singleton package. Hooks error "Invalid hook call", instanceof failing, duplicated context — check pnpm why react / npm ls react; the fix is a peer dependency or an overrides entry, not a hack.
  • Library published with ^-free exact pins. Forces every consumer into duplicate copies. Apps pin via the lockfile; libraries declare ranges.

npm install vs npm ci — the one-line contract of each?
install resolves ranges and may rewrite the lockfile; ci wipes node_modules, installs exactly the lock, and fails if lock and package.json disagree. CI and Docker use ci (pnpm: --frozen-lockfile).
How does Node resolve import "zod"?
Bare specifier → walk up from the importing file's directory looking for node_modules/zod/package.json; first hit wins (nearest shadows root). Then exports["."] conditions in order (import/require, custom, default), else main, else index.js.
Why does peerDependencies exist, and when do you use it?
Because node_modules nests duplicates: a library that needs the host's single copy of React (hooks, context) declares react as a peer instead of installing its own. Use it for framework deps when publishing a library; apps never need it.
What is a phantom dependency and which tool catches it?
An import of a package you never declared, reachable only because npm/yarn hoisted a transitive dep flat into node_modules. pnpm's strict layout makes the import fail; ESLint's import/no-extraneous-dependencies flags it.
Which TS features break under single-file transpilers (esbuild, SWC, type stripping)?
const enum, namespace merging, re-exporting types without the type keyword — anything needing cross-file type info. isolatedModules / verbatimModuleSyntax make tsc reject them up front.
