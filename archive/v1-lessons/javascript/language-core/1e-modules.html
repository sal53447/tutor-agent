Modules — ESM vs CommonJS

JS has two module systems, both still in use. This is the biggest "papercut" of the Node ecosystem.

ESM (the modern, standard)

// file: math.js
export function add(a, b) { return a + b; }
export const PI = 3.14159;
export default function mul(a, b) { return a * b; }

// file: main.js
import mul, { add, PI } from "./math.js";
import * as math from "./math.js";
import("./math.js").then(m => m.add(1,2));  // dynamic import

CommonJS (Node legacy)

// math.js
function add(a, b) { return a + b; }
module.exports = { add };
module.exports.default = function mul(a,b) { return a*b; };

// main.js
const { add } = require("./math.js");
Python bridge

ESM is what from math import add feels like. CommonJS is closer to Python's importlib — it's runtime-evaluated and supports conditional imports naturally. In Python you'd never think about this split. In Node you absolutely will.

ESM equivalents of __dirname / __filename

CJS provides __dirname and __filename as globals. ESM doesn't — use import.meta.url instead.

import { fileURLToPath } from "node:url";
import path from "node:path";

const __filename = fileURLToPath(import.meta.url);
const __dirname  = path.dirname(__filename);

// Or as a one-liner for the directory:
const dir = new URL(".", import.meta.url).pathname;

Prefer named exports over default exports

Default exports are anonymous — editors and refactoring tools can't reliably rename them across files. Named exports are explicit and autocomplete correctly.

// Prefer this:
export function add(a, b) { return a + b; }
export function sub(a, b) { return a - b; }

// Over this:
export default function(a, b) { return a + b; }  // what's it even called?

Exception: framework conventions sometimes require a default export (Next.js page components, React Router route elements). Follow the framework there; everywhere else use named.

Circular imports — the silent gotcha

ESM handles circular imports by returning a partially-constructed module — the binding exists but its value is undefined at the time of the first import. The code doesn't throw; it just fails at runtime with a confusing undefined is not a function.

// a.js
import { b } from "./b.js";
export const a = () => b();   // b is undefined when a.js first loads

// b.js
import { a } from "./a.js";
export const b = () => a();

Fix: break the cycle by extracting the shared dependency into a third module, or restructure so one side only imports at call time.

How to pick, and how to mix

  • New code: always ESM. Set "type": "module" in package.json.
  • Old/legacy: CJS still works. require can load CJS modules only (until Node 22's experimental require(esm)).
  • Bundlers (Vite, esbuild, webpack, Turbopack) abstract the split for you — they consume both and output whatever the target wants.
Code review — barrel files

A barrel file (index.ts that re-exports everything from a folder) is a popular pattern but a performance footgun: it defeats tree-shaking and forces tools to parse files you don't import. Prefer direct imports from the actual file. Teams with large apps (Airbnb, Vercel) actively remove barrels for load-time wins.
