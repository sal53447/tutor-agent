Functions, Closures, and this

Functions are first-class values: you pass them around, return them, store them in variables. JS leans heavily on higher-order functions — more than Python culturally does. Three mechanisms from this lesson carry the rest of the curriculum: hoisting/TDZ explains what a module can reference before it runs (1e), closures are how React hooks remember state between renders (4c, 4d — every "stale closure" bug is this lesson), and the this rules explain why a method handed to setTimeout or an event listener breaks.

Three function forms

// 1. Function declaration — hoisted, has its own `this`, has `arguments`
function add(a, b) { return a + b; }

// 2. Function expression — not hoisted, otherwise same
const add2 = function (a, b) { return a + b; };

// 3. Arrow function — not hoisted, NO own `this`, NO `arguments`, cannot be `new`'d
const add3 = (a, b) => a + b;

Arrow functions are not just shorter syntax. They capture this lexically from the enclosing scope. This is often what you want — and occasionally exactly what you don't.

...rest replaces arguments. arguments is array-like, not a real array, and doesn't exist in arrow functions; a rest parameter is a real array and works in every form:

function old() { console.log(arguments[0]); }          // legacy
const sum = (...nums) => nums.reduce((a, b) => a + b, 0); // modern
sum(1, 2, 3);  // 6

Hoisting and the Temporal Dead Zone

Before a scope's code runs, the engine registers every declaration in it. Function declarations are fully hoisted — name and body — so you can call them before the line they appear on. let/const/class bindings are registered too, but stay uninitialized until their line executes: that window is the Temporal Dead Zone (TDZ), and touching the binding inside it throws a ReferenceError — even via typeof.

// Function declaration — fine, fully hoisted
greet("world");               // "hello world"
function greet(name) { return `hello ${name}`; }

// const function expression — TDZ
sayBye("world");              // ReferenceError: Cannot access 'sayBye' before initialization
const sayBye = (name) => `bye ${name}`;
Gotcha

var declarations are hoisted (to undefined), which is why calling a var-assigned function before the assignment returns TypeError: sayBye is not a function — a different and more confusing failure mode. Another reason to never use var.

Closures — the real workhorse

A closure is a function plus the scope it was created in. The function keeps a live link to that scope's bindings — not copies of their values — so it sees later changes and can make its own. Identical to Python closures, but used much more idiomatically in JS.

function makeCounter() {
  let count = 0;                       // captured
  return {
    inc: () => ++count,
    get: () => count,
  };
}
const c = makeCounter();
c.inc(); c.inc();
c.get();  // 2 — count is private and shared between the two methods
Python bridge

Python has closures (nested def), but the culture prefers classes for anything stateful, and writing to a captured variable needs nonlocal. JS closures write to captured bindings freely and are used for private state, module state, event handlers, and anywhere you'd reach for a class in Python. Recognize this pattern — you'll see it constantly.

The this keyword — four binding rules

this is decided at call time, by the shape of the call expression — not by where the function was defined. That's the entire trick. Arrow functions opt out: they have no this of their own and read the enclosing scope's.

// 1. Default — `this` is undefined (strict mode / modules) or globalThis (sloppy)
function show() { console.log(this); }
show();

// 2. Implicit (method call) — `this` is the object before the dot
const obj = { name: "x", show() { console.log(this.name); } };
obj.show();           // "x"

// 3. Explicit — `.call`, `.apply`, `.bind`
show.call({ name: "y" });

// 4. `new` — `this` is the freshly created instance
function Foo() { this.x = 1; }
new Foo();            // { x: 1 }
The classic trap

When you pass a method as a callback, it loses its this: setTimeout(obj.show, 100) runs show with no object before the dot, so this is undefined and this.name throws. Fixes: setTimeout(() => obj.show(), 100) or setTimeout(obj.show.bind(obj), 100). Arrow functions sidestep it by not having their own this — they inherit from the enclosing scope.

Mechanism

Read the call site, not the definition. Precedence when rules collide: new > bind > explicit call/apply > method call > plain call. A method passed as a callback is invoked as f() — the "plain" column — which is the whole trap.

Python bridge

Python binds self at attribute access: f = obj.method produces a bound-method object, so f() still works. JS has no bound-method creation on access — const f = obj.method gives you the bare function, and f() runs with this === undefined. The equivalent of Python's automatic binding is explicit: obj.method.bind(obj), an arrow wrapper () => obj.method(), or a class-field arrow (below). Python's @staticmethod is what every JS arrow function effectively is: no implicit receiver.

Class field arrow functions — modern this binding

When you need a method that is safe to pass as a callback (an event handler, a setTimeout target), declare it as a class field arrow. The arrow is created per-instance in the constructor with this already lexically bound — no .bind(this) needed. Cost: one function object per instance instead of one shared on the prototype, which only matters for thousands of instances.

class Button {
  label = "Click me";

  // Arrow field: `this` is always the instance, even when passed as a callback
  handleClick = () => {
    console.log(this.label);
  };
}

const btn = new Button();
element.addEventListener("click", btn.handleClick); // works, no bind needed

Code review
  • Unbound method passed as a callback. el.addEventListener("click", this.onClick), setTimeout(obj.method, …), arr.map(this.format) — all run the method with this === undefined. Wrap in an arrow, bind in the constructor, or use a class-field arrow. ESLint: @typescript-eslint/unbound-method.
  • Arrow function as an object-literal method or prototype method that uses this. { name: "x", greet: () => this.name } never sees the object. Use method shorthand greet() {}.
  • Default to arrows; use function only when you need this or hoisting. A plain utility that reads this is a smell — refactor toward explicit parameters.
  • var in loops with closures. One shared binding → every callback sees the last value. let/const; ESLint no-var, no-loop-func.
  • Closures over mutable state in long-lived callbacks. The React "stale closure": an effect or interval that captured a value from a previous render keeps using it. Functional updates (setN(n => n + 1)) and correct dependency arrays (4d) are the fix — the mechanism is this lesson's.
  • Reading a let/const before its line in module initialisation order. Shows up as a TDZ ReferenceError that only appears with circular imports (1e). Declarations up top; no top-level side effects that call across modules.
  • arguments. Legacy, array-like, absent in arrows. Use rest parameters. ESLint: prefer-rest-params.

Recall
What is the Temporal Dead Zone, and what does reading a binding inside it do?
The span from the start of a scope until a let/const/class declaration's line runs. The binding exists but is uninitialized; reading it — even with typeof — throws a ReferenceError.
Which function form is hoisted with its body, and what happens when you call a var-assigned function before its assignment?
Only function declarations. A var binding is hoisted as undefined, so calling it throws TypeError: x is not a function rather than a ReferenceError.
Do closures capture values or bindings? What does that mean for let count = 0 captured by two arrows?
Bindings. Both arrows reference the same count in the same scope, so a write through one is visible through the other — and the scope outlives the function call that created it.
What does this print? 
const fns = [];
for (var i = 0; i < 3; i++) fns.push(() => i);
console.log(fns.map(f => f()));
const gns = [];
for (let j = 0; j < 3; j++) gns.push(() => j);
console.log(gns.map(g => g()));
[3, 3, 3] then [0, 1, 2]. var gives one function-scoped binding, already 3 when the closures run; let creates a fresh binding per iteration.
The four this binding rules, in precedence order.
new f() → the new instance; f.call/apply(o) and f.bind(o) → o; o.f() → o; plain f() → undefined in strict mode / modules. Arrow functions ignore all four and use the enclosing scope's this.
Why does setTimeout(obj.show, 100) fail when show reads this.name, and what are the three fixes?
The timer calls the bare function with no object before the dot, so this is undefined. Fix with an arrow wrapper () => obj.show(), obj.show.bind(obj), or declare show as a class-field arrow.
What does this refer to inside an arrow function, and can .call() change it?
The this of the scope where the arrow was defined; it has none of its own. call, apply, bind and new cannot change it (new on an arrow throws).
How do Python and JS differ when you do f = obj.method and then call f()?
Python creates a bound method on attribute access, so f() still has self. JS hands you the bare function; f() runs with this === undefined unless you bind it.
