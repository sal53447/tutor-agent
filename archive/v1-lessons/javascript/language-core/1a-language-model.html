The Language Model — history, runtime, values, equality

This lesson makes you fluent in the shape of JS — the runtime, the value system, the equality rules, the legacy corners. Every later lesson assumes it: closures (1b) are references to the same binding, prototype lookup (1c) walks references, React's render model (4a) decides "did state change?" with the equality rule taught here, and half of the bugs a Python engineer writes in week one are truthiness and || defaults.

The 5-minute history

Brendan Eich designed JS in 10 days at Netscape in 1995. Originally Mocha, then LiveScript, then renamed to JavaScript to ride Java's marketing. The languages are unrelated. The spec is now called ECMAScript and updates yearly.

ES2015 ("ES6") was the inflection point — let, const, arrow functions, classes, Promises, modules, destructuring, template literals. Modern JS is a legitimately good language if you stick to the post-2015 subset.

Python bridge

Python was designed deliberately by one person over years. JS was designed in 10 days, then governed by committee under a strict "don't break the web" constraint. This explains most of the "weird JS" you'll encounter — it's fossils from that rushed design that cannot be removed without breaking existing websites.

The runtime model

JavaScript is single-threaded, event-loop-based, dynamically typed, garbage-collected, and JIT-compiled. Only one thing runs at a time. All concurrency happens through a task queue (covered in depth in 1f).

Python bridge

Python is also single-threaded (GIL) and dynamically typed. The key difference: Python uses threads with asyncio as an opt-in, while JS is non-blocking by default. If you block the JS thread, the entire program freezes — this shapes every JS API toward async.

Values vs references: two buckets

There are exactly two kinds of things in JS. The seven primitives (string, number, boolean, null, undefined, symbol, bigint) are copied and compared by value. Everything else — arrays, functions, dates, objects, Maps — is a reference to one heap object: assignment copies the arrow, not the object, and === compares arrows.

// Primitives: value equality
"hello" === "hello"   // true
42 === 42             // true

// Objects: reference equality only
{ a: 1 } === { a: 1 } // false — two distinct objects
[1, 2] === [1, 2]     // false

const x = { a: 1 };
const y = x;
x === y               // true — same reference
Gotcha

JS has no built-in deep equality. You write it yourself or reach for lodash.isEqual / assert.deepStrictEqual. Python's == on lists/dicts does value equality; JS's === on objects does not.

Mechanism

x === y is true because both arrows point at the same heap object; y.a = 2 is visible through x. s === t is true because strings compare by content, and changing t never touches s.

typeof, null, and symbol

typeof 42            // "number"
typeof "s"           // "string"
typeof undefined     // "undefined"
typeof null          // "object"   ← the 1995 fossil
typeof Symbol()      // "symbol"
typeof 10n           // "bigint"
typeof (() => {})    // "function" — functions are objects; typeof special-cases them
typeof []            // "object"   — use Array.isArray(x)

typeof null === "object" — null is a primitive, but the type tag was never fixed. Check for null explicitly with === null, not typeof. undefined means "never assigned" (missing property, bare let x;, no return); null means "deliberately empty" — APIs return it on purpose.

symbol creates a guaranteed-unique key: const id = Symbol("id"). Two calls with the same description are never equal. Symbols power the iterator protocol (Symbol.iterator, lesson 1d) and other well-known hooks the runtime uses to extend built-in behaviour.

Equality: ==, ===, Object.is

Three operators, all different. == (abstract equality) performs type coercion and produces pretzel logic. === is strict — no coercion. Object.is is like === but treats NaN and -0 differently; React uses Object.is to decide whether state changed.

// Why == is banned in practice:
0 == "0"           // true
0 == ""            // true
"" == false        // true
null == undefined  // true
[] == false        // true

// === is the real equality:
0 === "0"          // false
null === undefined // false
NaN === NaN        // false (the one weird case)
Object.is(NaN, NaN) // true
Object.is(0, -0)    // false (=== says true)
Rule

Always use ===. The only legitimate == is x != null, which uniquely catches both null and undefined in one check. Every respectable ESLint config enforces this via the eqeqeq rule.

Truthiness — the Python-developer trap

The eight falsy values: false, 0, -0, 0n, "", null, undefined, NaN. Everything else is truthy — including [] and {}, and including the strings "0" and "false".

if (arr) { … }             // always true for an array, even []
if (arr.length) { … }      // "non-empty?" — the JS idiom
if (count) { … }           // skips 0 — usually a bug; use count != null
if (flag === "false") { … } // query params and env vars are strings
Python bridge

In Python, if my_list: means "is this non-empty?" because empty collections are falsy. In JS, if (arr) is true for [] and if (obj) is true for {}; only the eight falsy values above are false. The idiomatic checks are if (arr.length), if (Object.keys(obj).length), and if (x != null) for "is it set". 0 and "" are falsy in both languages, which is exactly why || defaults are a trap in both — but Python's or has no ?? to escape to. This catches every Python dev at least once.

Your daily tools: ?? and ?.

Nullish coalescing ?? defaults only on null/undefined. Optional chaining ?. short-circuits to undefined on null/undefined without throwing. ??= assigns only when the target is nullish.

// || treats 0 and "" as "missing" — often a bug:
const portA = process.env.PORT || 3000;  // BUG if PORT is "" or "0"
const portB = process.env.PORT ?? 3000;  // only falls back if unset

// Optional chaining:
const city = user?.address?.city;   // undefined if any link missing
callback?.();                        // only calls if defined
arr?.[0];                            // nil-safe index

// Assign-if-missing:
cache[key] ??= computeExpensive(key);
Rule of thumb

Default to ?? for defaults. Use || only when you genuinely want to coalesce on all falsies (rare). Use ?. aggressively — it's the closest JS gets to Python's getattr(x, 'y', None) chains, and much nicer.

const is a binding, not a value

const arr = [1, 2, 3];
arr.push(4);      // legal — the binding is unchanged
arr = [];         // TypeError — rebinding forbidden

const means "this name always refers to the same value." It does not freeze the value. Immutability in JS is convention + spread operators + (optionally) tools like Immer. This matters enormously in React, where mutating state in place doesn't trigger re-renders — React compares the old and new reference with Object.is, and a mutated object is the same reference.

const user = { name: "A", tags: ["x"] };
Object.freeze(user);
user.name = "B";        // silently ignored (TypeError in strict mode / modules)
user.tags.push("y");    // works — freeze is shallow
Code review
  • var. Reject. Function-scoped, hoisted to undefined, re-declarable. Use const; fall back to let when you need to reassign. ESLint: no-var, prefer-const.
  • ==. Reject unless it is x != null. The coercion chain in 1a-19 is the bug. ESLint: eqeqeq with { "null": "ignore" }.
  • if (count) / if (name) on values where 0 or "" is legal. Silently skips real data. Use != null or compare explicitly.
  • opts.x || default for config. Almost always a bug — 0, "" and false are valid settings. Use ??. ESLint: @typescript-eslint/prefer-nullish-coalescing.
  • Comparing objects with === and expecting value equality. Shows up as a React effect that re-fires every render because [{ a: 1 }] is a new reference each time, or a test asserting result === expected. Use deepStrictEqual / toEqual; memoise or key by a primitive.
  • Object.freeze used as "security" or deep immutability. It's shallow and advisory; nested objects stay mutable. Use it for constants tables at most; for real immutability use spread-on-update or Immer.
  • Global isNaN(x). Coerces first, so isNaN("abc") is true. Use Number.isNaN(x); for "is this a usable number" use Number.isFinite(x).

A colleague writes const ms = opts.timeoutMs || 5000;. What's the bug?

If the caller passes timeoutMs: 0 (a legitimate "no timeout" value in some APIs), they get 5000 instead. Fix: opts.timeoutMs ?? 5000.

if (user.preferences.darkMode) { ... } — two things can go wrong. Which two?

(a) If user.preferences is undefined, this throws TypeError. Use user.preferences?.darkMode. (b) If darkMode is the string "false" (from, say, a query param), the condition is truthy. Don't rely on coercion — explicitly check === true or parse the value.

false true — two literals are two objects, c shares a's reference. true false — == coerces [] → "" → 0; === stops at the type mismatch. fallback 0 — || skips every falsy value, ?? only null/undefined.
Where do === and Object.is disagree, and who uses Object.is?
NaN (=== false, Object.is true) and 0 vs -0 (=== true, Object.is false). React's state and dependency comparisons use Object.is.
Does const obj = { a: 1 } stop obj.a = 2? Does Object.freeze(obj) stop obj.nested.x = 2?
No and no. const fixes the binding, not the value; Object.freeze is shallow. Immutability in JS is convention: copy on update (spread, structuredClone, Immer).
Why is Number.isNaN preferred over global isNaN?
Global isNaN coerces its argument first, so isNaN("abc") is true. Number.isNaN only returns true for the actual NaN value.
