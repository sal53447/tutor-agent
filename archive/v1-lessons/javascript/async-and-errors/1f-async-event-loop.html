Async & Concurrency — the Event Loop

This is the single most important lesson in the JavaScript topic. Everything on the JS side — timers, promises, fetch, React effects, Express handlers, Next.js server components — sits on this model.

The model: one thread, two queues

JS runs on a single thread with a call stack. When the stack is empty, the runtime pulls work from queues:

  • Microtask queue — resolved Promise callbacks, queueMicrotask. Drained completely before the next render or macrotask.
  • Macrotask queue — setTimeout, setInterval, I/O callbacks, setImmediate (Node). Processed one at a time.

Python bridge

asyncio has the same shape — one thread, a loop, a ready queue — but you start it explicitly with asyncio.run(), and only coroutines participate. In JS the loop is always running and everything is on it: a click handler, a timer, a resolved promise, a module's top-level await. Closest mappings: Promise.resolve().then(cb) ≈ loop.call_soon(cb); setTimeout(cb, 0) ≈ loop.call_later(0, cb) — and like asyncio, "later" is a lower priority than "soon", which is why 3 prints before 2.

Promises — the lifecycle

A Promise is in one of three states: pending, fulfilled (with a value), or rejected (with an error). Once settled, it's immutable — a second resolve() or reject() is silently ignored.

const p = new Promise((resolve, reject) => {
  setTimeout(() => resolve(42), 100);
});

p.then(v => console.log(v))
 .catch(err => console.error(err))
 .finally(() => console.log("done"));
Mechanism

The executor runs immediately and synchronously; only the handlers are deferred. Every .then/.catch/.finally returns a new promise, which is what makes chaining work.

async / await — the real API

async function getUser(id) {
  try {
    const res = await fetch(`/api/users/${id}`);
    if (!res.ok) throw new Error("Not ok");
    return await res.json();
  } catch (err) {
    console.error(err);
    throw err;  // let caller decide
  }
}
Python bridge

Syntactically identical to Python's async def / await. Semantically different in one key way: Python's asyncio is opt-in (you must run an event loop explicitly). In JS, the event loop is always running — every function can be async, every top-level can await (in ESM). There's no "blue/red function" social split in JS; async is ambient.

Combinators

// Parallel — fail if any fails
const [a, b] = await Promise.all([fetchA(), fetchB()]);

// Parallel — wait for all, get results and errors
const results = await Promise.allSettled([fetchA(), fetchB()]);

// First to settle (resolve OR reject) — rarely what you want
await Promise.race([op, timeout]);

// First to FULFILL (ignore rejections)
await Promise.any([a, b, c]);
Sequential-in-a-loop bug
// BAD — fetches sequentially, 10x slower
for (const id of ids) {
  const u = await fetchUser(id);
  users.push(u);
}

// GOOD — fetches in parallel
const users = await Promise.all(ids.map(fetchUser));

This is the single most common async bug in JS code. If the iterations are independent, map + Promise.all. If they depend on each other, for...of is correct.

Exercise

loadUsers works but is slow: it waits for each user before requesting the next. Make the requests run in parallel while keeping the result order. fetchUser is instrumented — the tests check how many requests were in flight at once.

// --- instrumented fake API (leave as is)
let inFlight = 0, maxInFlight = 0;
function fetchUser(id) {
  inFlight++; maxInFlight = Math.max(maxInFlight, inFlight);
  return new Promise(resolve => setTimeout(() => { inFlight--; resolve({ id, name: `user-${id}` }); }, 5));
}

// --- fix this
async function loadUsers(ids) {
  const users = [];
  for (const id of ids) {
    const u = await fetchUser(id);
    users.push(u);
  }
  return users;
}

Cancellation with AbortController

Promises can't be cancelled. The convention is a signal: the caller creates an AbortController, passes controller.signal down, and anything that takes a signal (fetch, timers you write, streams) stops when abort() is called.

const ctrl = new AbortController();
fetch(url, { signal: ctrl.signal });
setTimeout(() => ctrl.abort(), 5000);  // cancel after 5s

// Or, built in: a signal that aborts itself
fetch(url, { signal: AbortSignal.timeout(5000) });
Exercise

Implement withTimeout(task, ms). task(signal) is an async function that honours an AbortSignal. If it finishes within ms, resolve with its value; otherwise abort it and reject with an error whose name is "TimeoutError". Don't leave a dangling timer when the task wins.

// A task that honours the signal (leave as is)
function sleep(ms, signal) {
  return new Promise((resolve, reject) => {
    const t = setTimeout(() => resolve("slept " + ms), ms);
    signal?.addEventListener("abort", () => { clearTimeout(t); reject(signal.reason); });
  });
}

Unhandled rejections — Node crashes, browser warns

// This promise rejects with no handler — behaviour differs by environment
async function boom() { throw new Error("oops"); }
boom();  // fire-and-forget (no await, no .catch)

// Node (since v15): process exits with code 1 — UnhandledPromiseRejection
// Browser: fires window.unhandledrejection event, logs a warning, continues running

// Guard at module level in Node:
process.on("unhandledRejection", (reason) => {
  console.error("Unhandled rejection:", reason);
  process.exit(1);  // explicit exit so the error is visible in CI logs
});
Gotcha

The browser's leniency masks bugs during development. If you write backend Node code and test it only in a browser-like environment (Vitest with jsdom, for example), unhandled rejections that would crash production may silently pass tests. Run critical async tests in a Node environment.

Code review
  • Unhandled rejection. Every promise needs a .catch or a surrounding try/catch. Unhandled rejections crash the Node process in modern versions.
  • Forgotten await. asyncFn() without await returns a floating promise — often a silent bug. ESLint rule: @typescript-eslint/no-floating-promises.
  • Sequential await in a loop over independent work. Reviewers look for for … await and ask whether iterations depend on each other.
  • Don't nest .then chains. Use await. It reads top to bottom.
  • Avoid mixing callbacks and promises. Node utilities have .promises variants (fs.promises, fs.readFile via util.promisify).
  • No timeout on external calls. Every fetch to a third party gets an AbortSignal.timeout; otherwise one slow upstream pins your request handlers.

Recall
In what order does the runtime run: synchronous code, microtasks, macrotasks? What drains completely vs one at a time?
Sync code to completion → all microtasks (and any they enqueue) → one macrotask → microtasks again → next macrotask.
What does this log, and why? 
async function f() {
  console.log("a");
  await 1;
  console.log("b");
}
f();
console.log("c");

a, c, b. await always suspends the function at least once even if the awaited value is already resolved. Execution resumes on the microtask queue, after the current synchronous block finishes.

Name the four Promise combinators and the one-line difference between Promise.race and Promise.any.
all (fail-fast, ordered values), allSettled (every outcome), race (first to settle, fulfilled or rejected), any (first to fulfil; rejects only if all reject, with an AggregateError).
Why is for (const id of ids) await fetchUser(id) usually a bug, and when is it correct?
It serialises independent requests — N × latency instead of 1 ×. Correct only when iteration n+1 needs the result of n (or you must limit concurrency deliberately).
How does AbortController relate to a Promise, and what's the shortcut for a timeout signal?
Promises can't be cancelled; the controller's signal is passed into the work, which listens for abort and rejects with signal.reason. AbortSignal.timeout(ms) builds a self-aborting signal with a TimeoutError.
What happens to an unhandled promise rejection in Node vs in the browser?
Node (≥15) exits the process with code 1; the browser fires window.unhandledrejection, logs, and carries on — so browser-like test environments can hide a crash.
