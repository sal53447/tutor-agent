Error Handling — Hierarchies, cause & Async Boundaries

1f covered how work is scheduled; this lesson covers how failure travels through it. Every boundary later in the curriculum — Express error middleware (3b), Zod validation (3d), React error boundaries, Next.js error.tsx — assumes you can answer two questions about any line: what can it throw, and where does that surface — as a synchronous throw, as a rejected promise, or nowhere at all.

The model: throw anything, catch at boundaries

throw accepts any value and catch receives any value. The idiom is to throw an Error (or a subclass) — it is the only thing that carries a stack — and to catch at boundaries: a request handler, a job runner, one try around a group of awaits. Code in between lets errors propagate.

function parsePort(raw) {
  const n = Number(raw);
  if (!Number.isInteger(n) || n < 1 || n > 65535) throw new RangeError(`bad port: ${raw}`);
  return n;
}

try {
  parsePort("http");
} catch (err) {
  // err is whatever was thrown — not necessarily an Error
  if (err instanceof Error) console.error(err.name, err.message);   // RangeError bad port: http
  else console.error("non-Error thrown:", err);
} finally {
  // runs either way — after a return or throw in try or catch too
}

Built-ins you will actually meet: TypeError (called undefined, wrong shape), RangeError, SyntaxError (JSON.parse), DOMException with name "AbortError" / "TimeoutError" (fetch + AbortSignal, 1f), and Node system errors, which are plain Errors distinguished by code ("ENOENT", "ECONNREFUSED") rather than by subclass.

Gotcha

throw "not found" is legal. The catch site gets a string: no stack, err.message is undefined, instanceof Error is false. Under TypeScript strict the catch variable is typed unknown (useUnknownInCatchVariables) precisely because of this — narrow before touching .message. ESLint: @typescript-eslint/only-throw-error.

Your own hierarchy: class … extends Error

JS ships no domain hierarchy; you build one. The base class must get two things right: name — every subclass reports "Error" unless you set it, and that is what stack traces and loggers print — and a stable, machine-readable code, so handlers never match on message text. Everything else (status, issues, the id that was not found) is a plain field.

class AppError extends Error {
  constructor(message, { code = "APP_ERROR", cause } = {}) {
    super(message, { cause });
    this.name = this.constructor.name;   // "NotFoundError", not "Error" — see Gotcha
    this.code = code;
  }
}

class NotFoundError extends AppError {
  constructor(resource, id, options) {
    super(`${resource} ${id} not found`, { ...options, code: "NOT_FOUND" });
    this.resource = resource;
  }
}

class HttpError extends AppError {
  constructor(status, message, options) {
    super(message, { ...options, code: `HTTP_${status}` });
    this.status = status;
  }
}

const e = new NotFoundError("user", 42);
console.log(e.name, e.code, e instanceof AppError, e instanceof Error);  // NotFoundError NOT_FOUND true true
console.log(String(e));                                                   // NotFoundError: user 42 not found
Gotcha

this.constructor.name is whatever the minifier left: in a production browser bundle it can be "a". For code that ships minified, write this.name = "NotFoundError" literally in each subclass (or keep names: esbuild --keep-names, terser keep_classnames). Server-side Node is unminified, so the shortcut is fine there.

Narrowing is instanceof. The rule that goes with it: handle what you own, rethrow what you don't.

Do
async function findUser(id) {
  try {
    return await users.findOrThrow(id);          // may throw NotFoundError — or whatever the driver throws
  } catch (err) {
    if (err instanceof NotFoundError) return null;   // expected: the caller asked "maybe"
    throw err;                                       // not ours → the boundary logs it and maps to 500
  }
}
Don't
async function findUser(id) {
  try {
    return await users.findOrThrow(id);
  } catch (err) {
    console.log(err);
    return null;   // the database being down now means "no such user"
  }
}
instanceof has an identity problem

It compares against one specific class object. Two copies of a library in node_modules, an error crossing a worker or iframe boundary, or a class re-bundled twice each give you an error whose instanceof is false against your import. That is the second reason code exists: err.code === "NOT_FOUND" survives all of those.

Python bridge

raise HttpError(…) from err ≈ throw new HttpError(…, { cause: err }) — with one difference: Python also chains implicitly (__context__) whenever you raise inside except; JS chains only if you pass cause. Forget it and the original stack is gone. except NotFoundError as e: ≈ catch (e) { if (e instanceof NotFoundError) … else throw e; } — there is no per-type catch clause, so the narrow-and-rethrow is written by hand every time; except (A, B) is instanceof A || instanceof B. A bare catch is a bare except:, and in JS "everything" includes strings and undefined. finally is identical; there is no else clause. traceback.print_exc() ≈ console.error(err) — Node prints the whole cause chain.

error.cause — wrapping without losing the original (ES2022)

new Error(message, { cause }) stores whatever you pass as err.cause. Each layer rewraps in its own vocabulary and keeps the layer below, so the handler at the top can say "profile unavailable" while the log still shows the socket timeout that started it.

// Layer 1 — transport. Knows about sockets and signals.
async function fetchJson(url) {
  let res;
  try {
    res = await fetch(url, { signal: AbortSignal.timeout(3000) });
  } catch (err) {                       // DOMException { name: "TimeoutError" } or TypeError (DNS, refused)
    throw new NetworkError(`${url}: ${err.name}`, { cause: err });
  }
  if (!res.ok) throw new HttpError(res.status, `GET ${url} → ${res.status}`);
  return res.json();
}

// Layer 2 — API client. Knows about users, not sockets.
async function loadProfile(id) {
  try {
    return await fetchJson(`/api/users/${id}`);
  } catch (err) {
    throw new HttpError(503, `profile ${id} unavailable`, { cause: err });
  }
}

// What the handler holds after a timeout:
//   HttpError: profile 42 unavailable
//     [cause] NetworkError: /api/users/42: TimeoutError
//       [cause] DOMException [TimeoutError]: The operation was aborted due to timeout

cause is just a property, so walking the chain is a loop:

function causeChain(err) {
  const chain = [];
  for (let e = err; e; e = e.cause) chain.push(`${e.name}: ${e.message}`);
  return chain;
}
// ["HttpError: profile 42 unavailable", "NetworkError: /api/users/42: TimeoutError", "TimeoutError: The operation was aborted due to timeout"]
Errors don't serialise

message, stack and cause are non-enumerable own properties, so JSON.stringify(err) and { ...err } drop all three and keep only the fields you assigned yourself — a bare Error becomes {}, the NotFoundError above becomes {"name":"NotFoundError","code":"NOT_FOUND","resource":"user"}: a shape that looks fine in a log and has lost the message and the stack. Node's console.error(err) / util.inspect print the nested [cause]; browser devtools show it too. For structured logs use the logger's error serialiser (pino's err key, serialize-error) and check it walks cause.

Mechanism

cause is an ordinary property, so the chain is a singly linked list that ends at undefined — which is exactly the loop condition in causeChain(). The DOMException at the tail is what the handler at the head would otherwise never see.

A throw inside async is a rejection

An async function never throws synchronously. Whatever happens in its body — an explicit throw, a TypeError on line one, a rejected await — becomes a rejection of the promise it returned, and the caller sees it only through await or .catch. That makes the position of the await relative to try load-bearing:

async function fails() { throw new Error("boom"); }

function a() {
  try { return fails(); }            // returns the (rejected) promise; try is already exited
  catch (err) { return "caught in a"; }
}

async function b() {
  try { return await fails(); }      // awaits here → the rejection surfaces inside try
  catch (err) { return "caught in b"; }
}

a().catch(err => console.log("a:", err.message));   // a: boom      — catch in a never ran
b().then(v => console.log("b:", v));                 // b: caught in b

Rule: inside try, return await. Outside try, return promise is fine. Same trap with finally: return promise runs the finally block before the promise settles, so a cleanup there (release a lock, clear a timer) happens while the work is still in flight. ESLint: @typescript-eslint/return-await (default in-try-catch).

Two failure channels

The mirror image — a non-async function that returns a promise and can throw — gives the caller two failure channels, and they usually handle only one:

function load(id) {
  if (!id) throw new TypeError("id required");   // synchronous
  return fetch(`/api/items/${id}`);              // asynchronous
}
load().catch(report);   // TypeError escapes before .catch is ever attached
Do

Mark it async. Now the TypeError is a rejection like everything else, and one .catch / one try around the await covers both.

The forgotten await inside try

The most expensive version of the previous block. The call is made, the body runs up to its first await, the returned promise is dropped on the floor — and the catch two lines down is not attached to it.

async function save(row) { throw new Error("db down"); }

async function handler() {
  try {
    save({ id: 1 });                     // forgot await — the rejected promise floats
    return "saved";
  } catch (err) {
    return "failed: " + err.message;     // never runs
  }
}

handler().then(console.log);
// saved
// …then, once the microtask queue drains: unhandled rejection "db down"
//   Node ≥ 15: process exits with code 1. Browser: window "unhandledrejection", page carries on.
Python bridge

Python tells you: calling save(...) without await creates a coroutine that never runs, and the interpreter prints RuntimeWarning: coroutine 'save' was never awaited. JS does the opposite — the body starts immediately, side effects and all, and nothing is said until the rejection has nobody to go to. The lint rule is your warning: @typescript-eslint/no-floating-promises (needs type information).

Fire-and-forget on purpose
void audit.log(event).catch(report);   // explicit: not awaited, failures reported, lint satisfied

void is the conventional marker that the floating promise is intentional; the .catch is what makes it safe. .catch(() => {}) is the same shape with the safety removed.

Throws that reach no try at all

The "nowhere" channel. A callback handed to the host — setTimeout, an event listener, a stream's data handler — runs later on an empty stack. The try that was open when you registered it is long gone. Only the new Promise executor is special: it catches a throw and turns it into a rejection. A timer callback gets no such wrapper: the throw climbs to the top and is an uncaughtException — Node exits with code 1, the browser logs it to the console.

function risky() { throw new Error("late"); }

try {
  setTimeout(risky, 0);                                                      // registers the timer; try exits
  new Promise(() => risky()).catch(e => console.log("promise:", e.message));  // executor throw → rejection
} catch (err) {
  console.log("caught:", err.message);                                       // never runs
}
// promise: late
// Uncaught Error: late   ← the timer callback runs on an empty stack: uncaughtException, Node exits 1

Same family: an EventEmitter that emits "error" with no "error" listener throws from emit() — and since sockets and streams emit from I/O callbacks, that throw is also uncaught. The fix is the same everywhere: handle inside the callback (or attach the "error" listener), and surface failures through a promise you await (see withTimeout in 1f). This is exactly what 3b hits next: in Express 4 an async handler's rejection reaches nobody, and a throw inside a stream callback never reaches the error middleware either.

AggregateError — many failures, one throw

Three combinators, three different stories about partial failure. Promise.all rejects with the first reason and the rest are invisible (not unhandled — all subscribed to them — just dropped). Promise.any rejects only if every input rejects, and then with an AggregateError holding every reason in .errors. Promise.allSettled never rejects; you decide what a partial failure means, and the way to say "these N failed" as one error is to build the AggregateError yourself.

const fail = (msg) => Promise.reject(new Error(msg));

try {
  await Promise.any([fail("primary down"), fail("mirror down")]);
} catch (err) {
  console.log(err instanceof AggregateError, err.errors.map(e => e.message));
  // true [ "primary down", "mirror down" ]
}

const results = await Promise.allSettled([fail("a"), Promise.resolve(1), fail("b")]);
const failed = results.filter(r => r.status === "rejected").map(r => r.reason);
if (failed.length) {
  throw new AggregateError(failed, `${failed.length}/${results.length} jobs failed`);
}
Python bridge

AggregateError(errors, message) ≈ ExceptionGroup(message, errors) (3.11). There is no except*; you catch the group and iterate .errors.

Throw vs Result

Nothing in a JS signature says what a function throws — there are no checked exceptions, and TypeScript does not track them. Throwing is right for the unexpected: bugs, infrastructure down, anything the immediate caller cannot act on and a boundary several frames up will log and map. For expected outcomes the direct caller must branch on — validation, parsing, a lookup that may miss — returning a value puts the failure in the type, where the compiler enforces that it is handled.

type Result<T, E = Error> = { ok: true; value: T } | { ok: false; error: E };

function parsePort(raw: string): Result<number, RangeError> {
  const n = Number(raw);
  if (!Number.isInteger(n) || n < 1 || n > 65535) {
    return { ok: false, error: new RangeError(`bad port: ${raw}`) };
  }
  return { ok: true, value: n };
}

const r = parsePort(process.env.PORT ?? "3000");
if (!r.ok) { console.error(r.error.message); process.exit(1); }
listen(r.value);   // r.value is only typed on this side of the guard — listen(): elided

You already use this shape: Promise.allSettled returns { status, value | reason }; Zod's safeParse returns { success, data | error } (3d). Libraries like neverthrow add map/andThen so you are not writing if (!r.ok) return r; at every layer — which is the cost of Result: it does not propagate by itself.

Rule of thumb
  • Throw for programmer errors (TypeError), infra failures, anything handled at a boundary rather than by the caller.
  • Result when the caller branches on the outcome, and on public API surfaces where "what can fail" must be visible in the type.
  • Neither extreme: Result for everything means every layer re-wraps; throwing for control flow (throw to mean "not found" in a hot loop) is slow and reads as a bug.

Code review
  • Catch-all that continues. catch (err) { log(err); return null; } or .catch(() => {}) turns a database outage into "no result" and the caller proceeds with garbage. Narrow with instanceof / code, handle what you own, rethrow (or next(err)) the rest.

  • Rewrapping without cause. catch (err) { throw new Error("load failed"); } discards the one error that had the real stack. Pass { cause: err }; ESLint core preserve-caught-error flags the omission (built-in constructors only — it won't flag new LoadError(...) without cause).
  • return promise inside try. The catch never fires and finally runs before the work completes. return await; @typescript-eslint/return-await.
  • Floating promise. A call without await, return, or .catch — inside try it is a catch that does nothing, elsewhere it is a crash in Node. @typescript-eslint/no-floating-promises; if intentional, void p.catch(report).
  • Logging JSON.stringify(err) or { ...err }. Drops message, stack and cause (non-enumerable) and keeps only own enumerable fields (name, code, …) — a bare Error logs as {}, a custom one logs as a plausible-looking object with no stack.   • Boundaries. Unexpected errors propagate to one top-level handler per surface (Express 4-arity middleware, Next.js error.tsx, a job runner's loop). process.on("uncaughtException") / "unhandledRejection" is log-then-exit, never log-and-continue: after one the process state is unknown.

Recall
What must a custom error base class set so logs and handlers are useful, and what does passing { cause } do?
A correct name (otherwise every subclass reports "Error") and a machine-readable code so handlers never match on message text. new Error(msg, { cause }) stores the original as err.cause; JS only chains if you pass it, unlike Python's implicit __context__.
A catch handles NotFoundError and must not hide anything else. Write the pattern.

if (err instanceof NotFoundError) return null; throw err; Handle what you own, rethrow what you don't. A catch-all that returns null turns a database outage into "no such user".

Is err instanceof Error always true inside catch (err)? What else is instanceof unreliable for?

No: throw "x" is legal and gives a string with no stack or message. instanceof also fails across duplicate package copies, workers and iframes, so err.code is the stable discriminator.

What does this print? 
async function work() {
  await null;
  console.log("work done");
  throw new Error("x");
}
async function run() {
  try { return work(); }
  catch (err) { console.log("catch"); }
  finally { console.log("finally"); }
}
run().catch(err => console.log("outer", err.message));

finally, work done, outer x. return promise leaves try before the rejection exists, so catch is skipped and finally runs while the work is in flight. return await inside try fixes both.

An async function throws on its first line. Does the caller see a synchronous throw? What about a plain function that returns a promise?

No: an async function turns every throw into a rejection, so one .catch or try/await covers it. A non-async function that can throw and return a promise has two failure channels; mark it async.

Inside try, you call an async save() without await and it rejects. What happens in Node vs the browser?

catch never runs. Node (15+) reports an unhandled rejection and exits with code 1; the browser fires unhandledrejection and carries on. Lint: no-floating-promises; intentional fire-and-forget is void p.catch(report).

When should a function throw and when should it return a Result?

Throw for the unexpected (bugs, infrastructure down) that a boundary logs and maps. Return { ok, value } | { ok: false, error } for expected outcomes the direct caller must branch on (validation, lookup miss). Result does not propagate by itself, so using it everywhere means rewrapping at every layer.
