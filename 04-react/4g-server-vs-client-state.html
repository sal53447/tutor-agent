Server State vs Client State

Where does this code run?

In Next.js App Router (Part 5), every component is a Server Component by default. Understanding the boundary is the most important mental model shift coming from plain React.

Rule of thumb

Default to Server Component. Add "use client" only when you need interactivity (hooks, events, browser APIs). Push the boundary as far down the tree as possible — the smaller the client island, the less JS shipped.

The single most important distinction in modern React. Server state is data owned by a remote system (the DB), cached on the client. Client state is data owned by the UI (toggles, form drafts, selection).

They need different tools. Using useState + useEffect for server data is the classic anti-pattern — you end up reimplementing caching, deduplication, retries, background refetching, pagination, optimistic updates, and staleness. TanStack Query (née React Query) exists precisely to solve this.

import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";

function User({ id }) {
  const { data, isLoading, error } = useQuery({
    queryKey: ["user", id],
    queryFn: () => fetch(`/api/users/${id}`).then(r => r.json()),
  });

  if (isLoading) return ;
  if (error) return ;
  return 
{data.name}
;
}

function UpdateButton({ id }) {
  const qc = useQueryClient();
  const m = useMutation({
    mutationFn: (input) => fetch(`/api/users/${id}`, { method: "PATCH", body: JSON.stringify(input) }),
    onSuccess: () => qc.invalidateQueries({ queryKey: ["user", id] }),
  });
  return ;
}
Defaults that earn their keep
  • staleTime: 60_000 — don't refetch for 60s.
  • retry: 2, refetchOnWindowFocus true for read-heavy UIs.
  • Use queryKey as the "cache key" — includes all params.

TanStack Query's role in a Next.js app

Server Components handle initial data fetching — no Query needed there. Query's role shifts to:

  • Client-side data that changes after page load (polling, WebSocket-driven refetches)
  • Mutation management: optimistic updates, cache invalidation after writes
  • Any data that is genuinely client-only (user preferences stored in an API, not in the DB query)

The classic useQuery fetch-on-mount pattern is largely replaced by RSC initial loads. Query stays relevant for the mutation half of the picture.

Suspense mode

TanStack Query v5 ships useSuspenseQuery. It integrates with React <Suspense> — while data is loading the component suspends, the nearest Suspense boundary shows its fallback, and the component renders only once data is available (no isLoading guard needed).

// No isLoading check needed — component only renders when data is ready
function UserCard({ id }) {
  const { data } = useSuspenseQuery({
    queryKey: ["user", id],
    queryFn: () => fetch(`/api/users/${id}`).then(r => r.json()),
  });
  return 
{data.name}
;
}

SWR — the lightweight alternative

SWR (from Vercel) is a simpler alternative to TanStack Query. Same stale-while-revalidate semantics, smaller API surface. Good pick for projects that only need basic caching and don't need the full Query feature set (infinite queries, mutations with cache invalidation, etc.).

import useSWR from "swr";
const { data, error, isLoading } = useSWR("/api/user", url => fetch(url).then(r => r.json()));
Python bridge

There's no exact Python analog. Closest cultural equivalent: your Python code knows the difference between a local dict and a Redis cache you hit repeatedly. TanStack Query is "the client's Redis" for API responses — with invalidation, TTLs, stale-while-revalidate built in.
