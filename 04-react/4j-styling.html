Conditional classes — clsx + tailwind-merge

Template literals get unwieldy fast. clsx handles conditional class toggling cleanly. tailwind-merge (twMerge) deduplicates conflicting Tailwind classes (e.g., when a consumer passes className="p-4" to a component that already has p-2, the last one wins instead of both applying).

import clsx from "clsx";
import { twMerge } from "tailwind-merge";

// Combine both: cn() is a convention in shadcn/ui and most Tailwind projects
function cn(...inputs) { return twMerge(clsx(...inputs)); }

Tailwind v4 — CSS-first configuration

Tailwind v4 (2025) replaces tailwind.config.js with an @theme block directly in your CSS file. No JS config file needed for custom tokens.

/* globals.css */
@import "tailwindcss";

@theme {
  --color-primary: oklch(55% 0.2 260);
  --color-surface: oklch(98% 0 0);
  --font-sans: "Inter", sans-serif;
}

/* Use as normal Tailwind utilities: bg-primary, text-surface, font-sans */

If you're on an existing v3 project, tailwind.config.js still works. For new projects in 2026, prefer the v4 CSS-first approach.

Design tokens

Don't spread raw colors through your JSX. Put them in Tailwind's config (or a CSS variable layer), and reference names. bg-primary, text-body. Refactor-friendly, rebrandable, accessible.

Python bridge

There's no Python styling ecosystem directly comparable. The closest mental model: Tailwind utility classes are like inline styles that compile away — similar to how you'd configure visual properties in a declarative config (like a Matplotlib stylesheet) rather than imperatively setting attributes. CSS Modules are close to Django's template inheritance scoping — styles are local by default.
