Part 4 · React · 4a

React Mental Model

React is a declarative UI library. You describe what the UI should look like for a given state; React figures out the DOM changes. You never write "when X, update element Y" — that's the old imperative model.

The one-sentence model

UI = f(state). Your components are pure functions from props + state to a virtual DOM tree. React diffs the new tree against the old one and applies the minimal set of real DOM changes.

Unidirectional data flow

State lives somewhere. It flows down as props. Events flow up via callbacks. No two-way binding. This predictability is the whole point.

Analogy

Imagine a spreadsheet. The state is the raw input cells. Components are the formulas. Change an input — the dependent cells recompute. You don't tell individual cells to update; the spreadsheet engine does it for you. React is that engine for UI.

Rendering ≠ DOM update

Critical distinction. "Rendering" in React = calling your component function to get a new virtual tree. Running your component function 100 times in a second doesn't touch the DOM 100 times; React batches and diffs. Optimization discussions get muddy when people confuse the two.

Concrete form of UI = f(state)

function Counter() {
  const [count, setCount] = useState(0);
  // Every time count changes, this function re-runs and returns a new description.
  // React handles turning that description into real DOM.
  return ;
}

Concurrent rendering

React 18+ has a scheduler that can pause, interrupt, and restart renders. This is what makes useTransition and useDeferredValue possible: React can abandon a low-priority render mid-flight when higher-priority work arrives (like a keypress). Implication: your component function must be a pure function of its inputs — no side effects during render — because React may call it more than once to get a result it keeps.

Forward pointer — where does this code run?

In a browser-only React app, components always run in the browser. In Next.js (Part 5), components can run on the server — Server Components render to HTML at request time and never ship JS to the client. The UI = f(state) model still holds, but "state" on the server is request data, not useState. Details in 4g and Part 5.
