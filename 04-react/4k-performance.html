Part 4 · React · 4k

Performance — Profiling, Memoization, Virtualization

The rule: measure, don't guess

Most React apps are fast enough. Premature memoization slows the build and the dev experience without helping users. Open React DevTools Profiler, record an interaction, look for components rendering far more than expected. The flame chart in the Profiler shows each component as a bar — width is render time, grey bars were skipped (memoized). Look for unexpectedly wide bars or components that fire on every interaction when they shouldn't.

The actual levers

  • React.memo — skips re-render if props are referentially equal. Pair with useMemo/useCallback on the parent.
  • Virtualization — render only visible list items. TanStack Virtual. Essential above ~1000 rows.
  • Code splitting — React.lazy + Suspense, or route-based splits in Next. Ship less JS.
  • useTransition / useDeferredValue — let React deprioritize expensive updates so input stays responsive.

React Compiler — automatic memoization in React 19

The React Compiler (stable in React 19) analyzes your component code at build time and automatically inserts useMemo, useCallback, and memo wrapping where they're safe and beneficial. In a compiler-enabled codebase, manually writing these three APIs for performance is largely unnecessary — you write natural code and the compiler handles referential stability.

The compiler does not change runtime semantics. It only optimizes what's already valid React code. Impure components (direct state mutation, side effects during render) will not be optimized and may be flagged.

npm install babel-plugin-react-compiler
# or: Next.js 15+ enables it via next.config experimental.reactCompiler: true
In practice

On new projects with the compiler enabled: write clean code, skip manual useMemo/useCallback/memo unless you have a specific non-performance reason (e.g., stable callback identity for a third-party library). On projects without it: the old rules still apply.

Suspense as a performance boundary

<Suspense> is not just error handling — it's a progressive loading primitive. Wrap subtrees in Suspense to stream their content independently. In Next.js, a slow database query in a Server Component suspends only its Suspense boundary; the rest of the page renders immediately. This is the mechanism behind Next.js loading.tsx.

// Fast parts render immediately; slow DB query streams in later
export default function Page() {
  return (
    <>
      
                        {/* renders instantly */}
      }>
                   {/* streams in when ready */}
      
    
  );
}
The "wrap everything in useMemo" cargo cult

Memoizing a const doubled = useMemo(() => n * 2, [n]) is slower than not — you paid for a dependency compare and memory allocation to save a multiplication. Only memoize when (a) the computation is actually expensive, or (b) you need referential stability for a downstream memo, effect deps, or hook input. With the React Compiler enabled, this concern largely disappears.

Python bridge

Python has no direct equivalent to React's render model, but the performance intuition maps to Django's select_related/prefetch_related: you profile first, identify the N+1 query, then fix it. Don't add select_related everywhere preemptively — same principle as not wrapping everything in useMemo.
