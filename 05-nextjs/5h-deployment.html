Part 5 · Next.js · 5h

Deployment — Vercel vs Self-hosted

Next.js is built by Vercel. Vercel is the easiest and most complete host — zero config, edge network, image optimization, ISR, preview deployments. If you're small, just use it.

Self-hosting with standalone output

// next.config.js
module.exports = { output: "standalone" };

This produces a minimal node_modules-free server. Build a Docker image, run it on Fly.io / Railway / AWS / any container host. Some Vercel features (ISR on-demand, image optimization) need additional work or plugins to match.

What changes when you self-host

  • Image optimization needs a loader (Cloudinary, Imgix) or a sidecar like sharp.
  • ISR and revalidation require a cache backend; @neshca/cache-handler with Redis is a popular choice.
  • Edge middleware only truly runs on the edge on Vercel/Cloudflare. On your own Node server, middleware runs in Node (fine, just different perf profile).

Cloudflare Workers / Pages

@cloudflare/next-on-pages adapts the Next.js output to run on Cloudflare's network. Trade-off: full Edge runtime constraints everywhere, no Node APIs, but truly global distribution at Cloudflare pricing. Best for apps that can stay within Edge runtime limits.

npx @cloudflare/next-on-pages  # build adapter
wrangler pages deploy .vercel/output/static

Environment variables

Two namespaces, very different behavior:

  • NEXT_PUBLIC_* — inlined into the client bundle at build time. Visible to every user. Never put secrets here.
  • All other vars — server-only. Accessible in server components, actions, API routes. Never sent to the browser.
Rule

If a variable name starts with NEXT_PUBLIC_, it is baked into the JS bundle and visible in the browser's source. Putting a DB password or API secret there exposes it to the world. Use non-prefixed env vars for anything sensitive, and access them only in server-side code.

Post-response work — next/after

after() schedules a callback to run after the response is sent. Use it for fire-and-forget logging, analytics, or cleanup that shouldn't block the response.

import { after } from "next/server";

export async function GET() {
  after(async () => {
    await analytics.track("page_view");  // runs after response is flushed
  });
  return Response.json({ ok: true });
}

Observability — instrumentation.ts

Next.js calls the exported register() function once when the server starts. Use it to initialize OpenTelemetry, Sentry, or custom loggers.

// instrumentation.ts (project root)
export async function register() {
  if (process.env.NEXT_RUNTIME === "nodejs") {
    const { init } = await import("./sentry.server.config");
    init();
  }
}
// For Sentry, the recommended approach is next.config.ts + withSentryConfig() wrapper.
