App Router Architecture

The folder structure is the routing.

app/
  layout.tsx           # shared shell
  page.tsx             # /
  loading.tsx          # Suspense fallback for this segment
  error.tsx            # Error boundary for this segment
  not-found.tsx
  (marketing)/         # route group — not in URL
    about/page.tsx     # /about
  blog/
    [slug]/page.tsx    # /blog/:slug
    [...catchall]/page.tsx
  api/
    users/route.ts     # /api/users — route handlers

Layouts — persistent shells

A layout.tsx wraps every page in its segment and persists across navigation (no re-mount). Great for headers, nav, sidebars.

// app/layout.tsx
export default function RootLayout({ children }) {
  return (
    
      
        

        
{children}

      
    
  );
}

Special files

  • loading.tsx — Suspense boundary. Shows while async data in the page is pending.
  • error.tsx — Error boundary. Must be "use client" — React error boundaries require client-side lifecycle methods.
  • template.tsx — Like layout.tsx but re-mounts on every navigation. Use when you need effects to re-run on route change (e.g., page-view analytics, scroll reset).
  • not-found.tsx — 404 UI for that segment.
  • route.ts — REST-style handlers (export async function GET/POST(req) {...}).
Gotcha

error.tsx silently breaks if you forget "use client" at the top — Next will throw a build error or show a blank boundary. Always add it.

Parallel routes

Render multiple independent pages in the same layout simultaneously. Each slot is a folder prefixed with @.

app/dashboard/
  layout.tsx          # receives @team and @analytics as props
  @team/
    page.tsx
  @analytics/
    page.tsx
  page.tsx
// app/dashboard/layout.tsx
export default function DashboardLayout({ children, team, analytics }) {
  return (
    <div>
      {children}
      <aside>{team}</aside>
      <aside>{analytics}</aside>
    </div>
  );
}

Each slot fetches and renders independently — handy for dashboards with multiple unrelated data streams.

Intercepting routes

Override what a URL renders within the current layout context, without leaving the page. Prefix the segment with (.) (same level), (..) (one up), or (...) (root).

app/feed/
  page.tsx
  @modal/
    (.)photo/[id]/
      page.tsx          # intercepts /photo/[id] when navigated from /feed
app/photo/
  [id]/page.tsx         # direct URL still shows full page

Classic use case: clicking a photo in a feed opens a modal overlay; sharing the direct URL or refreshing shows the standalone photo page.

Static params for dynamic segments

generateStaticParams tells Next which dynamic values to pre-render at build time (SSG for dynamic routes).

// app/blog/[slug]/page.tsx
export async function generateStaticParams() {
  const posts = await db.posts.findMany({ select: { slug: true } });
  return posts.map((p) => ({ slug: p.slug }));
}
// Next builds /blog/hello-world, /blog/getting-started, etc. at build time.

Metadata API

Export metadata (static) or generateMetadata (dynamic, runs on server) from any page.tsx or layout.tsx.

// Static — same for all visitors
export const metadata = {
  title: "My Blog",
  description: "Thoughts on software.",
};

// Dynamic — per request; has access to params and fetched data
import type { Metadata } from "next";

export async function generateMetadata(
  { params }: { params: Promise<{ slug: string }> }
): Promise<Metadata> {
  const { slug } = await params;
  const post = await db.posts.findBySlug(slug);
  return {
    title: post.title,
    openGraph: { images: [post.ogImage] },
  };
}
Python bridge

Django's URL patterns are explicit (path("blog/<slug:slug>/")). Next's file-system routing is implicit — the folder name is the pattern. Parallel routes and intercepting routes have no Django equivalent; they're specific to the client-side navigation model.
