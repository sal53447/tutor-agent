Part 5 · Next.js · 5d

Data Fetching & Caching

Next.js extends fetch with caching and revalidation semantics, and has four layered caches. Understanding them is most of being productive in Next.

Next 14 vs Next 15 — breaking default

In Next 14, fetch() defaulted to cached indefinitely (SSG-like). In Next 15, the default flipped to no-store — every fetch is fresh unless you opt in. The examples below reflect Next 15 behavior. If you're reading old tutorials showing "cached by default," they're describing Next 14.

// Next 15 default: no-store (dynamic, always fresh)
const res = await fetch("https://api.example.com/data");

// Opt into caching: cache indefinitely (Next 15 SSG-like, was the OLD default)
const res = await fetch(url, { cache: "force-cache" });

// Revalidate every 60s (ISR-like)
const res = await fetch(url, { next: { revalidate: 60 } });

// Tag-based — explicit invalidation via revalidateTag()
const res = await fetch(url, { next: { tags: ["products"] } });

Cache invalidation — revalidateTag and revalidatePath

These are the two primitives for purging cached data. Call them from server actions or route handlers after a mutation.

import { revalidateTag, revalidatePath } from "next/cache";

// Purge all cached data tagged "products" — across all routes
revalidateTag("products");

// Purge the full route cache for a specific path
revalidatePath("/products");
revalidatePath("/products/[slug]", "page");  // dynamic segment variant
Rule of thumb

Prefer revalidateTag over revalidatePath — it's surgical (only the data) rather than nuking the whole rendered page. Tag your fetches at the resource level ("products", "user-42"), then call revalidateTag in the mutation action.

The four caches — what they actually are

  1. Request memoization — per-render, in-memory dedupe of identical fetch calls within one server render pass. Two components fetching the same URL → one HTTP request. Lives only for the duration of that render.
  2. Data cache — cross-request, persistent on the server (or a cache backend like Redis). Survives deploys, shared across users. This is what revalidateTag and revalidatePath purge.
  3. Full route cache — the rendered HTML of a static route, cached at build or after first render.
  4. Router cache — client-side, in-memory cache of prefetched RSC payloads. Next.js manages it automatically.
Python bridge

Django's cache.set("key", value, timeout) is closest to Next's Data Cache with revalidate. Django's cache_page decorator maps to Next's Full Route Cache. Request memoization has no Django equivalent — it's specific to React's single-render tree deduplication.

unstable_cache — cache ORM calls and SDK fetches

fetch caching only works for HTTP calls. For Prisma, Drizzle, or any SDK that doesn't use fetch, wrap the call with unstable_cache.

import { unstable_cache } from "next/cache";
import { db } from "@/lib/db";

// Wrapped function is cached with the given tags and revalidation period.
// The cache key is derived from the function body + arguments.
export const getProducts = unstable_cache(
  async (categoryId: string) => {
    return db.product.findMany({
      where: { categoryId },
      orderBy: { createdAt: "desc" },
    });
  },
  ["products"],            // cache key prefix / tags
  {
    tags: ["products"],    // used by revalidateTag("products")
    revalidate: 3600,      // also time-bound: revalidate every hour
  }
);

// In a server component:
const products = await getProducts(params.categoryId);
Gotcha

unstable_cache is still the production-stable API in Next 15 despite the name. The replacement is the use cache directive (see forward-pointer below) which is still stabilizing. Use unstable_cache today.

Forward pointer: use cache / cacheLife / cacheTag (Next 15 dynamicIO)

Next 15 introduced an experimental directive-based caching model as part of dynamicIO. Instead of wrapping with unstable_cache, you annotate the function or component directly:

// Experimental — requires dynamicIO: true in next.config.ts
"use cache";
import { cacheLife, cacheTag } from "next/cache";

export async function getProducts(categoryId: string) {
  cacheTag("products");         // same as unstable_cache tags
  cacheLife("hours");           // named revalidation profile ("seconds" | "minutes" | "hours" | "days" | "weeks" | "max")
  return db.product.findMany({ where: { categoryId } });
}

This API is not yet stable. Use unstable_cache for production code; keep an eye on use cache as it matures.

  2. You have a Drizzle query that fetches the product catalog. How do you cache it with tag-based invalidation?
  3. What is the difference between Request Memoization and the Data Cache?
  4. After updating a product in a server action, which call purges only the product-related cached data?

Expected answers: (1) Fresh / no-store — you must opt in with force-cache or revalidate. (2) Wrap the query in unstable_cache with tags: ["products"]. (3) Request Memoization is per-render in-memory (one render pass, no persistence); Data Cache is cross-request persistent on the server. (4) revalidateTag("products").
