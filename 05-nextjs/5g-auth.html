Part 5 · Next.js · 5g

Auth in Next.js

The ecosystem default is Auth.js (previously NextAuth). For most apps it's the right answer — OAuth providers, email, sessions, all integrated with middleware and server components.

// auth.ts
import NextAuth from "next-auth";
import Google from "next-auth/providers/google";

export const { auth, handlers, signIn, signOut } = NextAuth({
  providers: [Google],
  callbacks: {
    async session({ session, token }) {
      session.user.id = token.sub;
      return session;
    },
  },
});

// In a server component:
const session = await auth();
if (!session) redirect("/login");

Three-layer defense — each layer has a different job

  • Middleware — coarse, stateless, JWT-based. Blocks unauthenticated requests before they reach the app. Fast; no DB. Use jose to verify the JWT (see 5f). Cannot check fine-grained roles — it only has what's in the token.
  • Layout / Server component — fine-grained. Has the session; can query the DB for the user's actual role or plan. Redirect or render fallback UI here for role-gated pages.
  • Server action / route handler — always re-authorize. Never trust the client. A user can call a server action directly; the action must verify permission for that specific operation regardless of what the UI shows.
// Server action — always re-check, never rely on middleware alone
export async function deletePost(postId: string) {
  const session = await auth();
  if (!session) throw new Error("Unauthenticated");

  const post = await db.post.findUnique({ where: { id: postId } });
  if (post?.authorId !== session.user.id) throw new Error("Forbidden");

  await db.post.delete({ where: { id: postId } });
  revalidatePath("/posts");
}

Session cookies vs JWT

  • Auth.js default — JWT stored in a cookie (encrypted). No DB lookup per request. Token revocation requires short expiry or a blocklist.
  • DB sessions (Auth.js with strategy: "database", Lucia, Better-Auth) — session ID in cookie, session record in DB. Instant revocation; costs a DB read per request. Prefer for apps where logout-everywhere is important.

CSRF and server actions

Next.js automatically adds CSRF protection to server actions by checking the Origin header against the host. This covers standard setups. Gaps to know about:

  • Custom domains behind a proxy may need NEXTAUTH_URL set correctly so the origin check passes.
  • If you call server actions from a separate origin (e.g., a native app), the built-in check will block them — use route handlers with explicit CORS instead.
Alternatives
  • Clerk, WorkOS, Auth0 — managed services. Great if you want SSO, MFA, enterprise features without building them.
  • Better-Auth — the current actively-maintained lightweight alternative. Lucia (v2 and earlier) is being sunset — don't start new projects on Lucia; migrate to Better-Auth if you're already on it.
Python bridge

Django's @login_required decorator is middleware-layer protection. Django's permission_required is the server-component-layer check. And validating ownership inside a view function (if post.author != request.user) is the action-layer re-authorization. Same three layers, same reasoning — Next.js just makes you more explicit about where each one lives.

Self-check
  1. Why can't middleware alone be the only auth check for a mutation?
  2. What is the difference between Auth.js JWT sessions and DB sessions? When would you prefer each?
  3. A user logs out. With JWT sessions, what's the challenge? How do DB sessions solve it?

Expected answers: (1) Middleware is stateless and coarse — it only checks "is there a valid token?", not "does this user own this resource?" A server action must re-verify ownership before mutating. (2) JWT: no DB read, but revocation is hard. DB: instant revocation, costs a DB lookup per request. Prefer DB sessions when logout-everywhere or role changes need immediate effect. (3) JWT tokens are self-contained and valid until expiry — you can't invalidate them without a blocklist. DB sessions have a record you can delete immediately.
