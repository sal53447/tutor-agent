Part 5 · Next.js · 5a

The Rendering Spectrum

Next.js's raison d'être: a plain React app renders in the browser (CSR), which is bad for SEO, slow on first paint, and expensive on mobile. Next offers every rendering strategy on the spectrum.

Python bridge

Django's template views are SSR: the server renders HTML per request. Flask with render_template is the same. Next.js adds SSG (build-time render), ISR (scheduled rebuild), and Streaming (chunked HTTP) on top of what Django already gives you — plus a path back to pure CSR for app-like UIs.

ModeHTML generatedWhen
CSR (client-side)Browser runs JS, React builds DOMApp-like UIs. Dashboards behind login. Poor SEO, slow first paint.
SSR (server-side)Server renders HTML per requestDynamic, personalized pages. Good SEO, good first paint, server-bound.
SSG (static)HTML built at build timeMarketing, blogs, docs. Fast, cheap, cacheable. Can't be per-user.
ISR (incremental static)SSG with on-demand rebuildMostly static content that can update (e.g., product pages on an e-commerce site).
StreamingHTML streamed as it rendersModern default. Fast initial HTML + progressively enhanced UI.

Next.js (App Router) lets you mix modes per route. A marketing page can be static; a dashboard can stream server components with client islands for interactivity. CSR was fine in Part 4 because you were building self-contained browser apps — but as soon as SEO, first-paint budget, or server resources matter, you need the strategies below.

Streaming — how it actually works

Classic SSR sends nothing until the full HTML tree is ready. Streaming uses chunked HTTP transfer encoding: the server flushes the page shell immediately, then sends more HTML chunks as each suspended subtree resolves. The browser progressively renders each chunk. No second network round-trip; no client JS needed for the initial paint.

// app/dashboard/page.tsx
import { Suspense } from "react";
import { RecentOrders } from "./recent-orders"; // async server component

export default function Dashboard() {
  return (
    <main>
      <h1>Dashboard</h1>
      <Suspense fallback={<p>Loading orders…</p>}>
        <RecentOrders />   {/* streams in when its await resolves */}
      </Suspense>
    </main>
  );
}

Partial Prerendering (PPR)

PPR is a hybrid that ships a static HTML shell at build time, then streams dynamic holes into it at request time — combining the cold-start speed of SSG with per-request freshness for the parts that need it. Opt in per-route or globally (Next 15, still experimental).

// next.config.ts
export default {
  experimental: { ppr: "incremental" },  // or true for all routes
};

// app/product/[slug]/page.tsx
export const experimental_ppr = true;  // opt this route into PPR

import { Suspense } from "react";
import { StaticProductInfo } from "./static-info";      // rendered at build
import { DynamicStockLevel } from "./dynamic-stock";    // streamed at request

export default function ProductPage() {
  return (
    <>
      <StaticProductInfo />
      <Suspense fallback={<span>Checking stock…</span>}>
        <DynamicStockLevel />
      </Suspense>
    </>
  );
}
Rule of thumb

Wrap each independently-dynamic piece in its own <Suspense> boundary. The static parts of the page are served from the CDN edge instantly; only the dynamic subtrees wait on the origin.

Self-check
  1. What is the mechanical difference between SSR and Streaming? (Hint: think HTTP transfer.)
  2. PPR serves a page in two stages — what are they, and where does each run?
  3. You're building a product page: hero image + name are the same for all users; the "in stock" badge hits a live inventory API. Which rendering strategy fits best?

Expected answers: (1) SSR buffers and sends the full HTML in one response; Streaming sends it in chunks via chunked transfer encoding as Suspense boundaries resolve. (2) Static shell from CDN at request time; dynamic holes streamed from origin. (3) PPR — static shell for hero/name, suspended dynamic component for stock level.
